Mẫu Luật Phòng Thủ: JWT Attacks & Session/Cookie Forge

  • Nguồn tham chiếu: attack/jwt_attacks.html, attack/session_cookie_forge.html, attack/access.html
  • Nhóm OWASP CRS liên quan: attack-protocol / attack-injection-generic
  • Dải Rule ID: 25200–25299 (Config Type: MODSEC)
  • Khả năng vá bằng WAF: Trung bình–Cao đối với lỗ hổng header JWT (alg:none, kid traversal/SQLi, jku/x5u SSRF, jwk injection); WAF không vá được secret yếu bị crack offline để tự ký lại token (cần đổi secret ở app nếu được phép).

1. Dấu hiệu tấn công chính cần chặn

  • JWT dùng thuật toán none ("alg":"none", Base64URL bắt đầu bằng eyJhbGciOiJub25l, eyJhbGciOiJOT05F, eyJhbGciOiJOb25l) hoặc thiếu phần chữ ký (header.payload.).
  • Tiêm vào header JWT: jku, x5u, jwk, x5c (ép server tải public key của kẻ tấn công) hoặc kid chứa ../, ', ;, | (LFI/SQLi/CMDi qua kid).
  • Lạm dụng thuật toán đổi từ RS256 sang HS256 nếu app chỉ dùng RS256.

2. Bộ luật ModSecurity v3 mẫu

# [25201] Chặn JWT có alg=none (sau khi giải mã Base64 ở Authorization header và Cookie)
SecRule REQUEST_HEADERS:Authorization|REQUEST_COOKIES "@rx (?i)\"alg\"\s*:\s*\"none\"" \
    "id:25201,phase:1,pass,log,t:none,t:base64Decode,msg:'JWT: alg none rejected',tag:'jwt',logdata:'%{MATCHED_VAR_NAME}'"

# [25202] Chặn JWT không có chữ ký (dạng header.payload. rỗng phần 3)
SecRule REQUEST_HEADERS:Authorization|REQUEST_COOKIES "@rx (?i)(?:^|Bearer\s+)eyJ[A-Za-z0-9_-]{8,}\.eyJ[A-Za-z0-9_-]{8,}\.(?:\s*$)" \
    "id:25202,phase:1,pass,log,t:none,msg:'JWT: Empty signature segment',tag:'jwt',logdata:'%{MATCHED_VAR_NAME}'"

# [25203] Chặn JWT header chứa jku / x5u / jwk / x5c (key injection / SSRF)
SecRule REQUEST_HEADERS:Authorization|REQUEST_COOKIES "@rx (?i)\"(?:jku|x5u|jwk|x5c)\"\s*:" \
    "id:25203,phase:1,pass,log,t:none,t:base64Decode,msg:'JWT: Untrusted key header (jku/x5u/jwk)',tag:'jwt',logdata:'%{MATCHED_VAR_NAME}'"

# [25204] Chặn tấn công qua trường kid trong JWT (Path Traversal / SQLi / CMDi)
SecRule REQUEST_HEADERS:Authorization|REQUEST_COOKIES "@rx (?i)\"kid\"\s*:\s*\"[^\"]{0,120}(?:\.\.|/|\\|'|--|;|\||`|\$\()" \
    "id:25204,phase:1,pass,log,t:none,t:base64Decode,msg:'JWT: Suspicious kid injection',tag:'jwt',logdata:'%{MATCHED_VAR_NAME}'"

# [25205] Nếu app CHỈ dùng RS256, chặn HS256/HS384/HS512 (chống Algorithm Confusion)
# (Chỉ bật rule này sau khi xác nhận trên Traffic log rằng token hợp lệ dùng RS256!)
SecRule REQUEST_HEADERS:Authorization|REQUEST_COOKIES "@rx (?i)\"alg\"\s*:\s*\"HS(?:256|384|512)\"" \
    "id:25205,phase:1,pass,log,t:none,t:base64Decode,msg:'JWT: Unexpected HMAC alg (possible confusion)',tag:'jwt',logdata:'%{MATCHED_VAR_NAME}'"

3. Giải thích chi tiết từng luật

Rule ID Biến & Transform Cơ chế hoạt động Mức độ an toàn bật deny
25201 REQUEST_HEADERS:Authorization\|REQUEST_COOKIES (t:base64Decode) Chặn tấn công alg: none (không phân biệt hoa/thường None, NONE) khi kẻ tấn công bỏ qua bước kiểm tra chữ ký JWT. Rất cao
25202 REQUEST_HEADERS:Authorization\|REQUEST_COOKIES Chặn JWT có phần chữ ký rỗng (header.payload.) kể cả khi header không ghi alg: none. Rất cao
25203 REQUEST_HEADERS:Authorization\|REQUEST_COOKIES (t:base64Decode) Chặn các trường header JWT dùng để tiêm khóa giả (jku, x5u, jwk, x5c). Rất cao
25204 REQUEST_HEADERS:Authorization\|REQUEST_COOKIES (t:base64Decode) Chặn injection trong trường kid của JWT header (chứa .., /, \, ', --, ;, |, $(). Rất cao
25205 REQUEST_HEADERS:Authorization\|REQUEST_COOKIES (t:base64Decode) Chống Algorithm Confusion (RS256 → HS256): chặn token dùng HS256/HS384/HS512. CHỈ bật nếu app dùng RS256/ES256

4. Cách sửa khi gặp trường hợp thực tế (Ví dụ)

Ví dụ 1: App lưu JWT trong header tùy chỉnh X-Auth-Token hoặc tham số query ?token=eyJ...

Mặc định 25201–25204 chỉ soi Authorization và REQUEST_COOKIES. Nếu Traffic log cho thấy app dùng header X-Auth-Token: - Cách sửa: Thêm |REQUEST_HEADERS:X-Auth-Token vào danh sách biến của 25201–25204:

# Bản sửa thực tế từ [25201] khi app truyền JWT qua header X-Auth-Token
SecRule REQUEST_HEADERS:Authorization|REQUEST_HEADERS:X-Auth-Token|REQUEST_COOKIES "@rx (?i)\"alg\"\s*:\s*\"none\"" \
    "id:25201,phase:1,deny,status:403,log,t:none,t:base64Decode,msg:'JWT: alg none rejected',tag:'jwt',logdata:'%{MATCHED_VAR_NAME}'"

Ví dụ 2: App dùng RS256 và đối thủ gửi HS256 để lừa server verify bằng public key

Kiểm tra 1 request hợp lệ của bot trên Traffic log: decode phần đầu JWT thấy {"alg":"RS256","typ":"JWT"}. Lúc này bạn đổi 25205 từ pass,log sang deny,status:403,log để chặn ngay mọi token HS256.

Ví dụ 3: Đối thủ giả mạo Flask session cookie có "role": "admin" trên route chỉ dành cho user thường

Nếu app để lộ SECRET_KEY mà bạn không sửa được code, bạn có thể tạm chặn cookie chứa payload "is_admin":true trên các route không phải admin (nếu bot SVC không đăng nhập admin trên route đó) và kết hợp rule Phase 4 chặn lộ Flag (26205).

5. Lưu ý tránh False Positive & Giới hạn WAF

  • Cẩn thận với 25205: Phần lớn bài CTF dùng HS256 mặc định — tuyệt đối không đổi 25205 sang deny trừ khi đã xác nhận 100% app dùng RS256/ES256.
  • Nếu đối thủ crack được SECRET_KEY yếu của Flask/JWT rồi tự ký cookie giả có cấu trúc hợp lệ y hệt user thật, WAF không phân biệt được chữ ký hợp lệ giả mạo; khi đó tập trung chặn các hành vi leo thang đặc quyền (xem thêm 13_idor_mass_assignment.md) và chặn lộ Flag ở Phase 4.
