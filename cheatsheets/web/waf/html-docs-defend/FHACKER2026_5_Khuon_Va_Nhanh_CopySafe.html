FHACKER 2026 — 5 Khuôn Vá Nhanh (bản Copy-Safe, đã sửa lỗi)

Dùng file này thay cho block “5 Khuôn mẫu vá vạn năng” cũ. Bản cũ dùng placeholder <<<...>>>, dễ copy sót; path @streq dễ bypass bằng case/trailing slash; và không chống JSON array.

Quy ước placeholder: thay tất cả __...__ trước khi Save. - __ROUTE__ — route thật, không gồm query. Ví dụ /api/user. - __PARAM__ — tên param trần. Ví dụ id, không điền json.id. - __ID__ — số rule 5 chữ số trong 20000–29999, không trùng. - __REGEX__ — regex allowlist, lấy từ FHACKER2026_Regex_CopySafe.md. - __FIELDS__ — danh sách field cách nhau bằng |. Ví dụ role|is_admin|balance. - __FLAG_ROUTE__ — route trả cờ hợp lệ của bot. Ví dụ /api/flag.

Quy tắc chung: 1. Luôn bắt đầu pass,log → test 200/403 → chờ 1 chu kỳ 30 giây → đổi deny,status:403,log. 2. Không chèn dòng trống/comment giữa dòng cha và dòng con của chain. 3. Không để khoảng trắng sau dấu \ nối dòng. 4. Backup rule cũ trước khi Save; Save xong xem chuông báo lỗi + error.log. 5. Nếu route có ký tự regex đặc biệt (. + ( ) [ ]), escape bằng \.

KHUÔN 1 — Allowlist chặt (SQLi / LFI / RCE / IDOR)

# ── KHUÔN 1: ALLOWLIST CHẶT ──
# THAY:
#   __ROUTE__ = /api/user
#   __PARAM__ = id
#   __ID__    = 27101
#   __REGEX__ = ^[0-9]{1,10}$
#
# Bước 1: giữ pass,log → Save → test 200/403 → xem cột WAF
# Bước 2: đổi pass,log thành deny,status:403,log → Save
SecRule REQUEST_FILENAME "@rx (?i)^__ROUTE__/?$" \
    "id:__ID__,phase:2,pass,log,t:none,t:normalizePath,chain,msg:'Invalid __PARAM__',tag:'allowlist',logdata:'%{MATCHED_VAR_NAME}=%{MATCHED_VAR}'"
    SecRule ARGS:__PARAM__|ARGS:json.__PARAM__ "!@rx __REGEX__" "t:none,t:urlDecodeUni,t:urlDecodeUni"

Đã sửa so với bản cũ: - @rx (?i)^__ROUTE__/?$ + t:normalizePath: chống /API/user, /api/user/, //api/user. - Có logdata để biết param nào gây khớp. - (?i) giúp không phải lo hoa/thường của route.

Vẫn cần kiểm tra: - JSON array: {"id":[1,2]} không nằm trong ARGS:json.id; thêm array guard ở Mục 6 nếu app không cần mảng. - Param tùy chọn rỗng: nếu ?sort= hợp lệ, dùng ^(?:asc|desc)?$. - Nested JSON: json.data.id không khớp ARGS:json.id; phải dùng đúng tên thực tế. - Regex tên file vẫn cho shell.php.jpg; dùng thêm rule 20411 chặn double-extension.

KHUÔN 2 — SQLi / XSS trên ô text tự do

# ── KHUÔN 2: SQLi/XSS TRÊN Ô TEXT TỰ DO ──
# THAY:
#   __ROUTE__ = /api/comment
#   __PARAM__ = comment
#   __ID__    = 27102
#
# Mặc định @detectSQLi. Nếu là ô bình luận/hồ sơ, đổi sang @detectXSS
# và thêm t:htmlEntityDecode,t:jsDecode (xem biến thể bên dưới).
SecRule REQUEST_FILENAME "@rx (?i)^__ROUTE__/?$" \
    "id:__ID__,phase:2,pass,log,t:none,t:normalizePath,chain,msg:'Attack in __PARAM__',tag:'sqli-xss',logdata:'%{MATCHED_VAR_NAME}=%{MATCHED_VAR}'"
    SecRule ARGS:__PARAM__|ARGS:json.__PARAM__ "@detectSQLi" "t:none,t:urlDecodeUni,t:urlDecodeUni"

Biến thể XSS — thay dòng con bằng:

    SecRule ARGS:__PARAM__|ARGS:json.__PARAM__ "@detectXSS" "t:none,t:urlDecodeUni,t:urlDecodeUni,t:htmlEntityDecode,t:jsDecode"

Lưu ý: - @detectSQLi/@detectXSS có thể false-positive với text hợp lệ (dấu ', từ khóa SQL, HTML thật). Test với traffic bot trước. - Nếu ô text quá dài/đa dạng, cân nhắc để pass,log lâu hơn hoặc chỉ chặn pattern rõ ràng. - JSON array/nested cũng có thể lọt; kiểm tra ARGS_NAMES thực tế.

KHUÔN 3 — Mass Assignment / Leo quyền

# ── KHUÔN 3: MASS ASSIGNMENT / LEO QUYỀN ──
# THAY:
#   __ROUTE__  = /api/profile
#   __FIELDS__ = role|is_admin|balance
#   __ID__     = 27103
#
# Regex bắt: role, user[role], json.role, json.role.array_0
SecRule REQUEST_FILENAME "@rx (?i)^__ROUTE__/?$" \
    "id:__ID__,phase:2,pass,log,t:none,t:normalizePath,chain,msg:'Blocked privileged field',tag:'mass-assignment',logdata:'%{MATCHED_VAR_NAME}'"
    SecRule ARGS_NAMES "@rx (?i)(?:^|[.\[])(?:__FIELDS__)(?:\]|\.array_\d+|$)" "t:none"

Đã sửa so với bản cũ: - Thêm \.array_\d+ để bắt "role":["admin"] → json.role.array_0. - Vẫn bắt role, user[role], json.role, json.user.role.

Lưu ý: - Nếu app có field hợp lệ tên role (ví dụ role công việc), đừng đưa role vào __FIELDS__. - Rule chỉ soi ARGS_NAMES; nếu JSON parser không chạy (sai Content-Type), có thể lọt. Kiểm tra Traffic log. - Có thể thêm REQUEST_BODY nếu muốn bắt cả body thô, nhưng dễ false-positive với text có chữ role.

KHUÔN 4 — Shell / Path Traversal trên đúng 1 route

# ── KHUÔN 4: SHELL / PATH TRAVERSAL TRÊN 1 ROUTE ──
# THAY:
#   __ROUTE__ = /api/export
#   __PARAM__ = file
#   __ID__    = 27104
#
# Chặn: ../  ..\  ;  &  |  `  CR LF  <  >  NUL  $(
SecRule REQUEST_FILENAME "@rx (?i)^__ROUTE__/?$" \
    "id:__ID__,phase:2,pass,log,t:none,t:normalizePath,chain,msg:'Traversal/Shell char blocked',tag:'rce-lfi',logdata:'%{MATCHED_VAR_NAME}=%{MATCHED_VAR}'"
    SecRule ARGS:__PARAM__|ARGS:json.__PARAM__ "@rx (?:\.\.[/\x5c]|[;&|`\r\n<>\x00]|\$\()" "t:none,t:urlDecodeUni,t:urlDecodeUni"

Đã sửa so với bản cũ: - Thêm \x00 (Null byte). - Path linh hoạt như KHUÔN 1. - Có logdata.

Lưu ý: - &, <, > có thể hợp lệ trong một số param (ví dụ URL có query). Nếu app dùng param kiểu URL, cân nhắc bỏ & khỏi regex hoặc scope chặt hơn. - Rule chỉ bảo vệ một param; các param khác trên cùng route vẫn có thể bị khai thác. - Với LFI, nên dùng allowlist tên file thay vì blacklist nếu biết định dạng hợp lệ.

KHUÔN 5 — Phase 4: lưới cuối chặn lọt Flag

# ── KHUÔN 5: PHASE 4 — LƯỚI CUỐI CHẶN LỌT FLAG ──
# THAY:
#   __FLAG_ROUTE__ = /api/flag
#   __ID__         = 27105
#
# BẮT BUỘC: để pass,log trước; test bot + response lớn; rồi mới đổi deny.
# CẢNH BÁO: Phase 4 không phải bảo hiểm 100%; nếu route cờ bị lỗi, phải vá gốc.
SecRule REQUEST_FILENAME "!@rx (?i)^__FLAG_ROUTE__(?:/|$)" \
    "id:__ID__,phase:4,pass,log,t:none,t:normalizePath,chain,msg:'FLAG leak detected outside flag route',tag:'flag-leak',logdata:'%{REQUEST_METHOD} %{REQUEST_URI}'"
    SecRule RESPONSE_BODY "@rx FHACKER(?:2026)?\{[0-9a-fA-F]{64}\}" "t:none"

Đã sửa so với bản cũ: - Thêm (?i): /API/flag không bị chặn nhầm. - msg ghi “detected” thay vì “blocked” khi đang pass,log. - Có logdata để biết request nào lọt.

Lưu ý sống còn: - pass,log không chặn. Muốn chặn phải đổi thành deny,status:403,log. - deny ở Phase 4 có thể cắt response/500 → bot báo lỗi → mất SVC. Test với đúng route cờ và response lớn. - Nếu chính __FLAG_ROUTE__ là route bị lỗ hổng, rule này không cứu được vì đã loại trừ route đó. Phải vá gốc ở Phase 1–2. - __FLAG_ROUTE__ có dấu . thì escape thành \..

6. Guard tùy chọn: JSON array & HPP

6.1. Chặn JSON array cho một param (khoanh vùng đúng route)

Dùng khi route __ROUTE__ không cần nhận mảng cho param đó (vd {"id":[1,2]}). Luôn chain theo __ROUTE__ để không chặn nhầm route khác có dùng mảng hợp lệ.

# THAY: __ROUTE__ = /api/user, __PARAM__ = id, __ID_ARRAY__ = 27106
SecRule REQUEST_FILENAME "@rx (?i)^__ROUTE__/?$" \
    "id:__ID_ARRAY__,phase:2,pass,log,t:none,t:normalizePath,chain,msg:'Array not allowed for __PARAM__',tag:'hpp',logdata:'%{MATCHED_VAR_NAME}'"
    SecRule ARGS_NAMES "@rx ^json\.__PARAM__\.array_[0-9]+$" "t:none"

6.2. Chặn trùng tham số HPP (khoanh vùng đúng route)

Dùng khi route __ROUTE__ không được phép nhận ?id=1&id=2.

# THAY: __ROUTE__ = /api/user, __PARAM__ = id, __ID_HPP__ = 27107
SecRule REQUEST_FILENAME "@rx (?i)^__ROUTE__/?$" \
    "id:__ID_HPP__,phase:2,pass,log,t:none,t:normalizePath,chain,msg:'Duplicate __PARAM__',tag:'hpp',logdata:'count=%{MATCHED_VAR} uri=%{REQUEST_FILENAME}'"
    SecRule &ARGS:__PARAM__ "@gt 1" "t:none"

Nếu app có nhu cầu hợp lệ nhận mảng/trùng tham số, không bật các guard này.

7. Test nhanh sau khi dán

# 1. Request sạch — phải 200
curl -i 'http://TARGET/api/user?id=42'

# 2. Request bẩn — sau khi đổi deny phải 403
curl -i 'http://TARGET/api/user?id=1%20OR%201=1'

# 3. JSON bẩn — phải 403
curl -i -X POST 'http://TARGET/api/user' \
  -H 'Content-Type: application/json' \
  -d '{"id":"1 OR 1=1"}'

# 4. JSON array — phải 403 nếu bật array guard
curl -i -X POST 'http://TARGET/api/user' \
  -H 'Content-Type: application/json' \
  -d '{"id":[1,2]}'

# 5. Path biến thể — phải 403 nếu rule path chuẩn
curl --path-as-is -i 'http://TARGET/api/user/?id=1%20OR%201=1'
curl --path-as-is -i 'http://TARGET/API/USER?id=1%20OR%201=1'

# 6. Phase 4 — test pass,log trước, rồi mới deny
curl -i -X POST 'http://TARGET/' \
  --data 'note=FHACKER2026{0123456789abcdef0123456789abcdef0123456789abcdef0123456789abcdef}'

# 7. Route cờ hợp lệ — phải đi qua (không bị 403/500)
curl -i 'http://TARGET/api/flag'

Thay TARGET bằng service của mày. Sau mỗi lần Save, xem Traffic log cột WAF có ID rule không; nếu không, kiểm tra error.log.

8. Checklist trước khi Save

  • [ ] Đã thay tất cả __...__ (route, param, id, regex, fields, flag route).
  • [ ] __ID__ là số 5 chữ số, không trùng rule cũ.
  • [ ] Không có dòng trống/comment giữa dòng cha và dòng con của chain.
  • [ ] Không có khoảng trắng sau dấu \ nối dòng.
  • [ ] Đang để pass,log; đã test 200/403; đã chờ 1 chu kỳ 30 giây.
  • [ ] Đã đổi pass,log → deny,status:403,log (trừ khi cố ý chỉ detect).
  • [ ] Phase 4: đã test với route cờ thật + response lớn; đã xác nhận bot không bị cắt.
  • [ ] Đã backup bản rule đang xanh trước khi Save.
  • [ ] Nếu dùng @detectXSS: đã thêm t:htmlEntityDecode,t:jsDecode.
  • [ ] Nếu app dùng JSON array/trùng tham số hợp lệ: đã cân nhắc guard tương ứng.
