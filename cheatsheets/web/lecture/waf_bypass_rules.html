Khác mọi bài trước (mỗi bài là 1 lỗ hổng cụ thể), bài này là kỹ năng dùng chung: khi payload SQLi/XSS/SSTI/LFI... của bạn bị chặn, làm sao lách; và khi tới lượt phòng thủ, viết rule chặn đúng payload đối thủ mà không tự bắn vào chân mình (chặn nhầm request của chính service, bị trừ SVC).

WAF là gì, bypass/viết rule để làm gì?

WAF (Web Application Firewall) là 1 lớp đứng giữa người dùng và ứng dụng thật, soi từng request, so khớp với các "rule" (thường là regex) để nhận diện payload tấn công và chặn trước khi nó tới được app. Trong F-Hacker, bạn ở cả 2 vai: tấn công — WAF của đối thủ có thể chặn payload chuẩn của bạn, cần biến tấu để lọt qua; phòng thủ — bạn tự viết rule chặn đúng payload đối thủ hay dùng, nhưng không được chặn nhầm request bình thường (quy chế phạt nặng).

Nếu chỉ nhớ một điều WAF so khớp nguyên văn request nó nhìn thấy. Mọi kỹ thuật bypass đều xoay quanh 1 ý tưởng duy nhất: làm cho payload trông khác đi với WAF nhưng app đích vẫn hiểu đúng ý đồ gốc — lợi dụng việc 2 bên (WAF và app) không hiểu request giống hệt nhau 100%.

01 / NỀN TẢNG BẮT BUỘC

Những thứ cần hiểu trước

WAF (Web Application Firewall) — phần mềm/thiết bị đứng chặn giữa Internet và ứng dụng web thật, soi nội dung từng request (URL, header, body) so với tập "rule" đã định nghĩa, chặn request khớp rule tấn công.
ModSecurity — WAF mã nguồn mở phổ biến nhất, dùng ngôn ngữ rule riêng (SecRule), thường đi kèm bộ rule mẫu OWASP CRS (Core Rule Set). Nhiều nền tảng WAF-UI cho CTF (kể cả của BTC F-Hacker) xây trên nền này hoặc tương tự.
DetectionOnly mode — chế độ WAF chỉ ghi log khi rule khớp, KHÔNG thực sự chặn request. Dùng để kiểm tra rule có bắt nhầm request hợp lệ hay không trước khi bật chế độ chặn thật.

Luật chơi (từ quy chế, nhắc lại vì cực kỳ quan trọng):

  • Chặn theo payload, KHÔNG chặn theo IP (mọi request kể cả bot healthcheck BTC đến từ cùng 1 IP — chặn IP là chặn cả bot).
  • KHÔNG deny-all (chặn toàn bộ request).
  • KHÔNG chặn API phục vụ cờ (API nào có bug cố ý — cố ý chặn bị trừ SVC gấp đôi so với chặn nhầm API thường).
  • WAF giới hạn 2 CPU/3GB RAM — rule nặng (regex thảm họa) làm chậm WAF cũng mất điểm SVC.
02 / VÌ SAO BYPASS ĐƯỢC

WAF và app không "nhìn" request giống hệt nhau

WAF là 1 chương trình riêng, dùng engine parse/regex riêng của nó — khác với engine của ứng dụng thật phía sau (PHP, Python, Node...). Hai chương trình khác nhau, viết bởi 2 đội khác nhau, hoàn toàn có thể hiểu cùng 1 chuỗi byte theo 2 cách khác nhau — đây gọi là parser differential. Mọi kỹ thuật bypass WAF về bản chất là tìm ra 1 điểm khác biệt đó: WAF nhìn thấy A (không khớp rule, cho qua), app nhìn thấy B (chính là payload tấn công thật, thực thi bình thường) — dù A và B xuất phát từ cùng 1 request.

Ví dụ dễ hình dung: WAF so khớp chữ hoa/thường nghiêm ngặt (UNION ≠ UnIoN với regex không có cờ i), nhưng SQL hoàn toàn không phân biệt hoa thường ở từ khóa — app vẫn hiểu UnIoN SeLeCt y hệt UNION SELECT.

08 / VIẾT SCRIPT KIỂM TRA RULE TỰ ĐỘNG

Thay vì tự tay gửi từng request, kiểm tra rule bằng script

(A) Bản thủ công — để HIỂU từng bước

import requests

url = "http://TARGET/search"

# Request tấn công (phải bị chặn sau khi viết rule)
r1 = requests.get(url, params={"q": "' UNION SELECT 1,2,3-- -"})
print("Payload tấn công:", r1.status_code)   # mong đợi 403 sau khi bật rule

# Request bình thường (KHÔNG được bị chặn)
r2 = requests.get(url, params={"q": "laptop gaming"})
print("Request thường:", r2.status_code)   # mong đợi 200

(B) Bản gọn chắc — kiểm tra 1 rule với nhiều ca, báo cáo tóm tắt

import requests

url = "http://TARGET/search"
ATTACK_CASES = ["' UNION SELECT 1,2,3-- -", "' OR 1=1-- -", "UnIoN/**/SeLeCt 1,2,3-- -"]
NORMAL_CASES = ["laptop", "ao thun nam", "iPhone 15"]

def test_rule():
    blocked_attacks = sum(1 for p in ATTACK_CASES
                         if requests.get(url, params={"q": p}).status_code == 403)
    blocked_normal = sum(1 for p in NORMAL_CASES
                        if requests.get(url, params={"q": p}).status_code == 403)
    print(f"Chặn đúng payload tấn công: {blocked_attacks}/{len(ATTACK_CASES)}")
    print(f"Chặn NHẦM request thường: {blocked_normal}/{len(NORMAL_CASES)} (phải = 0!)")

test_rule()

(C) Bản tái dùng — chạy lại sau mỗi lần sửa rule, trước khi chuyển sang Block

import requests, sys

ATTACK_CASES = ["' UNION SELECT 1,2,3-- -", "' OR 1=1-- -"]
NORMAL_CASES = ["laptop", "ao thun nam"]

def test_rule(url):
    ok = True
    for p in ATTACK_CASES:
        r = requests.get(url, params={"q": p}, timeout=5)
        if r.status_code != 403:
            print(f"⚠ CHƯA chặn: {p!r} (status {r.status_code})"); ok = False
    for p in NORMAL_CASES:
        r = requests.get(url, params={"q": p}, timeout=5)
        if r.status_code == 403:
            print(f"❌ CHẶN NHẦM: {p!r} -- SỬA RULE NGAY, có thể bị trừ SVC"); ok = False
    if ok:
        print("✅ Rule an toàn để chuyển sang Block")
    return ok

if __name__ == "__main__":
    test_rule(sys.argv[1] if len(sys.argv) > 1 else "http://localhost:8000/search")
Dùng script này mỗi lần sửa ruleChạy lại (C) sau MỖI lần sửa rule trước khi bật Block — nhanh hơn nhiều so với tự tay gửi lại từng request qua Burp mỗi lần.
09 / VÍ DỤ THỰC TẾ END-TO-END

Cả 2 chiều: bypass đối thủ + tự phòng thủ

1
Tấn công — payload chuẩn bị chặn
SQLi ' UNION SELECT... trả 403 trên service đối thủ ⟹ có WAF.
2
Bypass
Thử UnIoN/**/SeLeCt → qua được (status 200, response chứa flag) ⟹ WAF đối thủ chỉ so khớp chữ thường nguyên văn.
3
Phòng thủ — tự xem log traffic
Vào UI WAF của mình, xem log thấy nhiều request có pattern UnIoN.*SeLeCt từ IP lạ (không phải bot healthcheck) ⟹ đối thủ đang dùng chính kỹ thuật này tấn công mình.
4
Viết rule (DetectionOnly trước)
SecRule ARGS "@rx (?i)union\s*(/\*.*?\*/)?\s*select" — bắt cả biến thể hoa/thường và comment chèn giữa.
5
Test bằng script (C) mục 08
Chạy script, xác nhận cả 2 payload tấn công bị 403, cả 2 request thường vẫn 200 ⟹ an toàn.
6
Chuyển sang Block
Bật chế độ Block thật, tiếp tục theo dõi log vài phút để chắc chắn không có request hợp lệ nào bị lọt vào diện chặn.
10 / VIẾT RULE PHÒNG THỦ — CHI TIẾT ĐẦY ĐỦ

Cú pháp, quy tắc, và checklist trước khi Block

A. Cú pháp cơ bản (kiểu ModSecurity, tham khảo nếu UI BTC dùng tương tự)

SecRule BIẾN "@toán_tử giá_trị" \

C. Checklist BẮT BUỘC trước khi chuyển sang Block

Vi phạm = trừ điểm nặng (Điều 3.5, Điều 5)
  • ☐ Rule chặn theo payload, không có điều kiện nào theo IP.
  • ☐ Không phải deny-all (rule chỉ khớp request CỤ THỂ có payload, không khớp mọi request).
  • ☐ Đã kiểm tra rule KHÔNG khớp API phục vụ cờ (API đọc flag hợp lệ của bot healthcheck).
  • ☐ Đã chạy script test (mục 08.C) xác nhận 0 request bình thường bị chặn nhầm.
  • ☐ Regex không có catastrophic backtracking (tránh (a+)+b kiểu lồng nhiều +/* — làm WAF chậm, mất SVC).
  • ☐ Đã bật DetectionOnly và xem log ít nhất vài phút trước khi chuyển Block thật.

12 / NHẬN DIỆN & GIỚI HẠN

Khi nào bypass khả thi / không

Tình huống
✅WAF dùng signature/regex cố định, có khác biệt xử lý so với app thật (case, encode, vị trí tham số).
❌WAF dùng machine learning/behavior-based detection (hiếm trong CTF, phổ biến hơn ở sản phẩm thương mại) — không có "1 kỹ thuật" bypass chung.
❌Rule được viết với (?i) + chuẩn hóa encode/Unicode trước khi so khớp + áp dụng cho MỌI vị trí (ARGS, body, header, cookie) — bề mặt bypass thu hẹp đáng kể, chỉ còn trông chờ vào lỗ hổng trong chính kỹ thuật lỗ hổng đó bị bỏ sót khỏi rule.
13 / BÀI TẬP & THUẬT NGỮ

Luyện tập

⭐ Làm lại: dựng repo 2026-waf-practice, viết 1 rule chặn SQLi theo mẫu mục 10.B, test bằng DetectionOnly, xác nhận không chặn nhầm trước khi Block.

Gợi ý nếu kẹtNhớ bước make up cần thời gian tải Docker image lần đầu — làm việc này sớm, đừng để sát ngày thi.

⭐⭐ Đổi 1 biến: rule bạn viết ở bài tập 1 vô tình chặn nhầm 1 request tìm kiếm có chữ "select" trong tên sản phẩm (vd "Select Comfort Mattress"). Sửa lại regex cho hẹp hơn mà vẫn bắt được SQLi thật.

Gợi ý nếu kẹtYêu cầu có cả UNION VÀ SELECT gần nhau (union\s*(/\*.*?\*/)?\s*select) thay vì chỉ match riêng lẻ select.

⭐⭐⭐⭐ Tự nghĩ: đối thủ viết rule chặn SQLi theo đúng mẫu mục 10.B (có (?i), bắt cả comment). Thiết kế 1 payload SQLi vẫn vượt qua được rule này bằng kỹ thuật KHÁC nhóm cú pháp tương đương/encode (gợi ý: đổi vị trí payload).

Gợi ý nếu kẹtRule mẫu chỉ soi ARGS (query string + body thường) — thử gửi payload qua Cookie header nếu app có đọc giá trị từ đó vào query, xem rule có áp dụng cho REQUEST_COOKIES không.

Thuật ngữ

WAF (Web Application Firewall)Lớp lọc request dựa trên rule, đứng giữa người dùng và ứng dụng thật.
Parser differentialSự khác biệt trong cách 2 thành phần (WAF và app) hiểu cùng 1 request.
DetectionOnlyChế độ WAF chỉ ghi log khi rule khớp, không thực sự chặn — dùng để kiểm tra an toàn trước khi bật chặn thật.
Catastrophic backtrackingLỗi hiệu năng của regex khi cấu trúc lồng nhiều lượng tử (+/*) khiến thời gian khớp tăng theo cấp số nhân với input dài.
