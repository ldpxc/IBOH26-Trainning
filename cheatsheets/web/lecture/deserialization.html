Insecure Deserialization

Khi app nhận 1 chuỗi đã "đóng gói" (serialize) object — thường qua cookie/token — rồi tự động "mở gói" (deserialize) lại thành object thật mà không kiểm tra nội dung, bạn có thể tự tạo 1 chuỗi độc, khiến quá trình mở gói tự gọi các hàm có sẵn trong code theo trình tự bạn chọn (gọi là gadget chain), thường dẫn thẳng tới RCE.

Insecure Deserialization là gì, để làm gì?

Serialize là biến 1 object trong bộ nhớ thành 1 chuỗi text/byte để lưu trữ hoặc gửi đi (vd lưu session, gửi qua cookie). Deserialize là chiều ngược lại — đọc chuỗi đó, tự động "dựng lại" thành object thật, gọi cả các hàm đặc biệt của object đó (constructor, destructor...) trong quá trình dựng. Nếu app deserialize dữ liệu từ người dùng (không chỉ dữ liệu tự nó tạo ra), bạn có thể tự viết 1 chuỗi serialize giả, chọn đúng class nào được dựng — nếu trong code có sẵn 1 chuỗi class mà hàm đặc biệt của chúng (khi gọi liên tiếp) dẫn tới thực thi lệnh, bạn đạt RCE chỉ bằng cách gửi đúng chuỗi.

Nếu chỉ nhớ một điều Dấu hiệu nhận biết theo định dạng chuỗi base64: PHP bắt đầu Tzo/YTo, Python pickle bắt đầu gASV/gAJ, Java bắt đầu rO0AB. Thấy 1 trong các dấu hiệu này trong cookie/token ⟹ gần như chắc chắn có deserialization, và cách khai thác luôn là dùng công cụ sinh sẵn gadget chain (PHPGGC/ysoserial) thay vì tự viết tay.

01 / NỀN TẢNG BẮT BUỘC

Những thứ cần hiểu trước

Serialize/Deserialize — chuyển object ↔ chuỗi, để lưu trữ/truyền đi rồi khôi phục lại object y hệt ban đầu.
Magic method — các hàm đặc biệt trong class được ngôn ngữ tự động gọi ở thời điểm nhất định, không cần gọi tường minh. Ví dụ PHP: __wakeup() (gọi ngay sau unserialize), __destruct() (gọi khi object bị hủy), __toString() (gọi khi object được dùng như chuỗi).
Gadget chain / POP chain — một chuỗi các class có sẵn trong code (của chính app hoặc thư viện nó dùng), khi được "dựng" liên tiếp qua các magic method, cuối cùng dẫn tới 1 hành động nguy hiểm (gọi lệnh hệ thống). Không cần app có lỗi gì đặc biệt — chỉ cần nó "tình cờ" chứa đủ các class ghép lại được thành chuỗi này (thường từ framework/thư viện phổ biến, không phải code tự viết).

Code hay viết (deserialize dữ liệu từ người dùng):

// PHP
$data = unserialize($_COOKIE['user_data']);   // input từ cookie, người dùng tự sửa được
02 / VÌ SAO LỖ HỔNG TỒN TẠI

Magic method chạy TỰ ĐỘNG, không hỏi ý bạn

Vấn đề cốt lõi: quá trình deserialize không chỉ "đọc dữ liệu" — nó thực thi code (magic method) như một tác dụng phụ tự động. Bạn, với vai trò kẻ tấn công, chọn được class nào sẽ bị dựng (chuỗi serialize ghi rõ tên class), nên bạn chọn đúng class có magic method làm điều bạn muốn — dù chính bạn không hề viết ra class đó, nó vốn đã có sẵn trong framework/thư viện app dùng.

06 / THEO NGÔN NGỮ — CÁCH TIẾP CẬN KHÁC NHAU

Mỗi ngôn ngữ một kiểu gadget

A. PHP — unserialize()

Magic method quan trọng: __wakeup() (sau unserialize), __destruct() (khi object hết phạm vi sống), __toString() (khi ép kiểu chuỗi). Dùng PHPGGC (mục 07) để sinh gadget theo đúng framework. Lưu ý: Phar deserialization — nếu app gọi các hàm filesystem (file_exists, unlink...) trên 1 đường dẫn bạn kiểm soát, đổi thành phar://đường_dẫn_tới_file_phar_độc cũng kích hoạt unserialize dù không gọi trực tiếp.

B. Python — pickle

Gadget chuẩn: định nghĩa __reduce__() trả về (os.system, ("id",)) — khi unpickle, Python tự gọi hàm đó với tham số đó.

import pickle, os, base64

class Exploit:
    def __reduce__(self):
        return (os.system, ("cat flag.txt",))

payload = base64.b64encode(pickle.dumps(Exploit())).decode()
print(payload)   # dán vào cookie/field cần
Không cần công cụ ngoài cho PythonPickle gadget tự viết trực tiếp bằng __reduce__() như trên là đủ, không cần công cụ chuyên dụng như PHPGGC/ysoserial.

C. Java — ysoserial

Phức tạp hơn nhiều (cần đúng gadget khớp thư viện trên classpath của app) — luôn dùng ysoserial (mục 07), gần như không tự viết tay. Lưu ý: Java là ngôn ngữ ít gặp nhất ở CTF sinh viên theo khảo sát tần suất (xem bài Recon/tổng quan) — đầu tư thời gian ít hơn PHP/Python nếu phải chọn ưu tiên.

D. Node.js — node-serialize

⭐⭐⭐⭐ Tự nghĩ: app không deserialize trực tiếp từ cookie, nhưng có hàm file_exists($user_input) gọi trên đường dẫn do người dùng kiểm soát. Giải thích cách Phar deserialization (mục 06.A) biến lỗ hổng "chỉ kiểm tra file tồn tại" này thành RCE.

Gợi ý nếu kẹtPHP tự động "mở" file phar:// để đọc metadata (kể cả khi chỉ gọi hàm tưởng như vô hại như file_exists), và việc đọc metadata đó tự kích hoạt unserialize nội dung file phar — cần upload được 1 file phar độc trước (kết hợp bài File Upload).
