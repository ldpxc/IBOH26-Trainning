Recon & Source Leak

Trước khi nghĩ tới SQLi/XSS/SSTI... luôn kiểm tra xem server có vô tình để lộ mã nguồn hoặc file cấu hình không. Đọc được source gần như luôn là cách nhanh nhất để biết chính xác lỗ hổng nằm ở đâu — thay vì dò mù bằng payload.

00 / TÓM TẮT 1 PHÚT

Recon & Source Leak là gì, để làm gì?

Rất nhiều service bị triển khai (deploy) ẩu — quên xóa thư mục .git, để lộ file .env chứa mật khẩu database, hay quên tắt trang debug hiện toàn bộ source khi có lỗi. Việc recon (thu thập thông tin) là bước đầu tiên, bắt buộc với MỌI service bạn gặp — vì chỉ cần 5 phút kiểm tra đúng chỗ, bạn có thể đọc được toàn bộ mã nguồn thay vì phải dò mù từng loại lỗ hổng một.

Nếu chỉ nhớ một điều Luôn thử truy cập /.git/config đầu tiên với MỌI service — nếu trả về nội dung (không phải 404), bạn dump được toàn bộ lịch sử source code chỉ bằng 1 lệnh (git-dumper, mục 07), không cần tìm lỗ hổng gì khác nữa.
⚡ COMBAT CARD — đọc trước, đủ để khai thác ngay
⚡ RECON & SOURCE LEAK
🚩 Nhận ra trong 30 giây Mọi service MỚI nhận đều đáng thử ngay: /.git/config, /.env, /robots.txt, /backup.zip — nếu bất kỳ cái nào trả về 200 (không phải 404) ⟹ trúng ngay từ bước đầu tiên, không cần tìm lỗ hổng phức tạp.
✅ Tiền đề cần có Không cần gì đặc biệt — đây là bước luôn làm đầu tiên với mọi service, trước cả khi biết service đó chạy công nghệ gì.
🔍 Dò nhanh bằng curl/ffuf curl -s http://TARGET/.git/config — xem có nội dung không. Nếu có, chạy git-dumper ngay (mục 07) để lấy toàn bộ.

01 / NỀN TẢNG BẮT BUỘC

Những thứ cần hiểu trước

Deploy (triển khai) — quá trình đưa code từ máy lập trình viên lên server thật để chạy. Cách làm đúng: chỉ copy đúng file cần chạy. Cách làm ẩu (hay gặp ở service dựng nhanh cho CTF): copy nguyên cả thư mục dự án, bao gồm cả file không nên public.
Thư mục .git — nơi Git lưu toàn bộ lịch sử source code (mọi commit, mọi phiên bản từng có, kể cả những dòng code đã bị xóa sau này). Nếu thư mục này vô tình được web server phục vụ công khai, ai cũng tải về được và khôi phục lại toàn bộ source + lịch sử.
File .env — quy ước phổ biến để lưu biến môi trường (database password, API key, SECRET_KEY) tách riêng khỏi code, KHÔNG nên được web server phục vụ công khai.

Vì sao điều này hay xảy ra: khi dựng service CTF nhanh, người tạo đề thường chỉ làm git clone → docker build . hoặc copy thẳng thư mục dự án vào webroot mà quên loại trừ các file/thư mục ẩn này.

02 / VÌ SAO LỖ HỔNG TỒN TẠI

Web server phục vụ "mọi file nó tìm thấy", không chỉ file được định sẵn

Mặc định, nhiều web server (đặc biệt cấu hình đơn giản như Python http.server, hoặc Apache/Nginx không cấu hình kỹ) sẽ phục vụ bất kỳ file nào nằm trong webroot nếu có đường dẫn URL khớp tên file đó — kể cả file không định để công khai. Phải chủ động cấu hình chặn (deny rule cho .git, .env...) thì các file này mới bị giấu đi — đây không phải hành vi mặc định an toàn, mà là thứ lập trình viên phải tự nhớ làm thêm.

Trong môi trường CTF dựng nhanh (ưu tiên "chạy được" hơn "chuẩn production"), bước cấu hình thêm này rất hay bị bỏ qua.

03 / CƠ CHẾ HOẠT ĐỘNG ← MỤC LÕI

Từ .git lộ ra tới toàn bộ source

Điểm quan trọng: git-dumper không cần web server cho phép liệt kê thư mục (directory listing). Nó hoạt động bằng cách: đọc .git/config và .git/HEAD trước để biết cấu trúc repo, rồi dựa vào định dạng cố định của Git (file object luôn nằm ở .git/objects/xx/yyyy..., tên file có thể tính trước được từ hash) để tải từng file object cần thiết — kể cả khi bạn không "thấy" được danh sách file, công cụ vẫn đoán đúng đường dẫn cần tải.

07 / CÔNG CỤ THỰC CHIẾN: GIT-DUMPER, GITTOOLS & FFUF

Không muốn tự tải từng file .git? Dùng công cụ

A. git-dumper — dump toàn bộ .git chỉ bằng 1 lệnh

git-dumper — tự động: đọc .git/config+HEAD, suy ra toàn bộ object cần tải, tải về, rồi tự git checkout để bạn có nguyên source code như lúc clone bình thường. Đã clone về ~/hoc/CTF/Tools/web/git-dumper/ (từ arthaud/git-dumper, 2700+ sao).
python3 ~/hoc/CTF/Tools/web/git-dumper/git_dumper.py http://TARGET/.git/ ./dumped_source
cd dumped_source
git log --oneline     # xem lịch sử commit -- có thể thấy cả dòng code đã bị xóa
git show --all         # xem mọi commit, kể cả nhánh/commit không còn trên HEAD
Mẹo tìm bí mật trong lịch sửĐôi khi mật khẩu/API key bị commit nhầm rồi xóa ở commit sau — vẫn còn trong lịch sử Git. Dùng git log -p | grep -iE "password|secret|key" để tìm qua mọi commit, không chỉ bản mới nhất.

B. GitTools — bộ công cụ đầy đủ hơn (Dumper + Extractor + Finder)

GitTools (internetwache/GitTools, 4100+ sao): gồm 3 công cụ — Finder (quét hàng loạt domain xem cái nào lộ .git), Dumper (tương tự git-dumper), Extractor (khi chỉ tải được 1 phần file .git thô, dựng lại cấu trúc commit từ những gì có). Đã clone về ~/hoc/CTF/Tools/web/GitTools/.
# Nếu git-dumper không tải được đầy đủ, thử Extractor trên phần đã tải
cd ~/hoc/CTF/Tools/web/GitTools/Extractor
bash extractor.sh /duong/dan/da/tai ./extracted

C. ffuf — fuzz tìm file/thư mục không đoán được tên (đã cài sẵn)

ffuf -u "http://TARGET/FUZZ" \
     -w ~/hoc/CTF/Tools/web/SecLists/Discovery/Web-Content/raft-small-files.txt \
     -mc 200,403
Vì sao thêm 403 vào -mcFile/thư mục trả 403 (Forbidden) nghĩa là NÓ TỒN TẠI nhưng bị chặn liệt kê — vẫn đáng thử tải trực tiếp file bên trong (như trường hợp .git/ bị 403 ở mục Combat Card) thay vì bỏ qua chỉ vì không phải 200.
08 / VIẾT SCRIPT KHAI THÁC (3 BẢN)

Từ tay-gõ-Burp sang script tự động

(A) Bản thủ công — để HIỂU từng bước

import requests

url = "http://TARGET"
paths = [".git/config", ".env", "robots.txt", "backup.zip"]

for p in paths:
    r = requests.get(f"{url}/{p}")
    print(p, r.status_code, len(r.text))
    if r.status_code == 200:
        print(r.text[:300])   # xem thử nội dung nếu lộ

(B) Bản gọn chắc — quét nhiều path + đọc flag trực tiếp nếu lộ

import re, requests

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")
PATHS = [".git/config", ".env", "config.php.bak", "backup.zip", ".git/HEAD"]

def scan_leaks(host):
    for p in PATHS:
        r = requests.get(f"http://{host}/{p}", timeout=5)
        if r.status_code == 200:
            m = FLAG_RE.search(r.text)
            if m:
                return m.group()
            print(f"[{host}] Lộ: {p} ({len(r.text)} bytes) -- kiểm tra tay, có thể cần git-dumper")
    return None

print(scan_leaks("TARGET_IP"))

(C) Bản A/D tái dùng — chạy mọi đội, mọi round

import re, requests

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")
PATHS = [".env", "config.php.bak", ".git/HEAD"]   # đã xác nhận .env ăn từ bước thử tay

def scan_leaks(host):
    try:
        for p in PATHS:
            r = requests.get(f"http://{host}/{p}", timeout=5)
            if r.status_code == 200:
                m = FLAG_RE.search(r.text)
                if m:
                    return m.group()
    except requests.RequestException:
        pass
    return None

if __name__ == "__main__":
    for host in open("teams.txt").read().split():
        flag = scan_leaks(host)
        if flag:
            print(f"{host} {flag}")
            with open("flags.txt", "a") as f:
                f.write(f"{flag}\n")
Lưu ý quan trọng cho recon trong A/DRecon thường chỉ cần làm 1 lần trên service của chính mình (vì mọi đội chạy cùng service, nên cấu trúc file/lỗ hổng giống nhau) — không phải chạy lại scan mỗi round. Sau khi recon xong và biết chính xác payload/đường dẫn nào ăn, chỉ script khai thác cụ thể mới cần chạy lặp lại mỗi round.
09 / VÍ DỤ THỰC TẾ END-TO-END

Từ nhận service tới lấy flag

1
Recon bước đầu
Nhận service mới toanh, chưa biết gì. Thử ngay curl http://TARGET/.git/config → trả về nội dung config Git thật ⟹ lộ.
2
Dump source
Chạy git-dumper, có toàn bộ source trong vài giây tới vài phút tùy kích thước repo.
3
Đọc source tìm lỗ hổng
Thấy app.py có dòng render_template_string(f"...{name}...") ⟹ xác định ngay là SSTI, không cần dò.
4
Đọc source tìm flag/secret
Grep git log -p | grep -i flag hoặc tìm trong file config — nếu flag hardcode sẵn (hiếm nhưng có ở challenge dễ), lấy luôn không cần khai thác gì thêm.
5
Khai thác đúng mục tiêu
Dùng payload SSTI đã biết chắc chắn ăn (xem bài SSTI), vì đã đọc source xác nhận trước.
10 / PHÒNG THỦ: VIẾT WAF RULE

Chặn đúng payload, không chặn nhầm request thường

Rule (soi URL path)Khớp gì
^/\.git/Mọi truy cập vào thư mục .git — gần như không có lý do hợp lệ nào cần truy cập trực tiếp đường dẫn này từ bên ngoài
^/\.env$File .env — tương tự, không nên truy cập công khai
\.(bak|swp|old)$File backup/tạm phổ biến
Đây là nhóm hiếm hoi WAF chặn HIỆU QUẢ CAOKhác với IDOR/Race Condition/Type Juggling, nhóm Recon & Source Leak chặn được tốt bằng WAF vì đường dẫn /.git/, /.env gần như không bao giờ là request hợp lệ của người dùng thật — rủi ro chặn nhầm cực thấp. Nên ưu tiên áp các rule này sớm ngay từ đầu trận.

12 / NHẬN DIỆN & GIỚI HẠN

Khi nào ĐƯỢC / KHÔNG dùng

Tình huống
✅Service deploy bằng cách copy nguyên thư mục dự án (bao gồm .git/.env) lên webroot, không có rule chặn các đường dẫn ẩn.
❌Service build qua pipeline đúng chuẩn (multi-stage Docker build chỉ copy artifact cần thiết, không copy source thô) — không có gì để leak theo cách này.
❌Web server/reverse proxy đã cấu hình chặn rõ ràng mọi đường dẫn bắt đầu bằng dấu chấm.
13 / BÀI TẬP & THUẬT NGỮ

Luyện tập

⭐ Làm lại: dựng ví dụ mục 09 bằng tay — curl thử từng path mục 06, nếu .git lộ thì chạy git-dumper, đọc source tìm 1 dòng code có lỗ hổng.

Gợi ý nếu kẹtNhớ thử cả .git/config lẫn .git/HEAD — đôi khi 1 trong 2 lộ trong khi cái kia không (tùy cấu hình chặn).

⭐⭐ Đổi 1 biến: /.git/ trả 403 (bị chặn liệt kê). Dùng git-dumper xem có vẫn dump được không, giải thích vì sao có/không.

Gợi ý nếu kẹtgit-dumper không cần liệt kê thư mục — nó tự tính tên file object từ config/HEAD đã đọc được trước đó. Nếu các file CON (như .git/objects/ab/cdef...) cũng bị chặn luôn (không chỉ chặn index) thì mới thực sự vô dụng.

⭐⭐⭐⭐ Tự nghĩ: không có .git, không có .env, robots.txt trống. Thiết kế 1 wordlist fuzz riêng (5-10 mục) nhắm đúng đặc thù 1 service Flask/Python điển hình (không dùng wordlist chung) để tăng khả năng tìm ra file lộ.

Gợi ý nếu kẹtNghĩ tới quy ước đặt tên phổ biến của Python/Flask: requirements.txt, wsgi.py, app.py.bak, __pycache__/, instance/config.py.
