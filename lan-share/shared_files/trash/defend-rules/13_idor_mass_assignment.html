Mẫu Luật Phòng Thủ: IDOR, Broken Access Control & Mass Assignment

  • Nguồn tham chiếu: attack/idor_access_control.html, attack/mass_assignment.html, attack/access.html
  • Nhóm OWASP CRS liên quan: Không có rule chuẩn cho logic nghiệp vụ (đội phải tự viết).
  • Dải Rule ID: 25300–25399 (Config Type: MODSEC)
  • Khả năng vá bằng WAF:
  • Mass Assignment & Header Override: Rất cao (chặn trường nhạy cảm như role, is_admin, balance trên route đăng ký/cập nhật profile).
  • IDOR ngang (user A đổi id=2 thành id=1): WAF không tự biết user nào sở hữu id nào, nhưng có thể chặn các bypass method override (X-HTTP-Method-Override), URL override (X-Original-URL, X-Rewrite-URL) và chặn trùng tham số (HPP).

1. Dấu hiệu tấn công chính cần chặn

  • Mass Assignment: Gửi kèm trường đặc quyền trong POST/PUT/PATCH đăng ký hoặc sửa hồ sơ: role, is_admin, isAdmin, admin, permissions, privilege, balance, credit, verified, active, owner_id, user_id.
  • Access Control Bypass qua Header: X-Original-URL, X-Rewrite-URL, X-HTTP-Method-Override, X-Method-Override, X-Custom-IP-Authorization.
  • HTTP Parameter Pollution (HPP): Truyền 2 lần user_id=2&user_id=1 để WAF kiểm tra giá trị đầu còn backend lấy giá trị sau.

2. Bộ luật ModSecurity v3 mẫu

# [25301] Chặn Mass Assignment: cấm gửi các trường nhạy cảm ở route đăng ký/cập nhật user
SecRule REQUEST_FILENAME "@rx (?i)^/api/(?:register|signup|profile|users?|account)(?:/[^/]*)?$" \
    "id:25301,phase:2,pass,log,t:none,t:normalizePath,chain,msg:'MassAssign: Privileged field in user request',tag:'mass-assignment',logdata:'%{MATCHED_VAR_NAME}'"
    SecRule ARGS_NAMES "@rx (?i)^(?:json\.)?(?:is_?admin|admin|role|roles|privilege|permissions?|balance|credit|verified|is_?verified|is_?staff|is_?superuser|group_?id)\z" "t:none"

# [25302] Chặn header đánh lừa routing/phân quyền (X-Original-URL, X-Rewrite-URL...)
SecRule REQUEST_HEADERS_NAMES "@rx (?i)^(?:X-Original-URL|X-Rewrite-URL|X-Override-URL|X-HTTP-Method-Override|X-Method-Override|X-Custom-IP-Authorization)\z" \
    "id:25302,phase:1,pass,log,t:none,msg:'BAC: Dangerous override header',tag:'access-control',logdata:'%{MATCHED_VAR}'"

# [25303] Chặn HTTP Parameter Pollution (gửi trùng lặp tham số id / user_id / account_id)
SecRule &ARGS:id|&ARGS:user_id|&ARGS:account_id "@gt 1" \
    "id:25303,phase:2,pass,log,t:none,msg:'IDOR/HPP: Duplicate sensitive ID parameter',tag:'access-control',logdata:'%{MATCHED_VAR_NAME}=%{MATCHED_VAR}'"

# [25304] Chỉ cho phép đúng HTTP Method hợp lệ trên endpoint nhạy cảm (chống verb tampering)
SecRule REQUEST_FILENAME "@rx (?i)^/api/admin/" \
    "id:25304,phase:1,pass,log,t:none,t:normalizePath,chain,msg:'BAC: Disallowed HTTP method on admin route',tag:'access-control',logdata:'%{REQUEST_METHOD} %{REQUEST_FILENAME}'"
    SecRule REQUEST_METHOD "!@rx ^(?:GET|POST)\z" "t:none"

3. Giải thích chi tiết từng luật

Rule ID Biến & Transform Cơ chế hoạt động Mức độ an toàn bật deny
25301 REQUEST_FILENAME + ARGS_NAMES Chặn Mass Assignment: cấm client tự gửi các tên trường đặc quyền (is_admin, role, balance, verified, group_id...) lên các route đăng ký hoặc cập nhật hồ sơ. Cao (kiểm tra form thật của bot trước)
25302 REQUEST_HEADERS_NAMES Chặn các header giả mạo đường dẫn/phương thức (X-Original-URL, X-Rewrite-URL, X-HTTP-Method-Override) thường dùng để lách kiểm tra phân quyền. Rất cao
25303 &ARGS:id\|&ARGS:user_id\|&ARGS:account_id Dùng toán tử đếm & (@gt 1) để chặn HTTP Parameter Pollution khi đối thủ gửi 2 lần cùng 1 tham số ID (?id=2&id=1). Rất cao
25304 REQUEST_FILENAME + REQUEST_METHOD Chặn Verb Tampering (gửi PUT, DELETE, PATCH, HEAD lạ lên /api/admin/ để bỏ qua check phân quyền chỉ viết cho GET/POST). Cao (khớp đúng method của route admin)

4. Cách sửa khi gặp trường hợp thực tế (Ví dụ)

Ví dụ 1: Form đăng ký hợp lệ của app tự gửi kèm {"username":"a","role":"user"}

Nếu bot SVC gửi role=user nên bị 25301 chặn nhầm vì 25301 cấm luôn tên trường role: - Cách sửa 25301: Bỏ role khỏi danh sách cấm tên ở 25301, và thêm 1 rule Allowlist giá trị riêng cho role chỉ được phép là user (hoặc member):

# Bản sửa thực tế: cho phép gửi role=user nhưng chặn role=admin/staff
SecRule REQUEST_FILENAME "@rx (?i)^/api/(?:register|signup|profile)/?$" \
    "id:25310,phase:2,deny,status:403,log,t:none,t:normalizePath,chain,msg:'MassAssign: Escalated role value',tag:'mass-assignment',logdata:'role=%{MATCHED_VAR}'"
    SecRule ARGS:role|ARGS:json.role "!@rx (?i)^(?:user|member)\z" "t:none,t:urlDecodeUni"

Ví dụ 2: JSON lồng nhau {"user": {"is_admin": true}}

ModSecurity parse JSON lồng thành ARGS_NAMES = json.user.is_admin. - Cách sửa 25301: Đổi phần đầu regex từ ^(?:json\.)? thành ^(?:json\.(?:[A-Za-z0-9_]+\.)*)? để bắt cả trường đặc quyền lồng bên trong object con.

5. Lưu ý tránh False Positive (SVC)

  • Trước khi bật deny cho 25301, kiểm tra Traffic log xem form đăng ký/cập nhật hợp lệ của bot SVC có tự gửi kèm role=user mặc định hay không.
  • Không chặn X-Forwarded-For vì reverse proxy của BTC tự gắn header này.
