Mẫu Luật Phòng Thủ: CSRF & CORS Misconfiguration

  • Nguồn tham chiếu: attack/csrf.html, attack/cors.html, attack/access.html
  • Nhóm OWASP CRS liên quan: Không có rule chuẩn (cần cấu hình theo domain dịch vụ).
  • Dải Rule ID: 25400–25499 (Config Type: MODSEC)
  • Khả năng vá bằng WAF: Cao (kiểm tra Origin / Sec-Fetch-Site cho request đổi trạng thái và chặn Origin: null / origin lạ cho CORS).

1. Dấu hiệu tấn công chính cần chặn

  • CSRF: Request POST/PUT/DELETE/PATCH gửi từ trang web khác (Sec-Fetch-Site: cross-site) hoặc mang Origin khác với Host của dịch vụ.
  • CORS Misconfiguration: Kẻ tấn công gửi Origin: null (qua sandboxed iframe), hoặc Origin: https://evil.com, hoặc Origin: http://target.local.evil.com để lợi dụng backend phản chiếu Access-Control-Allow-Origin kèm Access-Control-Allow-Credentials: true.

2. Bộ luật ModSecurity v3 mẫu

# [25401] Chặn Origin: null (kỹ thuật khai thác CORS qua sandboxed iframe)
SecRule REQUEST_HEADERS:Origin "@rx (?i)^null\z" \
    "id:25401,phase:1,pass,log,t:none,msg:'CORS: Null Origin header rejected',tag:'cors',logdata:'Origin=%{MATCHED_VAR}'"

# [25402] Chặn request thay đổi trạng thái (POST/PUT/DELETE/PATCH) có Sec-Fetch-Site: cross-site
SecRule REQUEST_METHOD "@rx ^(?:POST|PUT|DELETE|PATCH)\z" \
    "id:25402,phase:1,pass,log,t:none,chain,msg:'CSRF: Cross-site state-changing request',tag:'csrf',logdata:'Sec-Fetch-Site=%{REQUEST_HEADERS.Sec-Fetch-Site}'"
    SecRule REQUEST_HEADERS:Sec-Fetch-Site "@streq cross-site" "t:none"

# [25403] Chặn Origin lạ khác domain/IP dịch vụ (thay teamXX\.fhacker\.local hoặc IP thật của đội)
SecRule REQUEST_HEADERS:Origin "@rx ^.+" \
    "id:25403,phase:1,pass,log,t:none,chain,msg:'CSRF/CORS: Untrusted Origin header',tag:'cors',logdata:'Origin=%{REQUEST_HEADERS.Origin}'"
    SecRule REQUEST_HEADERS:Origin "!@rx (?i)^https?://(?:localhost|127\.0\.0\.1|team\d+\.fhacker\.local)(?::\d{1,5})?\z" "t:none"

# [25404] Phase 3: Phát hiện backend phản chiếu Access-Control-Allow-Origin: * kèm Credentials: true
SecRule RESPONSE_HEADERS:Access-Control-Allow-Credentials "@rx (?i)^true\z" \
    "id:25404,phase:3,pass,log,t:none,chain,msg:'CORS: Response allows credentials with suspicious ACAO',tag:'cors',logdata:'ACAO=%{RESPONSE_HEADERS.Access-Control-Allow-Origin}'"
    SecRule RESPONSE_HEADERS:Access-Control-Allow-Origin "@rx (?i)^(?:\*|null)\z" "t:none"

3. Giải thích chi tiết từng luật

Rule ID Biến & Transform Cơ chế hoạt động Mức độ an toàn bật deny
25401 REQUEST_HEADERS:Origin Chặn Origin: null — kỹ thuật kinh điển dùng <iframe sandbox> để khai thác CORS khi backend cho phép null. Rất cao
25402 REQUEST_METHOD + REQUEST_HEADERS:Sec-Fetch-Site Chặn mọi request đổi trạng thái (POST/PUT/DELETE/PATCH) bị trình duyệt đánh dấu là cross-site (chặn thẳng CSRF từ trang độc hại). Rất cao
25403 REQUEST_HEADERS:Origin Nếu request có mang header Origin, bắt buộc Origin phải trùng đúng domain/IP dịch vụ của đội; mọi origin lạ (evil.com, team01.fhacker.local.evil.com) bị chặn. Cao (cần điền đúng domain/IP thật)
25404 RESPONSE_HEADERS:Access-Control-Allow-Credentials + Access-Control-Allow-Origin (Phase 3) Phát hiện cấu hình CORS nguy hiểm ở backend khi vừa bật Credentials: true vừa trả ACAO: * hoặc null. Nên để pass,log để cảnh báo

4. Cách sửa khi gặp trường hợp thực tế (Ví dụ)

Ví dụ 1: Dịch vụ của đội lúc thi chạy ở IP http://10.10.20.5:8080

Khi mở Traffic log, thấy trình duyệt/frontend gửi Origin: http://10.10.20.5:8080. - Cách sửa 25403: Thay team\d+\.fhacker\.local bằng đúng IP 10\.10\.20\.5 (nhớ escape dấu chấm \. và cho phép cổng :8080):

# Bản sửa thực tế từ [25403] cho IP dịch vụ 10.10.20.5:8080
SecRule REQUEST_HEADERS:Origin "@rx ^.+" \
    "id:25403,phase:1,deny,status:403,log,t:none,chain,msg:'CSRF/CORS: Untrusted Origin',tag:'cors',logdata:'Origin=%{REQUEST_HEADERS.Origin}'"
    SecRule REQUEST_HEADERS:Origin "!@rx (?i)^https?://(?:10\.10\.20\.5|localhost|127\.0\.0\.1)(?::\d{1,5})?\z" "t:none"

Ví dụ 2: App bị CSRF qua phương thức GET (vd GET /api/change-email?email=attacker@x.com)

Rule 25402 mặc định chỉ kiểm tra POST|PUT|DELETE|PATCH. Nếu gặp chức năng nhạy cảm dùng GET, thêm 1 rule riêng cho route đó chặn Sec-Fetch-Site: cross-site hoặc yêu cầu Referer thuộc đúng domain của đội.

5. Lưu ý tránh False Positive (SVC)

  • Bot chấm SVC chạy bằng Python/curl thường không gửi Origin hay Sec-Fetch-Site, nên 25401–25403 hoàn toàn không làm ảnh hưởng đến bot.
  • Trước khi chuyển 25403 sang deny, bắt buộc kiểm tra đúng Host / domain trong Traffic log và cập nhật regex allowlist trong 25403 cho khớp 100%.
