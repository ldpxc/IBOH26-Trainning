1. Tổng quan hệ thống WAF của BTC

1.1. WAF này gồm những thành phần gì?

Image WAF BTC dùng lúc thi (ghcr.io/f-hacker-macos/custom_waf26:latest) được dựng trực tiếp từ BunkerWeb 1.6.16 nguyên bản (bunkerity/bunkerweb-all-in-one:1.6.16). BTC không sửa phần lõi (core) mà chỉ thêm: - Giao diện F-Hacker (mặc định Tiếng Việt, có thể đổi sang Tiếng Anh ở góc trên phải). - Plugin Traffic log (xem lịch sử Request/Response + rule khớp kiểu Burp Suite). - Bộ cấu hình mặc định (seed sẵn ModSecurity + OWASP CRS v4 ở chế độ DetectionOnly và 1 file rule mẫu mau-rule-phong-thu). - Trình soạn thảo Configs có tô màu cú pháp cho ModSecurity (MODSEC / MODSEC_CRS).

Bên trong WAF chạy 3 lớp chính: 1. NGINX (Reverse Proxy): Đứng trước nhận toàn bộ request rồi chuyển vào ứng dụng web phía sau. 2. ModSecurity v3 (libmodsecurity3): Bộ máy đọc và thực thi các rule phòng thủ (cả rule của OWASP CRS lẫn rule đội bạn tự viết). 3. OWASP CRS v4 (Core Rule Set): Bộ luật phòng thủ chuẩn quốc tế được bật sẵn (dải rule ID 900000–999999), hoạt động theo cơ chế tính điểm bất thường (Anomaly Score) — khi tổng điểm đạt ngưỡng (>= 5), rule 949110 sẽ kích hoạt chặn request.

Mỗi khi bạn bấm Save một file rule bị lỗi cú pháp, thông báo lỗi chi tiết từ nginx -t sẽ hiện tại đây.

2.1. Home (Trang chủ)

Các thành phần trên Trang chủ: 1. Bộ chọn khung thời gian (15 phút, 1 giờ, 6 giờ, 24 giờ, Tất cả) + nút làm mới: Thu hẹp biểu đồ vào đúng round đang thi (nên để 15 phút khi thi để nhìn biến động ngay lập tức). 2. Biểu đồ Tổng request: Hiển thị 3 đường theo thời gian thực: - Đường xanh dương: Tổng request đi qua WAF. - Đường cam: Khớp rule ModSecurity (request bị đánh dấu bất thường). - Đường tím: Bị chặn (số request đã bị WAF từ chối). 3. Khối Chế độ WAF (góc phải trên): - Báo rõ WAF đang ở chế độ Chỉ ghi log (DetectionOnly) hay Đang chặn (On). Khi đang ở DetectionOnly, có nút chuyển nhanh Bật chặn ngay tại đây. - 4 ô đèn trạng thái (WAF → ModSec → CRS → app): Tất cả chấm xanh lá nghĩa là chuỗi xử lý đang hoạt động bình thường. 4. Khối Mã trạng thái HTTP (góc phải dưới): Đếm số lượng 2xx (xanh), 3xx, 4xx (cam — thường tăng khi WAF chặn 403), 5xx (đỏ — cảnh báo app lỗi hoặc Phase 4 cắt response, cần mở Traffic log kiểm tra ngay!).

2.2. Traffic log (Lịch sử HTTP kiểu Burp Suite)

Đây là màn hình bạn sẽ mở 80% thời gian thi. Chức năng của từng khu vực:

  1. Tab Lịch sử / Hướng dẫn (góc phải trên): - Lịch sử: xem danh sách request. - Hướng dẫn: tài liệu tra cứu nhanh cú pháp tìm kiếm của BTC viết sẵn ngay trên giao diện (không cần nhớ thuộc lòng).
  2. Thanh công cụ lọc phía trên bảng: - Ô chọn nguồn log (bên trái): Mặc định là traffic.log (toàn bộ traffic, đang ghi). Có thể bấm xổ xuống để chọn các file log cũ (rotate) hoặc chuyển sang modsec_audit.log khi cần xem body lớn hơn giới hạn của traffic.log. - Ô tìm kiếm + nút Tìm + nút Bộ lọc: Lọc nhanh request theo nhiều điều kiện. - Công tắc Live 5s: Bật lên để bảng tự động tải request mới mỗi 5 giây (rất tiện để canh xem bot chấm SVC và đối thủ đang gửi gì).
  3. Các cột trong bảng lịch sử: - #, GIỜ, METHOD (GET/POST...), HOST, URL, STATUS (200 xanh, 403 đỏ/nâu, 500 đỏ). - Cột WAF: Hiện ID rule ModSecurity đầu tiên khớp + số lượng rule khớp thêm (ví dụ 942100 +2 nghĩa là khớp 942100 và 2 rule nữa; dấu — nghĩa là sạch, không khớp rule nào). - CONTENT-TYPE, LENGTH (kích thước response; hiện 8,192+ nếu vượt giới hạn capture 8 KiB của traffic.log), MS (thời gian xử lý tính bằng mili-giây — nếu thấy tăng vọt bất thường có thể do rule regex quá nặng).
  4. Khung chi tiết khi bấm vào một dòng: - Các dải màu đỏ ở giữa: Liệt kê từng rule ModSecurity khớp với request đó, gồm: Rule ID, severity, mô tả (msg), Matched Data (chính xác chuỗi ký tự/tham số nào bị bắt!), và tags. - 2 khung song song Request và Response: Có nút Pretty (tự format JSON đẹp dễ đọc) / Raw (nguyên bản) và nút Copy để copy nhanh sang terminal/Burp test lại.

Bảng cú pháp tìm kiếm nhanh trên Traffic log

Các từ khóa cách nhau bằng dấu cách mặc định là phép AND. Không hỗ trợ OR, NOT, regex. Cụm có dấu cách đặt trong ngoặc kép "...".

Cú pháp nhập vào ô tìm kiếm Tác dụng
modsec.id: Hiện tất cả request có khớp ít nhất 1 rule ModSecurity
modsec.id:20100 Chỉ hiện request khớp đúng rule ID 20100
modsec.tag:sqli hoặc modsec.tag:attack-sqli Lọc theo tag (rule đội dùng tag ngắn như sqli, rule CRS dùng attack-sqli, attack-xss, attack-lfi...)
modsec.msg:xss Tìm chuỗi trong thông báo msg của rule
status:403 / status:4xx / status:5xx Lọc theo mã trạng thái cụ thể hoặc theo dải mã
method:POST uri:"/api/login" Kết hợp Method và URL
request.body.username:admin Tìm trường username bên trong JSON hoặc Form request body
response.body.data.0.name:x Tìm trường lồng nhau trong JSON response body
"FHACKER2026{" Truy vết rò rỉ cờ: tìm mọi request/response có chứa chuỗi Flag

Lưu ý về dung lượng log: - traffic.log chỉ lưu tối đa 16 KiB request body và 8 KiB response body. - modsec_audit.log lưu được body lớn hơn rất nhiều (đã kiểm chứng >100 KiB; chịu giới hạn xử lý của ModSecurity là 128 KiB cho body không file và 512 KiB cho response). Nếu thấy nghi vấn mà traffic.log bị cắt cụt, hãy chuyển ô nguồn log sang modsec_audit.log.

2.3. Configs (Cấu hình - Nơi viết và quản lý Rule)

Đây là nơi bạn tạo, chỉnh sửa, bật hoặc tắt các file rule ModSecurity của đội (và cũng có sẵn file rule mẫu mau-rule-phong-thu của BTC để tham khảo).

Các nút điều khiển khi tạo/sửa Config

  1. Service: Luôn chọn Global (áp dụng cho service của đội).
  2. Config Type: Quyết định vị trí và thứ tự nạp file của bạn vào NGINX/ModSecurity (xem bảng dưới).
  3. Configuration Name: Đặt tên gợi nhớ (không dấu, không khoảng trắng, ví dụ team-rules, fix-fp-crs). Đuôi .conf được tự động gắn thêm.
  4. Nút Online: Trạng thái bật/tắt của file config.
  5. Nút xanh Save: Lưu vào database PostgreSQL → scheduler của BunkerWeb tự sinh lại cấu hình NGINX, chạy kiểm tra cú pháp nginx -t, rồi reload không làm gián đoạn kết nối (mất khoảng 2–5 giây).

Thứ tự nạp các loại Config Type (Phải nắm chắc!)

Config Type Thứ tự nạp Dùng để làm gì?
MODSEC_CRS Nạp TRƯỚC OWASP CRS Đặt các rule ctl:ruleRemoveTargetById=... hoặc ctl:ruleRemoveByTag=OWASP_CRS theo từng route cụ thể (gỡ False Positive của CRS trước khi CRS chạy).
MODSEC Nạp SAU OWASP CRS Dùng chính: Viết toàn bộ rule phòng thủ của đội (ID 20000–29999), và dùng SecRuleRemoveById / SecRuleUpdateTargetById để gỡ rule CRS đã nạp.
HTTP / SERVER_HTTP Cấu hình NGINX Dùng khi cần chỉnh directive thuần của NGINX (ví dụ header, limit, rewrite...) — đa phần lúc thi không cần đụng tới.
CRS_PLUGINS_BEFORE / CRS_PLUGINS_AFTER KHÔNG ĐƯỢC NẠP! BTC đã khóa USE_MODSECURITY_CRS_PLUGINS=no. Tuyệt đối không đặt rule vào 2 loại này vì rule sẽ không bao giờ chạy!

Quy ước dải số Rule ID (tránh trùng ID gây lỗi reload)

  • 10000–10099: File mẫu mau-rule-phong-thu của BTC.
  • 20000–29999: Dành cho đội thi tự do sử dụng.
  • 200000+: Rule nội bộ của BunkerWeb.
  • 900000–999999: Bộ rule OWASP CRS v4.

Cơ chế an toàn khi viết sai cú pháp: Nếu file bạn bấm Save bị lỗi cú pháp (trùng id, thiếu dấu ngoặc kép, viết id: vào dòng con của chain...), nginx -t sẽ thất bại. BunkerWeb KHÔNG làm sập WAF mà tự động giữ nguyên cấu hình cũ đang chạy và bắn cảnh báo vào nút cam NOTIFICATIONS góc trên phải (cũng ghi vào Logs → error.log).

2.4. Global Settings (Cài đặt chung)

Trang này chứa toàn bộ cấu hình module của BunkerWeb. Trong cuộc thi, bạn chủ yếu chỉ cần quan tâm mục ModSecurity ở cột bên trái:

Tham số trên UI Tên biến cấu hình Mặc định Ý nghĩa & Lưu ý khi thi
Use ModSecurity USE_MODSECURITY Bật (yes) Công tắc tổng bật/tắt toàn bộ WAF ModSecurity. Luôn giữ bật.
Use Core Rule Set USE_MODSECURITY_CRS Bật (yes) Bật/tắt bộ luật OWASP CRS v4. Nên giữ bật và chỉ gỡ từng rule gây False Positive.
Core Rule Set Version MODSECURITY_CRS_VERSION 4 Phiên bản OWASP CRS đang dùng (v4). Giữ nguyên.
SecRuleEngine MODSECURITY_SEC_RULE_ENGINE DetectionOnly Quan trọng nhất! Chuyển giữa DetectionOnly (chỉ ghi log, không chặn ai) và On (chặn thật khi khớp rule deny hoặc CRS điểm >= 5).
SecAuditEngine MODSECURITY_SEC_AUDIT_ENGINE RelevantOnly Chỉ ghi modsec_audit.log khi request khớp rule hoặc có mã lỗi liên quan (giữ RelevantOnly để không đầy đĩa/chậm WAF).
SecAuditLogParts MODSECURITY_SEC_AUDIT_LOG_PARTS BCEFH Các phần ghi vào audit log (Request headers/body, Response headers/body, Audit trailer). Giữ nguyên để Traffic log và waf-audit.py đọc đầy đủ.
SecRequestBodyNoFilesLimit MODSECURITY_REQ_BODY_NO_FILES_LIMIT 131072 (128 KiB) Giới hạn kích thước body (không tính file upload) mà ModSecurity kiểm tra.
SecRequestBodyLimitAction MODSECURITY_REQ_BODY_LIMIT_ACTION Reject Hành động khi body vượt giới hạn.

Nhớ bấm nút xanh Save ở góc trên phải sau khi thay đổi bất kỳ thông số nào trong Global Settings, và chờ 2–5 giây cho WAF reload!

2.5. Các mục khác: Logs, Reports, F-Hacker Changes, Plugins, NÂNG CAO

  • Logs (Log): Xem trực tiếp file log thô trên trình duyệt mà không cần SSH/Docker:
  • error.log: Nơi đầu tiên cần mở khi NOTIFICATIONS báo lỗi cú pháp config. Tìm dòng có chữ emerg hoặc ModSecurity ở cuối file sẽ thấy chính xác số dòng bị lỗi.
  • modsec_audit.log: Log JSON chi tiết của ModSecurity (body lớn >100 KiB).
  • access-web.log: Nhật ký truy cập NGINX rút gọn (có thời gian xử lý và Content-Type).
  • F-Hacker Changes: Trang tóm tắt chính thức của BTC liệt kê các thay đổi so với BunkerWeb gốc và danh sách các chức năng bị tắt kèm lý do — mở xem lại bất cứ lúc nào nếu quên.
  • Reports: Biểu đồ thống kê tổng hợp.
  • Plugins: Hỗ trợ upload plugin tùy chỉnh định dạng .zip (chứa plugin.json + mã Lua/Jinja theo chuẩn BunkerWeb 1.6.16) — chỉ dành cho đội đã chuẩn bị sẵn plugin trước giờ thi.
  • NÂNG CAO >: Chứa các trang quản trị hệ thống (Services, Templates, Instances, Jobs, Cache, Bans, Support). Không nên bấm sửa lung tung trong mục này (đặc biệt Services / Reverse proxy) để tránh làm đứt kết nối vào app của đội và rớt SVC.

3. Các tính năng bị BTC khóa tắt và tính năng không nên bật

Tại sao nhiều tính năng chống tấn công quen thuộc của BunkerWeb lại bị khóa mờ trong Global Settings? Vì 2 đặc thù của phòng thi: 1. Mọi request (đối thủ + bot chấm SVC) đều đi qua cùng 1 IP reverse proxy của BTC. Nếu bạn chặn hoặc giới hạn tốc độ theo IP → chặn luôn bot chấm điểm → SVC = 0 → DEF = 0! 2. Phòng thi cách ly hoàn toàn với Internet. Các tính năng tải danh sách từ mạng sẽ bị treo.

4. Hướng dẫn thao tác từng bước cho 6 tình huống hay gặp nhất lúc thi

Tình huống 1: Quan sát Traffic realtime để phân biệt Bot chấm vs Đối thủ

  1. Vào menu Traffic log.
  2. Bật công tắc Live 5s góc phải bảng.
  3. Quan sát 1–2 phút đầu: - Bot chấm SVC: Gọi đều đặn theo chu kỳ ~30 giây, gửi dữ liệu sạch và hợp lệ vào các chức năng chính của app. Ghi lại danh sách endpoint + tham số của bot để tuyệt đối không chặn nhầm. - Đối thủ tấn công: Nhập modsec.id: vào ô tìm kiếm → bấm Tìm để thấy ngay các request chứa payload bị CRS đánh dấu; hoặc nhập "FHACKER2026{" để phát hiện ngay nếu có chỗ nào đang bị rò Flag!

Tình huống 2: Thêm một bộ rule mới an toàn (không làm rớt SVC)

  1. Vào Configs → bấm nút tạo mới (New / Tạo mới).
  2. Chọn Service: Global, Config Type: MODSEC, đặt Name (vd team-rules).
  3. Dán rule vào editor, ban đầu để action là pass,log (hoặc giữ WAF ở DetectionOnly).
  4. Bấm Save → chờ 3–5 giây → kiểm tra nút cam NOTIFICATIONS không có thông báo lỗi đỏ.
  5. Quay lại Traffic log, tự gửi 1 request tấn công và chờ 30 giây cho bot chấm chạy qua: - Cột WAF hiện ID rule của bạn ở dòng tấn công = rule hoạt động đúng. - Không có dòng nào của bot chấm hiện ID rule của bạn = an toàn.
  6. Quay lại Configs mở file đó → đổi pass,log thành deny,status:403,log → bấm Save.

Tình huống 3: Bật / Tắt chế độ chặn (DetectionOnly ↔ On)

  • Cách nhanh (1 bấm): Vào Home (Trang chủ) → ở khối Chế độ WAF góc phải, bấm nút Bật chặn.
  • Cách chuẩn (đổi qua lại 2 chiều): Vào Global Settings → chọn mục ModSecurity ở cột trái → tìm ô SecRuleEngine (MODSECURITY_SEC_RULE_ENGINE) → chọn On (để chặn) hoặc DetectionOnly (để tạm ngừng chặn) → bấm nút xanh Save ở góc trên phải.

Tình huống 4: Gỡ False Positive khi OWASP CRS (9xxxxx) chặn nhầm bot chấm

  1. Mở Traffic log, gõ status:403 vào ô tìm kiếm → bấm Tìm.
  2. Bấm vào dòng request hợp lệ của app/bot bị 403.
  3. Nhìn danh sách thẻ đỏ ở khung chi tiết: bỏ qua rule 949110 (chỉ là rule tổng điểm), hãy ghi lại ID rule ngay phía trên nó (vd 942100, 941100, 920350) và tên biến bị khớp (vd ARGS:content hoặc ARGS:json.content).
  4. Vào Configs → Tạo mới: - Nếu chỉ muốn gỡ ở 1 route cụ thể (khuyên dùng): Chọn Config Type: MODSEC_CRS (nạp trước CRS), đặt tên fix-crs-fp, dán: apache SecRule REQUEST_FILENAME "@rx (?i)^/api/notes/?$" \ "id:22000,phase:1,pass,nolog,t:none,t:normalizePath,\ ctl:ruleRemoveTargetById=942100;ARGS:content,\ ctl:ruleRemoveTargetById=942100;ARGS:json.content" - Nếu muốn gỡ 1 tham số/cookie trên toàn site hoặc tắt hẳn 1 rule CRS: Chọn Config Type: MODSEC (nạp sau CRS), dán: apache SecRuleUpdateTargetById 942440 "!REQUEST_COOKIES:session" # Hoặc tắt hẳn 1 rule hay báo nhầm (vd Host là IP): SecRuleRemoveById 920350
  5. Bấm Save → gửi lại request hợp lệ thấy trả 200 là thành công.

Tình huống 5: Lưu config bị báo lỗi ở NOTIFICATIONS

  1. Bấm vào nút cam NOTIFICATIONS góc trên phải để xem tóm tắt lỗi.
  2. Nếu cần xem chi tiết số dòng lỗi: vào menu Logs → chọn error.log → cuộn xuống cuối tìm dòng ModSecurity / emerg.
  3. 4 lỗi cú pháp phổ biến nhất cần kiểm tra: - Trùng id: giữa 2 rule (kể cả trùng với file mau-rule-phong-thu đang bật!). - Ghi nhầm id:..., phase:..., deny, msg:... vào rule thứ 2 của một chain. - Có dấu # chú thích nằm ngay sau ký tự nối dòng \. - Viết dấu | trong regex tên biến (ARGS:/a|b/) — phải viết tách tường minh ARGS:a|ARGS:b.
  4. Sửa lại lỗi trong Configs → bấm Save lại. (Trong thời gian bị lỗi, WAF vẫn chạy bản config cũ trước đó nên app không bị sập.)

Tình huống 6: Cấp cứu khi bảng điểm SVC đột ngột báo đỏ

  1. Cầm máu ngay trong 10 giây: - Nếu vừa mới lưu 1 rule mới: vào Configs, tạm xóa/comment rule vừa thêm (hoặc chuyển action về pass,log) → bấm Save. - Nếu nghi OWASP CRS chặn nhầm hàng loạt mà chưa kịp tìm rule nào: vào Global Settings → ModSecurity, chuyển tạm SecRuleEngine về DetectionOnly → Save để giữ điểm SVC không tụt về 0.
  2. Điều tra nguyên nhân: Mở Traffic log lọc status:403 và status:500 trong 2 phút gần nhất để tìm đúng endpoint của bot bị chặn/cắt response.
  3. Gỡ False Positive theo Tình huống 4 rồi mới bật lại On.

5. Cài đặt và sử dụng bản tập 2026-waf-practice trên máy cá nhân

Bản tập 2026-waf-practice gồm 3 container chạy qua Docker Compose: - fuap_bunkerweb: Image WAF custom_waf26:latest (App ở cổng 8000, WAF UI ở cổng 8005). - postgres: Cơ sở dữ liệu PostgreSQL 16 lưu cấu hình rule và tài khoản UI. - app (alias mạng nội bộ fuap_edge:80): App Echo (mendhak/http-https-echo) phản hồi lại nguyên vẹn method, URL, header và body bạn gửi lên dưới dạng JSON — rất tiện để test cả Phase 1–2 lẫn Phase 4 (RESPONSE_BODY).

5.1. Yêu cầu & Khởi chạy

  • Cần Docker + Docker Compose v2, tối thiểu 3 GB RAM trống, và make.
  • Chạy tại thư mục 2026-waf-practice:
cd /home/kali/Documents/2026-waf-practice
make up

(Nếu user Linux chưa active group docker trong terminal hiện tại, chạy sg docker -c 'make up'.)

Lần chạy đầu mất ~1–2 phút để khởi tạo database và chạy seed cấu hình BTC. Khi thấy dòng thông báo hoàn tất: - App đi qua WAF: http://localhost:8000/ - Giao diện quản trị WAF UI: http://localhost:8005/ - Tài khoản mặc định (trong .env): admin / ChangeMe_Bw_2026!

6. Bài tập thực hành 10 phút làm quen WAF trước ngày thi

Hãy làm đúng 6 bước này 1 lần trên máy cá nhân trước ngày thi — vào phòng thi bạn sẽ thao tác WAF như phản xạ tự nhiên:

  1. Khởi chạy lab (2 phút): Chạy make up, mở http://localhost:8005/ đăng nhập bằng admin / ChangeMe_Bw_2026!.
  2. Gửi thử request ở chế độ DetectionOnly (2 phút): bash curl -i 'http://localhost:8000/.env' curl -i 'http://localhost:8000/api/product?id=1%27%20or%201=1' curl -i -X POST http://localhost:8000/ -d 'note=FHACKER2026{aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaa}' Cả 3 lệnh lúc này đều trả 200 vì WAF đang ở DetectionOnly.
  3. Đọc Traffic log (2 phút): Mở Traffic log trên UI, lọc modsec.id:, bấm vào từng dòng xem các thẻ đỏ rule khớp, bấm qua lại giữa Pretty / Raw và thử bật Live 5s.
  4. Nạp file rule team-rules.conf qua Configs (2 phút): - Vào Configs → New → Service: Global, Config Type: MODSEC, Name: team-rules. - Dán nội dung file team-rules.conf → bấm Save → kiểm tra nút NOTIFICATIONS không có lỗi. - Chạy MODE=detect ./test-waf.sh rồi chạy sg docker -c 'python3 waf-audit.py --tests-only --since-min 5' để xem rule 20xxx của đội đã khớp.
  5. Bật chặn On & chạy kiểm thử toàn diện (2 phút): - Vào Home → bấm Bật chặn (hoặc Global Settings → ModSecurity → SecRuleEngine = On → Save). - Chạy lại curl -i 'http://localhost:8000/.env' → phải trả 403. - Chạy MODE=on ./test-waf.sh --require-block và python3 waf-bypass.py --mode on → kiểm tra tất cả đều PASS / BLOCK và không có False Positive ở nhóm benign.
  6. Tập thử xử lý lỗi cú pháp (30 giây): Cố tình sửa sai 1 dòng trong Configs (vd xóa 1 dấu ") → bấm Save → quan sát thông báo lỗi ở NOTIFICATIONS và Logs → error.log, thấy WAF vẫn chạy bình thường với bản cũ → sửa lại cho đúng và bấm Save.
